下面我按**一个真实可落地的大模型知识问答系统**来讲，不把它简化成“向量化 + topk + prompt”三步，而是拆成：

1. **离线链路：知识如何进入系统**
2. **在线链路：用户问题如何被处理**
3. **更新与治理：知识冲突、增量更新、版本一致性**
4. **交互与性能：流式输出、降低延迟、提高吞吐**

你可以把它理解为：**RAG 不是一个检索模块，而是一条完整的数据工程 + 检索工程 + 推理编排链路。**

------

# 一、系统总览：一个完整的 RAG 问答链路长什么样

一个成熟的知识问答系统，整体通常分成两部分。

## 1. 离线建库链路

负责把原始知识加工成“可检索、可追溯、可更新”的知识单元：

**数据接入 → 清洗规范化 → 文档解析 → 切片 → 元数据抽取 → embedding → 建索引 → 入库**

## 2. 在线问答链路

负责把用户问题转成最合适的回答：

**用户输入 → 意图识别 → 是否需要检索 → 查询改写 → 检索召回 → 重排筛选 → 上下文组装 → LLM 生成 → 流式返回 → 日志与反馈回流**

------

# 二、为什么一定要检索，什么时候需要检索

先回答这个根问题。

## 1. 为什么需要检索

因为大模型参数里存的是**压缩后的统计知识**，不是你的业务事实数据库。它有几个天然问题：

### 第一，知识不新

模型训练截止后，外部世界还在变化。比如公司 CEO、产品价格、政策规则、内部制度，都会变。

### 第二，知识不全

你的私域知识、企业文档、内部 FAQ、工单、规章、产品手册，并不一定在预训练中出现。

### 第三，知识不可追溯

用户问“你这个答案依据是什么”，纯参数回答往往无法给出处，而企业系统通常要求可引用、可审计。

### 第四，幻觉不可控

没有外部证据时，模型容易补全出“看起来合理但实际上错误”的内容。

所以 RAG 的本质不是“给模型喂点资料”，而是：

**让回答建立在可检索、可更新、可引用的外部知识之上。**

## 2. 什么情况下需要检索

并不是所有问题都要检索。

### 需要检索的情况

- 涉及**业务知识库**内容的问题
- 涉及**时效性事实**的问题
- 涉及**需要引用依据**的问题
- 涉及**细粒度专业知识**的问题
- 涉及**用户私域/企业私域数据**的问题

### 不一定需要检索的情况

- 闲聊
- 通用常识
- 纯写作润色
- 情感陪伴
- 与知识库无关的开放域泛问
- 用户只是在追问上一个回答的表达方式，而不是事实内容

所以在线链路里通常会先做一个**路由判断**：

- 是知识问答
- 是闲聊
- 是任务执行
- 是域外问题
- 是追问/指代依赖型问题

在 RAG（检索增强生成）系统的在线链路中，**路由判断** 指的是在用户请求进入核心处理流程之前，通过一个轻量级的决策模块，判断当前请求应该走哪条处理路径。常见路径包括：

- **直接走大模型（无需检索）**：适用于通用知识、闲聊、创意生成等场景。
- **走 RAG 链路（先检索后生成）**：适用于需要外部知识、私有数据、时效性信息等场景。
- **其他路径**：如调用特定 API、专用模型、人工兜底等。

路由判断的目的是**在保证回答质量的前提下，最小化系统延迟和成本**（因为检索、重排等步骤会消耗额外资源），同时避免将不必要的上下文注入模型造成干扰。

---

## 1. 路由判断的常见粒度

- **请求级路由**：每个独立请求都进行判断，决定走哪条链路。
- **会话级路由**：根据整个对话的上下文（如用户身份、历史行为）决定当前会话统一采用何种模式。
- **意图级路由**：在一个请求内部，可能有多个子意图，分别路由到不同组件（如先查天气 API，再结合知识库回答）。

---

## 2. 路由判断的实现方式

实现路由判断通常有三种主流方法，可根据业务复杂度、准确率要求和成本来选择或组合。

### 2.1 基于规则（Rule-Based）
最轻量、可解释性强，适用于场景边界清晰、规则容易定义的业务。

- **关键词匹配**：若用户输入包含“公司内部”、“政策”、“2024年”等预定义关键词，则走 RAG。
- **领域白名单**：特定频道（如“客服”、“企业知识问答”）强制 RAG。
- **用户身份**：内部员工、VIP 用户走增强检索；普通用户走默认模型。
- **时间触发**：询问“最新”、“本周”等时效词且模型知识截止较早时，强制检索。

**优点**：简单、快速、无额外模型调用成本。  
**缺点**：规则无法覆盖所有情况，可能误判或漏判。

### 2.2 基于小模型分类器（Classifier）
训练一个轻量级的文本分类模型（如 BERT、FastText、逻辑回归）来判断请求是否需要检索。通常部署为独立的微服务或嵌入在 API 中。

- **训练数据**：标注一批用户请求，类别为“需要检索 / 不需要检索”。
- **特征**：原始文本、词频、语义向量等。
- **输出**：分类概率，设定阈值决定路由。

**优点**：准确率高于规则，能学习到复杂的语义模式。  
**缺点**：需要训练数据和维护成本，推理有一定延迟（但通常 <10ms）。

### 2.3 基于 LLM 的自省（LLM-Based Routing）
利用大语言模型自身的能力进行路由判断，通常通过 **function calling** 或 **结构化输出** 实现。这种方式将路由逻辑与生成逻辑统一，但会增加一次 LLM 调用。

- **方案 A：工具调用**  
  提示模型：你拥有工具 `retrieve_knowledge_base` 和 `chat_normally`，根据用户问题决定调用哪个。模型返回函数名及参数，后端根据函数调用执行对应链路。

- **方案 B：链式判断**  
  先让模型输出一个 JSON 字段 `need_retrieval: true/false`，然后再进行后续处理（可复用同一个 LLM 调用，通过 `logit_bias` 或流式输出提前解析）。

**优点**：最灵活，能理解复杂上下文，可与生成步骤共享模型调用。  
**缺点**：延迟高（多一次 LLM 往返，除非用流式合并），成本较高。

---

## 3. 路由判断在架构中的位置

路由判断通常位于 **API 网关或业务编排层**，在调用任何下游服务（向量数据库、LLM）之前执行。典型 FastAPI 实现如下：

```python
@app.post("/chat")
async def chat(request: ChatRequest):
    # 1. 路由判断
    route = router.decide(request.query, session_id=request.session_id)
    
    if route == "no_rag":
        # 直接调用 LLM 生成
        return await llm.generate(request.query)
    
    if route == "rag":
        # 检索 + 增强生成
        docs = await vector_db.search(request.query)
        context = format_docs(docs)
        return await llm.generate_with_context(request.query, context)
```

也可以将路由逻辑封装成一个独立服务，便于统一管理和 A/B 测试。

---

## 4. 路由判断的进阶策略

- **动态阈值**：根据系统负载、延迟要求动态调整路由策略（如高峰期强制走无检索链路）。
- **缓存路由结果**：对相同或相似的 query 缓存路由决策，减少重复计算。
- **多级路由**：先用规则快速过滤，再用模型对剩余请求精细判断。
- **可观测性**：记录路由决策、每条路径的耗时和效果，用于持续优化。

---

## 5. 总结

| 方法         | 复杂度 | 准确性 | 延迟 | 成本           | 适用场景                 |
| ------------ | ------ | ------ | ---- | -------------- | ------------------------ |
| 规则         | 低     | 中低   | 极低 | 零             | 场景明确、简单           |
| 小模型分类器 | 中     | 中高   | 低   | 低（推理成本） | 数据充足，需要较高准确率 |
| LLM 自省     | 高     | 高     | 高   | 高（额外调用） | 复杂意图、多工具协同     |

路由判断是 RAG 系统中一个关键的“智能开关”，它平衡了效果与效率。选择哪种实现方式，取决于你对准确性、延迟和成本的综合考量。在实际生产环境中，通常会从规则开始，随着数据积累逐步升级为模型路由，甚至结合多种策略形成鲁棒的路由模块。

这一步非常关键，因为它决定了后面要不要检索、检索什么、怎么检索。

# 三、离线建库链路：知识如何进入系统

------

## 1. 数据接入

知识源可能来自：

- PDF、Word、PPT、Excel
- HTML 页面、Wiki、FAQ
- 数据库记录
- 工单系统、CRM、客服历史
- API 数据
- 图片 OCR 后文本
- 表格、代码、日志

不同数据源不能直接统一处理，第一步通常是做**统一抽取层**，把它们转成标准化文档对象。

一个标准文档对象至少要有：

- `doc_id`
- `source`
- `title`
- `content`
- `created_at`
- `updated_at`
- `version`
- `permission_tag`
- `language`
- `business_type`

这是后续一切处理的基础。

------

## 2. 数据清洗

原始文档往往非常脏。清洗不是小事，它直接决定召回质量。

## 需要清理什么

### 结构噪声

- 页眉页脚
- 页码
- 水印
- 导航栏
- 面包屑
- 重复标题
- 模板化声明
- 版权信息
- 无意义空白

在文档数据清洗的语境中，**“面包屑”** 指的是**页面中用于显示当前页面位置层级关系的导航路径**，通常表现为一系列用分隔符（如 `>`、`/`）连接的链接或文本，例如：

```
首页 > 产品中心 > 智能手机 > 产品详情
```

在清洗文档（尤其是从网页抓取或 PDF 转换而来的文档）时，面包屑属于**冗余的 UI 元素**，与文档的主体内容无关。若不清理，它们可能会：

- **污染文本块**：被误当作正文内容切分进 chunk，干扰向量检索的语义。
- **引入噪音**：大量重复出现在不同页面的面包屑会导致相似度计算偏差。
- **浪费存储**：占用 embedding 和向量数据库的空间。

因此，在文档解析和预处理阶段，需要识别并移除这类导航栏、面包屑等**布局性文字**，确保最终进入知识库的是纯净的正文内容。

### 编码与格式噪声

- OCR 错字
- 乱码
- 异常换行
- 多余空格
- HTML 标签残留
- Markdown 格式碎片
- 表格被解析成断裂文本

### 内容噪声

- 重复段落
- 非正文附件描述
- 无效公告
- 过期内容
- 测试数据
- 草稿版本

## 清洗的目标

不是把文档“洗干净”这么简单，而是让知识变得：

- **可切片**
- **可理解**
- **可检索**
- **可更新**
- **可引用**

因此很多系统会同时保留两份文本：

### 原文文本

用于回显、引用、追溯

### 清洗后文本

用于 embedding、检索和生成

这是一个很常见也很重要的设计。

处理双栏 PDF（如学术论文、杂志、报纸）是文档抽取中的一个经典难题。双栏布局打破了自然的阅读顺序，如果直接按文本流提取，会导致左右两栏的内容交错混杂，严重影响后续切块与检索效果。下面从 **挑战 → 抽取方案 → 清洗策略 → 工具推荐** 四个维度给出系统性的解决方案。

---

## 1. 双栏 PDF 的抽取挑战

- **阅读顺序混乱**：PDF 底层文本流可能按物理位置顺序存储，从左栏第一行到右栏第一行，再到左栏第二行，导致提取出的文本是左右栏交错。
- **跨栏元素干扰**：图表、标题、脚注可能跨栏，需要正确归属。
- **段落识别困难**：双栏中的段落边界更难判断，因为每一栏都有自己的段落结构。
- **OCR 依赖**：部分 PDF 是扫描件，无文本层，必须先 OCR。

---

## 2. 抽取方案（从易到难）

### 2.1 基于布局解析（适用于原生文本型 PDF）
通过获取页面中每个文本块的坐标，然后根据 x 坐标将文本划分为左右两栏，再按 y 坐标排序输出。

**实现步骤**：
1. 使用 `pdfplumber`、`PyMuPDF`（fitz）或 `pypdf` 提取页面中所有文本块及其边界框（bbox）。
2. 统计页面上所有文本块的 x 坐标，通过聚类（如基于 x 中心点）确定左右两栏的 x 范围。
3. 将文本块分别归入左栏、右栏。
4. 每栏内部按 y 坐标（从上到下）排序，合并文本块形成段落。
5. 按左栏 → 右栏的顺序输出完整文本。

### 2.2 基于视觉模型（适用于复杂布局或扫描件）
使用深度学习模型（如 LayoutLMv3、YOLO、PaddleOCR 的 layout 分析）识别页面中的栏、标题、图表等区域，然后按阅读顺序重组。

- **PaddleOCR** 提供了 `PP-Structure` 模块，可以识别文档布局并还原阅读顺序。
- **DocLayout-YOLO** 等模型可检测文本块并预测其布局角色。

**流程**：
1. 将页面转为图像（如果 PDF 无文本层，先 OCR）。
2. 使用布局检测模型识别出“栏”区域。
3. 在每个栏内部进行文字识别（OCR）并排序。
4. 按左→右顺序输出。

这种方式准确度高，能处理复杂布局和扫描件，但需要额外模型推理资源。

### 2.3 基于开源工具链
一些成熟工具已经封装了双栏处理逻辑：
- **Camelot**：主要用于表格抽取，但可以结合坐标做布局分割。
- **PDFPlumber** 的 `page.extract_text()` 本身可以保留布局信息，但双栏仍需自定义排序。
- **Marker**（一种高效 PDF 转换工具）内置了布局分析和栏检测，可直接输出干净的 Markdown。

---

## 3. 清洗策略（抽取后的后处理）

即使正确分栏，抽取出的文本仍可能包含噪声，需要进一步清洗：

1. **段落合并**  
   同一栏内相邻文本块可能被拆成多行，需要根据字体、间距、缩进等特征合并成完整段落。
   - 简单方法：若两行 y 坐标差小于某阈值且上一行不以句号结束，则视为同一段落。

2. **跨栏标题处理**  
   标题有时居中跨栏，需单独提取并保留其上下文。可通过检测文本的字体大小、居中位置来判断。

3. **页眉页脚移除**  
   利用坐标（通常在页面顶部/底部）或正则匹配（如包含页码、文档标题）剔除。

4. **图表/脚注标记**  
   如果检测到图表区域，可以用 `[图表]` 或保留原始占位符，避免文本断层。

5. **去除冗余空白与连字符**  
   清理行尾的连字符，合并断开的单词，压缩多余空格。

---

## 4. 推荐工具与库

| 工具               | 适用场景                 | 特点                                                   |
| ------------------ | ------------------------ | ------------------------------------------------------ |
| **PyMuPDF (fitz)** | 文本型 PDF，精细控制坐标 | 速度快，可获取精确 bbox，适合自定义分栏逻辑            |
| **pdfplumber**     | 文本型 PDF，需要易用 API | 提供 `page.extract_words()` 并保留坐标，社区案例多     |
| **PaddleOCR**      | 扫描件、复杂排版         | 内置布局分析、表格识别、阅读顺序还原，支持中文         |
| **Marker**         | 学术论文等复杂 PDF       | 基于深度学习的端到端转换，输出 Markdown，保留标题/列表 |
| **LayoutLMv3**     | 需要高精度布局理解       | 适合构建自定义抽取流程                                 |

---

## 6. 总结

双栏 PDF 的抽取与清洗核心在于**恢复正确的阅读顺序**。可以通过：

- **坐标分析**：利用文本块 bbox 进行分栏和排序。
- **布局模型**：使用深度学习识别栏结构，尤其适合扫描件或复杂排版。
- **后处理**：合并段落、移除页眉页脚等噪音。

最终目标是将双栏文档转换为线性的、干净的文本，以便后续的切块、Embedding 和检索。根据你的文档类型（原生 PDF vs 扫描件）和业务对准确率的要求，可以选择不同的技术路线。

------

## 3. 文档切片

切片是 RAG 里最容易被说浅、但最影响效果的部分之一。

因为向量库检索的基本单元不是“整篇文档”，而是**chunk**。

## 为什么不能整篇入库

因为整篇文档有几个问题：

- embedding 太长，被压缩后语义混杂
- 检索粒度过粗
- topk 命中的内容里无关文本太多
- prompt 拼接后浪费上下文窗口
- 重排成本高

所以必须切片。

------

## 4. 如何切片

切片不是固定按 500 字砍一刀。真实系统里通常有多种策略。

## 4.1 固定窗口切片

例如每 300～500 tokens 切一片，overlap 50～100 tokens。

优点：

- 实现简单
- 稳定
- 适合普通纯文本

缺点：

- 会打断语义边界
- 上下段关系可能断裂

## 4.2 结构感知切片

按照文档结构切：

- 标题
- 小节
- 段落
- 列表
- 表格
- 代码块
- FAQ 问答对

这通常优于纯固定切片。

例如：

- 一个 FAQ 的问答对应该作为一个 chunk
- 一个表格应该整体保留，而不是拆散
- 一个函数说明和参数说明最好保留在一起
- 一个制度条款的编号和正文不能分开

## 4.3 语义切片

通过句向量相似度、段落边界、主题变化来切。也就是在语义突变处断开，而不是机械按长度断开。

适合：

- 长报告
- 长说明文档
- 主题分段明显的知识文档

## 4.4 父子切片

这是企业 RAG 很常见的设计。

### 子块

短 chunk，用于高精度召回

### 父块

更大 chunk，用于补充上下文

检索时先召回子块，再把对应父块取出来供生成使用。

这正好对应你提到的问题：

> 如果真正能回答问题的答案不在当前检索段，而在上一个段落怎么办？

这类问题最有效的办法之一就是：

- 检索粒度用小块
- 生成上下文用父块或邻接块扩展

也就是**检索细粒度，喂给模型时适当扩窗**。

## 4.5 邻接扩展

如果某个 chunk 被召回，可以把它的：

- 前 1 段
- 后 1 段
- 同标题下兄弟段
- 所属小节摘要

一起带出来。

因为很多知识是跨段表达的，单段不完整。

在 RAG 系统中，文档切分（chunking）策略直接决定了检索粒度和召回质量。面对固定窗口切片、结构感知切片、语义切片、父子切片这四种主流策略，没有绝对的“最佳”，而是需要根据文档类型、业务需求、模型能力进行权衡与组合。

下面我会从定义、优缺点、适用场景出发，给出真实业务中的选型建议。

---

## 1. 四种切分策略对比

| 策略             | 原理                                                         | 优点                                     | 缺点                                                 | 典型场景                                             |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| **固定窗口切片** | 按固定 token 数或字符数切割，可带重叠                        | 简单、计算快、实现成本低                 | 破坏语义完整性，可能切断句子/段落；难以保留上下文    | 初期原型、内容长度均匀的纯文本（如日志）             |
| **结构感知切片** | 利用文档结构（标题、段落、列表、表格）作为边界               | 保留语义单元，增强检索精度；便于定位来源 | 对非结构化文档（如纯文本对话）无效；依赖文档格式规范 | 技术文档、Markdown、HTML、学术论文（结构清晰）       |
| **语义切片**     | 基于向量相似度或模型预测，在语义边界处切割                   | 保证每个 chunk 内部语义高度内聚          | 计算开销大；需额外模型（如嵌入模型），可能过细或过粗 | 无结构的长文本、法律文书、小说                       |
| **父子切片**     | 将大块（父）切分成小块（子），检索时返回小块，但关联父块上下文 | 兼顾细粒度匹配与完整上下文               | 存储成本高，需维护父子关系；实现复杂                 | 需要精确定位又需保留全局背景的场景（如问答结合摘要） |

---

## 2. 真实业务中如何衡量重要性？

“重要性”取决于你的业务核心指标：**召回率、精准率、检索延迟、存储成本、维护复杂度**。

### 2.1 文档类型是首要决定因素
- **结构规范的技术文档（API 文档、用户手册、Markdown）**  
  **首选：结构感知切片**。它天然保留了章节、标题、列表的完整性，检索结果能直接指向文档的具体位置，用户可溯源。  
  辅助：对过长的章节可再采用父子切片（父为章节，子为段落），避免因 chunk 过长浪费上下文。

- **非结构化的长文本（小说、论坛帖子、会议记录）**  
  **首选：语义切片**。它能确保每个 chunk 是语义连贯的片段，减少噪音。  
  若文本极长且无明显语义边界，可先用固定窗口 + 重叠作为兜底。

- **混合型文档（含表格、代码块、流程图）**  
  需要组合策略：结构感知识别出表格、代码块等特殊元素，将其单独保留不切分；其余文本再用语义切片或固定窗口处理。

### 2.2 检索场景决定粒度
- **事实性问答（“某产品的发布时间”）**  
  需要高精度，适合较短的 chunk（如固定窗口 200~300 token），避免冗余信息干扰。
- **综述/分析类查询（“总结某技术的优缺点”）**  
  需要完整上下文，适合结构感知切片保留章节信息，或父子切片返回父块。

### 2.3 成本与资源
- **固定窗口**：计算成本最低，适合大规模快速实验。
- **语义切片**：需要调用 embedding 模型，对千亿级文档成本较高，可考虑仅对难处理的无结构文档使用。
- **父子切片**：存储空间翻倍（同时存父和子），检索时需两次查询或关联逻辑，适合对召回质量要求极高的场景。

---

## 3. 推荐组合策略（生产环境常用）

在实际业务中，往往采用“多策略混合”以获得最佳效果：

1. **预处理**：先用结构感知将文档按标题、段落切分，得到语义单元（如章节）。
2. **二次切分**：对过大的语义单元（超过 512 token）再进行固定窗口或语义切片，保证每个 chunk 大小可控。
3. **父子关联**：保留父块（章节）的完整内容，子块（段落）用于检索。检索时返回子块，同时将父块作为上下文提供给 LLM，实现“细粒度匹配 + 完整背景”。
4. **特殊元素保留**：对表格、代码、公式等，单独切出并标记类型，检索时可针对性召回。

这种组合既利用了结构感知的边界准确性，又通过父子切片解决了上下文缺失问题，同时控制 chunk 大小适应 LLM 上下文窗口。

---

## 4. 如何验证选型效果？

在确定策略后，必须通过评测来迭代：
- **建立问答测试集**：从文档中抽取真实问题与答案片段。
- **对比不同策略的召回率、命中率**：看检索结果是否包含答案所在的 chunk。
- **端到端评估**：将检索结果输入 LLM，人工或自动评估最终答案质量。

根据评测结果调整：
- 若召回率低 → 增加 chunk 重叠、缩小 chunk 大小、尝试语义切片。
- 若答案不完整 → 考虑父子切片，返回更大上下文。
- 若干扰信息多 → 提高结构感知的粒度，避免跨主题合并。

---

## 5. 总结

| 策略         | 重要性                     | 典型地位                         |
| ------------ | -------------------------- | -------------------------------- |
| 固定窗口切片 | 基础保底，简单高效         | 常用于兜底，或与其他策略组合     |
| 结构感知切片 | 高（对结构化文档）         | 优先选择，能极大提升检索体验     |
| 语义切片     | 中高（对无结构文本）       | 作为结构感知的补充，提升内聚性   |
| 父子切片     | 高（对需保留上下文的场景） | 高级优化，显著增强长文档问答能力 |

**真实业务中，没有单一万能策略，推荐采用“结构感知为主，语义/父子为辅，固定窗口兜底”的组合方式**，并通过评测持续调优。这样能在保证检索质量的同时，控制实现复杂度和成本。

## 5. chunk 里要不要 metadata

一定要，而且非常重要。

很多初学者只存文本和向量，这是不够的。

## metadata 至少包括什么

### 追溯信息

- `doc_id`
- `chunk_id`
- `source_url` 或文件路径
- `page_no`
- `section_title`
- `paragraph_idx`

### 语义信息

- `title`
- `keywords`
- `entity`
- `topic`
- `summary`

### 治理信息

- `version`
- `updated_at`
- `is_deleted`
- `valid_from`
- `valid_to`

### 权限信息

- `tenant_id`
- `department`
- `visibility`
- `access_level`

### 检索辅助信息

- `language`
- `doc_type`
- `business_domain`
- `quality_score`

metadata 的作用至少有五个：

1. **过滤**，比如只搜某个部门可见文档
2. **排序加权**，比如优先最新版本
3. **上下文扩展**，找到父块、前后块
4. **引用展示**，返回出处
5. **增量更新**，定位旧版本并替换

所以 metadata 不是可选项，而是核心字段。

在 RAG 应用中实现权限管理，核心思路是：**在检索阶段，根据用户权限动态过滤知识库中的文档或知识块**。下面从权限模型设计、元数据标签、检索过滤、后端实现几个方面给出完整方案。

---

## 1. 权限模型

最常用的是 **基于角色的访问控制（RBAC）**：

- **角色**：部门成员、部门主管、BOSS 等
- **资源**：知识库中的文档或知识块
- **权限**：读（检索）、写（更新知识库）等

根据你的场景：
- 部门成员只能检索本部门相关的知识
- BOSS 可以检索所有部门的知识

也可以扩展为 **基于属性的访问控制（ABAC）**，通过动态属性（如部门、级别、时间）实现更细粒度的控制。

---

## 2. 元数据设计

在知识库中，为每个文档或知识块添加权限相关的元数据字段。常见字段：

| 字段名         | 类型          | 说明                                             |
| -------------- | ------------- | ------------------------------------------------ |
| `department`   | string / list | 允许访问的部门标识，如 `["tech", "sales"]`       |
| `access_level` | int           | 访问级别，如 1（公开）、2（部门内）、3（仅BOSS） |
| `owner`        | string        | 创建者或所有者                                   |

**示例（存入向量数据库的 payload）**：
```json
{
  "text": "API 认证流程说明...",
  "vector": [...],
  "department": "tech",
  "access_level": 2,
  "owner": "zhang.san"
}
```

若文档需要多个部门共享，`department` 可设计为数组。

---

## 3. 检索时的权限过滤

利用向量数据库的**元数据过滤**功能，在相似性搜索时附加过滤条件。主流的向量数据库（Milvus、Qdrant、Pinecone、Elasticsearch）都支持这种机制。

### 3.1 场景一：部门成员查询
假设用户 `user1` 属于 `tech` 部门，他的检索请求需要带上过滤条件：  
`department == "tech"` 或 `access_level <= 2` 等。

**Qdrant 示例**：
```python
from qdrant_client import QdrantClient
from qdrant_client.http.models import Filter, FieldCondition, MatchValue

client = QdrantClient(host="localhost", port=6333)

def search_with_user(query_vector, user_department, top_k=5):
    results = client.search(
        collection_name="knowledge_base",
        query_vector=query_vector,
        limit=top_k,
        query_filter=Filter(
            must=[
                FieldCondition(
                    key="department",
                    match=MatchValue(value=user_department)
                )
            ]
        )
    )
    return results
```

### 3.2 场景二：BOSS 查询
BOSS 拥有最高权限，可以不添加过滤条件（或仅添加公开数据条件）：
```python
def search_for_boss(query_vector, top_k=5):
    results = client.search(
        collection_name="knowledge_base",
        query_vector=query_vector,
        limit=top_k,
        query_filter=None   # 无过滤，检索全部
    )
    return results
```

### 3.3 多部门共享文档
若文档属于多个部门，可将 `department` 字段设为数组，使用 `match_any` 条件：
```python
FieldCondition(
    key="department",
    match=MatchAny(any=user_departments)  # user_departments 是列表
)
```

---

## 4. 后端集成（以 FastAPI 为例）

1. **用户认证**：从 JWT 或 Session 中获取用户角色和所属部门。
2. **动态构建过滤条件**：根据角色生成对应的 Filter。
3. **调用检索服务**：将过滤条件传入向量数据库。

```python
from fastapi import Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

security = HTTPBearer()

@app.post("/search")
async def search(
    query: str,
    credentials: HTTPAuthorizationCredentials = Depends(security)
):
    # 1. 解析 token 获取用户信息
    token = credentials.credentials
    user = decode_token(token)   # 自定义函数
    if not user:
        raise HTTPException(401, "Invalid token")
    
    # 2. 根据用户角色生成过滤条件
    if user["role"] == "BOSS":
        filter_condition = None
    elif user["role"] == "MEMBER":
        filter_condition = {
            "department": user["department"]
        }
    else:
        raise HTTPException(403, "Insufficient permission")
    
    # 3. 向量化 query
    query_vector = embed_model.encode(query)
    
    # 4. 执行检索
    results = vector_db.search(
        collection="knowledge_base",
        vector=query_vector,
        filter=filter_condition,
        top_k=5
    )
    
    return {"results": results}
```

---

## 5. 性能与存储优化

- **索引过滤字段**：在向量数据库中为 `department`、`access_level` 等字段建立倒排索引，加快过滤速度。
- **分区策略**：可按部门对集合进行分区（如 Milvus 的分区），检索时只扫描相关分区，进一步提升性能。
- **缓存权限决策**：对于高频用户，可将权限结果缓存，避免重复解析 token 和构建 filter。

---

## 6. 更细粒度的权限控制

如果同一文档的不同段落权限不同（例如文档前半部分公开，后半部分机密），可在**块级别**打标签。但这样会显著增加元数据维护成本。一般建议在文档级或块级统一处理。

对于 BOSS 能查所有知识，只需在过滤逻辑中识别 BOSS 角色，不添加限制条件即可。

---

## 7. 总结

RAG 中的权限管理主要依靠 **元数据 + 检索过滤** 实现：

- **设计权限模型**（RBAC/ABAC）
- **为每个知识块打上权限标签**（如 department）
- **在向量检索时动态添加过滤条件**
- **后端根据用户角色构造过滤条件**

这种方案实现简单，与向量数据库的过滤能力天然契合，既能保证数据安全，又不影响检索性能。

## 6. embedding 怎么做

文档切成 chunk 之后，要把每个 chunk 编成向量。

## embedding 的输入是什么

通常不是只把正文直接编码，而会做一定包装，例如：

- 标题 + 正文
- 小节标题 + 段落正文
- FAQ 的问题 + 答案
- 表格标题 + 表头 + 行内容摘要

原因是：很多 chunk 脱离标题后语义不完整。

比如正文写的是“其退款时限为 7 个工作日”，如果不带标题，embedding 很难知道这是“退款政策”。

在离线构建知识库（即“入库”阶段）时，**被 Embedding 模型编码的信息主要是文本块（chunk）的核心内容**，但为了提升检索质量，有时会额外拼接一些上下文信息。具体来说，输入给 Embedding 模型的文本通常包括以下几类：

---

## 1. 文本块的主体内容（必需）

这是最基本的输入，即文档切分后得到的一个个语义单元（chunk）的**纯文本内容**。例如：

- 一个段落
- 一个表格的文本化描述
- 一段代码及其注释
- 一个列表项

Embedding 模型会将这段文本映射成一个高维向量，用于后续的相似度检索。

---

## 2. 可选的上下文增强信息（强烈推荐）

为了让向量能更好地代表该 chunk 在文档中的完整语义，常常会在文本块前或后拼接一些**结构性上下文**。这些信息本身不会作为独立的元数据存储，而是被“融入”到向量中。

常见的增强内容包括：

- **标题/章节路径**  
  例如：`"第3章 权限管理 > 3.2 RBAC模型\n\nRBAC（基于角色的访问控制）是一种..."`  
  这样向量就能隐含该 chunk 所处的主题层级，避免出现“孤立的语义”。

- **文档来源/类型**  
  如 `"[产品手册] 配置说明..."`，可以帮助检索时区分不同来源的相似内容。

- **摘要或关键句**  
  如果 chunk 过长，可以将该 chunk 的自动摘要或第一句作为前缀，增强主题代表性。

- **自定义标签**  
  如 `"[部门:技术] API认证流程..."`，但这类信息如果与元数据重复，一般建议放在元数据中而非文本中，以免增加向量噪声。

> **注意**：拼接的内容应该与 chunk 本身密切相关，且不宜过长，否则会稀释核心内容的权重。

---

## 3. 通常不被编码的信息

- **纯元数据**：如文档 ID、创建时间、权限标签、文件路径等，这些信息**不会输入给 Embedding 模型**，而是作为结构化字段与向量一并存储在向量数据库中，用于检索时的过滤或排序。
- **页眉页脚、水印、导航栏**：这些在文档清洗时已被移除，不进入知识库。
- **过于冗长的上下文**：如果整个文档都拼接到每个 chunk 中，会导致向量差异变小，检索精度下降。

---

## 4. 设计考量

- **编码一致性**：在线检索时，用户查询也会用同样的 Embedding 模型编码，因此两者输入格式应保持一致（例如都包含相同的上下文前缀）。
- **长度限制**：Embedding 模型通常有最大输入长度（如 512 token）。拼接后的文本不能超限，否则会被截断，丢失重要信息。
- **业务语义**：根据业务场景决定是否拼接。例如，对于多部门共享的知识库，可以在文本中加入“部门标识”来增强区分度；对于纯问答，则可能不需要拼接。

---

## 5. 总结

| 信息类型                   | 是否被编码 | 说明                                 |
| -------------------------- | ---------- | ------------------------------------ |
| 文本块正文                 | ✅ 是       | 核心内容，必须编码                   |
| 标题/章节路径              | ✅ 强烈推荐 | 增强语义完整性，提升检索精准度       |
| 摘要/关键句                | ✅ 可选     | 辅助长文本的表示                     |
| 文档类型/标签（文本形式）  | ✅ 可选     | 若需融入向量，可拼接；否则作为元数据 |
| 元数据（ID、权限、时间等） | ❌ 否       | 单独存储，用于检索过滤               |
| 页面噪声（页眉页脚等）     | ❌ 否       | 在清洗阶段移除                       |

在实际工程中，通常会采用**“正文 + 标题路径”**的拼接方式作为标准做法，既能保证每个 chunk 的语义独立，又能携带文档结构信息，从而在检索时获得更好的召回效果。

## embedding 模型怎么选

要看场景：

### 通用问答

通用中文/中英 embedding 模型

### 垂直领域

最好做领域适配，否则术语表达会偏

### 长文档

要考虑最大输入长度和长文本语义保真

### 高吞吐场景

还要考虑编码速度和成本

实际中往往不是只做一套向量，有时会同时维护：

- 文本 dense embedding
- 标题 embedding
- 关键词 sparse 表征
- 文档摘要 embedding

用于混合召回。

------

## 7. 数据如何存储

通常至少有三层存储。

## 7.1 对象存储 / 原文存储

存原始文件和原文内容。

## 7.2 结构化存储

关系库或文档库，存：

- 文档元信息
- chunk 信息
- 版本信息
- 权限信息
- 更新状态

## 7.3 索引存储

主要是检索引擎：

- 稀疏索引：BM25 / 倒排索引
- 稠密索引：向量库
- 混合索引：两者并存

这是标准架构。不要把所有信息都塞进向量库。

------

# 四、在线问答链路：用户问题如何处理

这部分才是真正决定“用户体感”的核心。

------

## 1. 用户输入后第一步：意图识别

系统不应该一上来就 embedding 用户问题然后 topk 检索。

应先做 query understanding。

## 要识别什么

### 1. 这是不是知识问答

还是闲聊、写作、任务执行、投诉、反馈等

### 2. 是否需要检索

有些问题直接让 LLM 回答即可

### 3. 是不是域外问题

和知识库完全不相关

### 4. 是不是多轮追问

比如“那他什么时候上任的？”
这里的“他”显然依赖上文

### 5. 问题是否歧义严重

例如：

- “这个流程怎么办”
- “它能退吗”
- “他是谁”
- “那个规定现在还有效吗”

没有消歧直接检索，通常会错。

------

## 2. 歧义、指代不明，怎么办

这是 RAG 很真实的问题。

## 常见问题类型

### 指代消解

- 他、它、这个、那个、前者、后者

### 省略

- “那退款呢？”
- “北京的呢？”
- “今年的版本呢？”

### 多义词

- 苹果是公司还是水果
- Java 是语言还是岛

### 范围不清

- “最近”
- “最新政策”
- “可以报销吗”

## 处理方式

### 2.1 对话上下文重写

先把当前问题和历史对话结合，重写成一个完整 query。

例如：

- 原问题：“那他什么时候上任的？”
- 重写后：“XX 公司现任 CEO 是谁，他是什么时候上任的？”

这一步很常见，通常叫：

- query rewrite
- standalone question generation

### 2.2 歧义检测

如果系统发现关键信息缺失，就不要盲搜，而是：

- 先澄清
- 或者给出候选理解
- 或者按多个候选并行检索再判别

### 2.3 实体识别与槽位抽取

把 query 中的公司名、产品名、时间范围、地区等结构化提取出来，用于过滤和排序。

| 策略         | 适用场景                         | 延迟                  | 效果 |
| :----------- | :------------------------------- | :-------------------- | :--- |
| 规则指代消解 | 指代类型有限、对话结构简单       | 极低                  | 中等 |
| 模型查询改写 | 对话复杂、对效果要求高           | 中等（额外 LLM 调用） | 高   |
| 多轮检索融合 | 无需精确指代消解，仅需上下文补充 | 低                    | 中高 |
| 主动澄清     | 歧义严重、容错率低的业务         | 增加交互轮次          | 极高 |

------

## 3. 如何实现长上下文对话

长对话不是把全部历史原样塞给模型。

真实系统通常分三层记忆。

## 3.1 短期窗口记忆

最近几轮对话，直接拼接。

## 3.2 对话摘要记忆

把较早历史压缩成摘要，保留关键事实和用户意图。

## 3.3 会话状态记忆

把关键槽位结构化保存，例如：

- 当前讨论主体：某公司
- 当前主题：退款政策
- 当前版本：2025 年制度
- 当前用户目标：申请报销

这样下一轮遇到“那流程呢”“材料有哪些”时，可以恢复上下文。

对于检索来说，最重要的是：

**不是把整段历史扔去做 embedding，而是抽取出当前轮检索真正需要的语义状态。**

在 RAG 系统处理长对话时，仅仅维护对话历史是不够的，需要构建**三层记忆架构**来分别处理**短期会话上下文、长期用户偏好、以及当前任务状态**。这样才能在多轮交互中保持连贯性、个性化，并避免上下文窗口爆炸。

下面从**三层记忆的定义、存储方案、维护策略**三个方面详细说明。

---

## 1. 三层记忆的定义与职责

| 记忆层       | 核心职责                                     | 典型内容                                         | 生命周期                       |
| ------------ | -------------------------------------------- | ------------------------------------------------ | ------------------------------ |
| **短期记忆** | 维护当前会话的上下文，支持指代消解与连贯对话 | 当前会话的问答对、系统回复、未完成的意图         | 单次会话（从开始到结束/超时）  |
| **工作记忆** | 存储当前任务的关键信息，用于流程推进         | 用户确认的订单信息、临时选择的参数、任务进度     | 单个任务周期（如一次订票流程） |
| **长期记忆** | 跨会话的用户画像、偏好、历史事实             | 用户身份、部门、常用设备、历史咨询记录、个人偏好 | 持久化（跨天、跨会话）         |

---

## 2. 各层的实现方案

### 2.1 短期记忆（Short-term Memory）

**存储形式**：通常以**对话历史列表**的形式存储，按时间顺序记录本轮会话中的所有交互。

**技术选型**：
- **Redis**：以 `session_id` 为 key，存储 JSON 格式的对话列表，设置 TTL（如 30 分钟）。
- **内存**：对于单机部署，可直接用 Python dict 缓存（需注意服务重启会丢失）。

**维护策略**：
- 只保留最近 N 轮（如 10 轮），避免上下文过长。
- 定期压缩：将早期对话进行摘要（用 LLM 生成简短总结）后保留，而不是简单丢弃。

**在 RAG 中的使用**：
- 用于**查询改写**（指代消解）和历史相关检索。
- 在 Prompt 中作为对话上下文提供给 LLM。

### 2.2 工作记忆（Working Memory）

**存储形式**：以**键值对**形式存储当前任务的关键字段，通常是结构化数据。

**技术选型**：
- **Redis Hash**：`session_id:task` → `{"intent": "book_ticket", "date": "2025-01-15", "destination": "北京", ...}`。
- **数据库临时表**：对于复杂流程，可存入 MySQL 临时表，关联 session_id。

**维护策略**：
- 任务开始时创建，任务完成后清除（或标记完成）。
- 每次用户输入时，通过意图识别更新工作记忆（如提取实体、确认值）。
- 可设置较短 TTL（如 2 小时），防止僵尸任务占用资源。

**在 RAG 中的使用**：
- 将工作记忆中的关键信息拼接到检索查询中（例如检索“北京的天气”时，将用户之前确认的日期自动带入）。
- 在 Prompt 中作为任务上下文，指导 LLM 的下一步行动。

### 2.3 长期记忆（Long-term Memory）

**存储形式**：用户画像、历史行为向量、知识图谱事实等，需要持久化存储。

**技术选型**：
- **关系型数据库**（MySQL/PostgreSQL）：存储用户属性（部门、角色、偏好设置）。
- **向量数据库**（Milvus/Qdrant）：存储用户历史交互的 embedding，用于检索类似场景下的偏好。
- **图数据库**（Neo4j）：存储用户与实体之间的关系（如“用户 A 经常咨询产品 X”）。

**维护策略**：
- 异步更新：在每次会话结束后，异步提取关键信息更新长期记忆（可调用 LLM 做信息抽取）。
- 定期聚合：按天/周合并用户行为，生成用户摘要。
- 隐私保护：需遵循数据合规要求，提供用户遗忘/删除接口。

**在 RAG 中的使用**：
- 在检索时，将长期记忆作为过滤条件（如“只检索该用户部门的知识库”）。
- 在 Prompt 中注入用户画像，让回复更个性化（如“根据您之前的偏好，推荐...”）。

---

## 3. 三层记忆的协同工作流程

以一个长对话场景为例：用户想订机票，过程中切换了话题，然后又回来继续。

```
1. 用户：帮我订一张后天去北京的机票
   - 短期记忆：记录本轮对话
   - 工作记忆：创建任务，记录 {intent: book_flight, date: 2025-01-17, destination: 北京}
   - 长期记忆：读取用户常坐的航空公司（从数据库获取）

2. 用户：等一下，先帮我查一下北京的天气
   - 短期记忆：记录新对话
   - 工作记忆：暂存订票任务（不删除），同时启动天气查询子任务
   - 检索时：将工作记忆中的 "北京" 和短期记忆中的上下文结合，准确检索天气

3. 系统：北京后天晴，5-15度...
   - 工作记忆：天气子任务完成，回到订票主任务

4. 用户：那还是订那天的票吧，经济舱
   - 短期记忆：记录新对话
   - 工作记忆：更新订票任务 {cabin: economy}
   - 检索时：需要检索航班信息，系统会将工作记忆中的所有字段拼接到查询中
```

---

## 4. 工程实现架构

```
┌─────────────────────────────────────────────────────────┐
│                     FastAPI 服务                        │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐    │
│  │ 短期记忆    │  │ 工作记忆    │  │ 长期记忆    │    │
│  │ (Redis)     │  │ (Redis)     │  │ (MySQL +    │    │
│  │ TTL:30min   │  │ TTL:2h      │  │ 向量库)     │    │
│  └─────────────┘  └─────────────┘  └─────────────┘    │
│         ▲                ▲                ▲            │
│         └────────────────┼────────────────┘            │
│                          │                             │
│                   ┌──────┴──────┐                      │
│                   │ 记忆管理器  │                      │
│                   │ (编排层)    │                      │
│                   └─────────────┘                      │
└─────────────────────────────────────────────────────────┘
```

**记忆管理器**的核心接口：
- `get_context(session_id)`：返回当前完整的对话上下文（短期+工作+长期相关记忆），用于 Prompt 构建。
- `update_memory(session_id, user_input, system_response)`：根据新交互更新三层记忆。
- `extract_long_term(session_id)`：会话结束后异步提取长期记忆。

---

## 5. 记忆压缩与裁剪

为了控制上下文长度和成本，需要定期压缩：

- **短期记忆压缩**：当超过 K 轮时，将最早的 N 轮对话用 LLM 生成摘要，替换为 `[摘要：用户询问了订票流程]` 形式。
- **工作记忆清理**：任务完成或长时间无交互后，自动清理。
- **长期记忆聚合**：定期将多条相似记录合并（如“用户多次查询 iPhone 价格”聚合成“偏好：iPhone 系列”）。

---

## 6. 总结

三层记忆架构是 RAG 系统处理长对话的成熟模式：

| 记忆层   | 存储介质       | 生命周期 | 核心作用                 |
| -------- | -------------- | -------- | ------------------------ |
| 短期记忆 | Redis（列表）  | 会话级   | 维持对话连贯性、指代消解 |
| 工作记忆 | Redis（Hash）  | 任务级   | 跟踪多步流程、临时参数   |
| 长期记忆 | MySQL + 向量库 | 持久化   | 个性化、跨会话知识       |

通过分层管理，既保证了对话的实时性，又能在长时间跨度内提供个性化体验，同时避免了单一上下文窗口的无限膨胀。在 FastAPI 中，可以通过依赖注入（Depends）将记忆管理器注入到每个请求中，实现统一维护。

# 五、检索器怎么选，如何检索

------

## 1. 检索器选什么

最常见的不是“只选一个”，而是**混合检索**。

## 1.1 稀疏检索

典型是 BM25 或倒排检索。

优点：

- 对关键词、术语、编号、专有名词敏感
- 对精确匹配很强
- 可解释性好

缺点：

- 同义改写、语义泛化能力弱

## 1.2 稠密检索

即 embedding 检索。

优点：

- 语义召回能力强
- 适合同义表达、自然语言问题

缺点：

- 容易漏掉精确关键词
- 编号、版本号、专业缩写有时不稳定

## 1.3 混合检索

现实里经常最好用。

做法一般是：

- BM25 召回一批
- 向量召回一批
- 合并候选
- 再做 rerank

这样能同时兼顾：

- 关键词命中
- 语义相似
- 鲁棒性

在RAG系统真实应用中，检索器通常分为**稀疏检索器**和**稠密检索器**两大类。它们各自有不同的代表模型，且在工业实践中常常组合使用以获得最佳效果。

---

## 一、稀疏检索器

稀疏检索器基于**关键词匹配**，将查询和文档表示为高维稀疏向量（大部分维度为0），擅长精确匹配和传统搜索场景。

### 1. BM25（最经典的基线模型）
**定位**：传统信息检索的标杆，RAG系统中作为基线或兜底方案。

**核心原理**：基于词频（TF）、逆文档频率（IDF）和文档长度归一化的统计公式计算相关性得分。虽然不涉及深度学习，但在关键词明确的查询上表现稳定，且计算速度快、可解释性强。

**使用场景**：作为混合检索的稀疏路组件，或处理包含专业术语、代码、ID等需要精确匹配的查询。

### 2. SPLADE（学习型稀疏检索器）
**定位**：BM25的深度学习升级版，用Transformer学出来的稀疏向量。

**核心原理**：SPLADE（SParse Lexical AnD Expansion）利用BERT等Transformer模型，为每个查询和文档生成词汇表上的稀疏权重分布。它不仅考虑文档中出现的词，还能通过模型学习"扩展"出语义相关但未出现的词，并赋予权重。

**特点**：
- 比BM25更强的语义理解能力（能理解同义词）
- 保留稀疏向量的高效存储和检索优势
- 可解释性优于稠密向量

**使用场景**：需要兼顾关键词匹配和语义理解的场景，作为混合检索中的稀疏路组件。

### 3. BM25 vs SPLADE 对比

| 维度       | BM25                   | SPLADE                   |
| ---------- | ---------------------- | ------------------------ |
| 技术基础   | 统计公式               | Transformer + 对比学习   |
| 语义扩展   | 不支持                 | 支持（自动扩展相关词）   |
| 计算复杂度 | 极低                   | 中等（需要模型推理）     |
| 可解释性   | 强（词频/文档频率）    | 中（权重可追溯）         |
| 适用场景   | 基线、兜底、关键词查询 | 需要语义理解的关键词场景 |


## 二、稠密检索器

稠密检索器基于**语义匹配**，将查询和文档映射到低维稠密向量空间，通过向量相似度（如余弦相似度、内积）计算相关性。核心优势是能理解同义词、上下文和复杂语义。

### 1. Bi-Encoder（双编码器架构）
**定位**：最主流的稠密检索架构。

**核心原理**：用一个共享权重的编码器分别对查询和文档进行编码，生成各自的向量，然后计算相似度。文档向量可以**离线预计算**并存入向量数据库，查询时只需编码query并做近似最近邻（ANN）搜索，因此**扩展性强、检索速度快**。

**代表性模型**：
- **BGE系列**（BAAI General Embedding）：中英文通用，如`bge-large-en-v1.5`、`bge-large-zh-v1.5`，在MTEB榜单上表现优异
- **text-embedding-ada-002**（OpenAI）：闭源API，8K上下文窗口，通用性强
- **E5系列**（微软）：基于对比学习训练的通用embedding模型
- **Sentence-BERT**：经典的句子向量模型

### 2. ColBERT（延迟交互架构）
**定位**：平衡Bi-Encoder和Cross-Encoder的中间方案。

**核心原理**：不为整个文档生成单一向量，而为**每个token生成一个向量**，查询时通过"延迟交互"（MaxSim操作）计算query token与doc token之间的最大相似度并求和。这种设计保留了token级别的语义信息，精度比Bi-Encoder高，又比Cross-Encoder更容易扩展。

**特点**：
- 细粒度匹配，对长文档和复杂查询效果好
- 索引体积大（每个token一个向量），内存占用高
- 适合对精度要求高且基础设施充足的场景

### 3. BGE-M3（混合能力模型）
**定位**：支持稠密、稀疏、多向量三种表示的统一模型。

**核心原理**：BAAI（智源研究院）推出的BGE-M3可以同时生成稠密向量（语义匹配）、稀疏向量（关键词匹配）和多向量（token级细粒度匹配），一套模型覆盖多种检索需求。

**特点**：
- 支持100+种语言
- 可根据场景灵活选择表示方式
- 适合需要多路召回但不想维护多个模型的场景

### 4. Word2Vec / GloVe（静态词向量）
**定位**：早期embedding技术，现在较少单独用于RAG。

**核心原理**：为每个词生成固定向量，不区分上下文。无法处理一词多义，通常需要配合其他技术使用。


## 三、实际业务中的组合策略

### 1. 混合检索（Hybrid Search）
**核心思想**：同时使用稀疏检索和稠密检索，融合两者结果，取长补短。

**为什么需要混合检索？**
- 稠密检索擅长语义理解，但可能漏掉精确关键词（如专业术语、ID、代码）
- 稀疏检索擅长关键词匹配，但可能不理解同义词和上下文

**实现方式**：
1. **两路并行召回**：分别用BM25/SPLADE（稀疏）和Bi-Encoder（稠密）检索
2. **结果融合**：使用RRF（Reciprocal Rank Fusion）等算法合并排序
3. **可调节权重**：通过`dense_weight`参数控制语义 vs 关键词的倾向

### 2. 多阶段检索（粗排 + 精排）
工业级RAG系统通常采用多阶段架构：

```
用户查询
    ↓
第一阶段（粗排，高召回）
    - 稀疏检索（BM25/SPLADE）
    - 稠密检索（Bi-Encoder）
    ↓ 召回Top-100~1000
第二阶段（精排，高精度）
    - Cross-Encoder重排序器
    ↓ 返回Top-3~10
大模型生成
```

**Cross-Encoder（重排序器）**：将查询和文档拼接后一起输入Transformer，输出相关性分数。精度最高，但无法预计算，只适合对少量候选集精排。

**代表性重排序模型**：
- **BGE-reranker系列**：`bge-reranker-v2-m3`、`bge-reranker-large`
- **MonoT5**：基于T5的reranker
- **Cohere Rerank**：商业API


## 四、选型建议总结

| 场景                    | 推荐方案                                         |
| ----------------------- | ------------------------------------------------ |
| 快速原型验证            | Bi-Encoder（BGE/OpenAI）+ BM25 简单混合          |
| 通用生产环境            | 混合检索：SPLADE/BGE-M3稀疏 + BGE稠密 + RRF融合  |
| 高精度要求（金融/医疗） | 混合检索 + Cross-Encoder重排序（如BGE-reranker） |
| 关键词精确匹配需求强    | 提升稀疏检索权重，使用BM25或SPLADE               |
| 长文档/复杂语义查询     | ColBERT 或 BGE-M3（多向量）                      |
| 多语言场景              | BGE-M3 或 text-embedding-ada-002                 |

### 研究趋势说明
值得注意的是，学术界近期研究发现，传统稀疏检索方法（如BM25、MRF、RM3）在某些RAG场景下效果可能优于稠密检索。这提示我们在实际选型时，不应盲目追求"新技术"，而应基于业务数据进行评测对比。

**最终建议**：在生产环境中，优先采用**混合检索（稀疏+稠密）+ 可选重排序**的架构，并根据业务数据做A/B测试验证效果。

## 2. 检索器到底是怎么检索的

你问到“检索算法是什么”，这个要分看。

## 2.1 稀疏检索算法

例如 BM25，本质是在倒排索引基础上，对词项重要度和词频做加权评分。

它更擅长：

- 标题词
- 专业术语
- 文档编号
- 组织名
- 法规名
- 产品 SKU
- 精确关键词

## 2.2 稠密检索算法

流程是：

1. 用 query embedding 模型把用户问题编码成向量
2. 在向量索引中找最近邻
3. 返回 topk chunk

相似度一般是：

- cosine similarity
- inner product
- L2 distance

## 2.3 ANN 近似最近邻

因为真实库很大，不能暴力全量比对，所以要用 ANN 索引。

典型包括：

- HNSW
- IVF
- IVF-PQ
- Flat 小库暴搜

其中 HNSW 很常见，因为召回和延迟平衡好。

IVF（倒排文件索引）和 HNSW（分层可导航小世界图）是向量检索中两种最核心的**近似最近邻（ANN）索引算法**。它们的目标都是在大规模向量集合中快速找到与查询向量最相似的若干个向量，牺牲微小的精度换取极大的速度提升。下面分别解释它们的原理、优缺点及适用场景。

---

## 1. IVF（Inverted File Index，倒排文件索引）

### 核心原理
IVF 基于**聚类**思想：
- **构建阶段**：将全部向量通过 k-means 聚类划分为多个簇（每个簇称为一个“倒排列表”）。每个向量被分配到离它最近的簇中心。
- **检索阶段**：给定查询向量，先计算它到所有簇中心的距离，选择最靠近的 `nprobe` 个簇；然后在这几个簇内做**暴力搜索**（计算查询向量与簇内所有向量的距离），返回最近的 k 个结果。

### 关键参数
- **`nlist`**：聚类中心的数量（即簇的个数）。值越大，索引构建越慢，但检索时可能更精确。
- **`nprobe`**：检索时探测的簇数量。值越大，召回率越高，但速度越慢。

### 优点
- 内存占用相对可控，可通过乘积量化（PQ）进一步压缩。
- 适合**超大规模**（亿级以上）向量集合。
- 构建速度较快。

### 缺点
- 精度受聚类质量影响，边界附近的向量可能被遗漏。
- 需要调参（nlist、nprobe）以平衡速度和召回率。

### 典型应用
Faiss 中 `IndexIVFFlat`、`IndexIVFPQ` 等。

---

## 2. HNSW（Hierarchical Navigable Small World，分层可导航小世界图）

### 核心原理
HNSW 基于**图结构**与**跳表思想**：
- 构建一个多层图，底层包含所有向量，上层是下层的子集（随机选取）。
- 每层内的节点通过边连接，形成一个小世界网络（即任意两点间存在短路径）。
- **检索时**：从顶层开始，贪心搜索离查询最近的节点，然后下降到下一层重复，直到最底层，最终在底层找到最近邻。

### 关键参数
- **`M`**：每个节点在图中连接的最大邻居数。影响内存和精度。
- **`ef_construction`** / **`ef_search`**：构建和搜索时动态候选列表的大小，控制召回率和速度的平衡。

### 优点
- **查询速度快**，且召回率高（通常优于 IVF）。
- 无需训练，支持增量插入（动态索引）。
- 对数据分布不敏感。

### 缺点
- 内存占用大（每个向量需存储邻居指针）。
- 构建时间较长。
- 超大规模（十亿级）时内存可能成为瓶颈。

### 典型应用
Faiss 中 `IndexHNSWFlat`、`IndexHNSWSQ`；向量数据库如 Qdrant、Milvus 的默认索引之一。

---

## 3. IVF vs HNSW 对比

| 维度         | IVF                                  | HNSW                          |
| ------------ | ------------------------------------ | ----------------------------- |
| **核心思想** | 聚类 + 倒排                          | 分层图 + 小世界搜索           |
| **内存占用** | 较低（尤其配合 PQ）                  | 较高（存储邻居连接）          |
| **查询速度** | 较快（取决于 nprobe）                | 非常快                        |
| **召回率**   | 中等（依赖聚类质量）                 | 高（可达 0.99 以上）          |
| **构建时间** | 快（k-means 聚类）                   | 慢（需要构建多层图）          |
| **动态插入** | 困难（需重建索引或使用 IVFADC 变种） | 支持（增量插入）              |
| **适用规模** | 亿级 ~ 千亿级                        | 百万级 ~ 十亿级（内存足够时） |

---

## 4. 在 RAG 系统中的选择

在实际的 RAG 应用中，向量数据库（如 Milvus、Qdrant、Elasticsearch）通常封装了多种索引类型，你可以根据数据量和硬件资源选择：

- **数据量 < 100 万**：直接用 **Flat（暴力搜索）** 或 **HNSW**，简单可靠。
- **数据量 100 万 ~ 1 亿**：**HNSW** 是首选，查询快、召回率高；若内存紧张，可选用 **IVF+PQ** 压缩。
- **数据量 > 1 亿**：**IVF+PQ** 是经典组合，可在有限内存下处理超大规模；或使用 **IVF+HNSW** 混合索引（如 Faiss 的 IndexHNSW + IVF 变种）。

### 重要提醒
- 索引的选择应基于**业务数据规模、查询延迟要求、召回率目标**进行基准测试。
- 现代向量数据库通常允许你动态切换索引，可先在开发环境使用 HNSW 快速验证，上线后根据实际负载调整。

---

## 5. 总结

- **IVF** 像是一本按主题分章节的书：先快速翻到相关章节，再在章节内逐页查找。
- **HNSW** 像是一张导航地图：从高速路快速接近目标区域，再通过街道级道路精确定位。

两者都是 ANN 索引的经典实现，在 RAG 系统的检索层扮演着加速器的角色。理解它们的原理有助于你为知识库选择合适的索引配置，从而平衡检索延迟与召回质量。

不是检索出来什么都拼进去。

## 应拼接的内容

### 高相关且高可信的 chunk

这是主体

### 必要的标题/小节信息

**context packing / context selection**

# 六、检索后为什么还要重排

因为召回不等于最终可用。

向量检索 topk 只是“可能相关”，并不等于“最适合回答”。

所以一般会加一层 reranker。

## reranker 的作用

对 query 和候选 chunk 做更精细的相关性判断。

常见作用：

- 去掉假相关
- 提升精确排序
- 让真正回答问题的证据排到前面

## 常见做法

### cross-encoder rerank

把 query 和 chunk 一起输入模型做打分，精度高但慢

### lightweight rerank

更快，但精度稍低

实际工程里常见做法是：

**粗召回大一点 → 精排缩小到少量高质量证据 → 再给 LLM**

# 七、如果检索结果拼接后超出上下文怎么办

这是非常常见的问题。

## 1. 根本思路

不是想办法把所有检索结果都塞进去，而是做**证据预算管理**。

## 2. 典型处理方式

在 RAG 系统中，检索阶段会从知识库中召回一批候选文本块（chunk）。直接将这些文本块全部塞入大模型会面临上下文窗口限制、成本增加、冗余信息干扰等问题。因此，需要在检索后对候选结果进行一系列处理，以提升最终生成质量。下面针对你列出的六种常见方法逐一展开。

---

### 2.1 限制 topn

**目的**：控制输入给大模型的证据数量，避免超出上下文窗口，同时减少无关信息干扰。

**原理**：向量检索返回的结果按相似度从高到低排序。只取前 `n` 个（如 3～10 个）作为最终的证据。这是一个简单的截断操作，能有效过滤掉低相关度的文本块，降低提示词长度和推理成本。

**实现**：在检索接口中直接设置 `top_k` 参数，例如 `vector_db.search(query, top_k=5)`。具体取值需根据业务场景和模型上下文窗口大小调整：对于短答案查询可取较小值（如 3），对于复杂综述可取较大值（如 10）。

**注意**：过于激进的 `top_n` 可能导致漏掉重要信息。通常建议先设置一个稍大的召回数（如 20），再通过重排序或压缩筛选出最终使用的少量块。

---

### 2.2 去重

**目的**：移除内容高度重复的文本块，防止冗余信息占据宝贵的上下文空间，也避免模型因重复内容产生偏见。

**原理**：由于文档切分和检索可能召回多个表述相似甚至完全一致的 chunk（例如不同切分方式导致同一段落被多次召回，或同一文档中多次出现类似句子）。通过去重可以保留一个代表性块即可。

**实现方式**：
- **基于文本相似度**：计算 chunk 之间的 Jaccard 相似度、编辑距离，或使用 Embedding 向量计算余弦相似度，若超过阈值则视为重复，保留其中一个。
- **基于哈希**：使用 **MinHash、SimHash** 等局部敏感哈希算法快速去重。
- **基于文档来源**：如果同一文档的相邻 chunk 内容连续，可合并或仅保留一个。

**应用场景**：当知识库中存在大量相似文档（如多个版本的同一说明书）或切分粒度较小时，去重尤其重要。

---

### 2.3 压缩

**目的**：将冗长的候选文本块进行压缩或摘要，保留核心信息，减少 token 占用，同时可能提升信息密度。

**原理**：对每个检索到的 chunk 或所有 chunks 整体进行压缩。常见压缩方式：
- **提取式摘要**：使用规则（如保留首尾句）或小模型（如 BERT）抽取关键句子。
- **生成式摘要**：使用大语言模型对每个 chunk 生成简短摘要（但会引入额外调用成本）。
- **去除冗余**：去掉链接、无意义修饰语、重复信息。

**实现**：
- 在检索后调用一个轻量级的摘要模型（如 T5-small）对每个 chunk 压缩。
- 或直接使用大模型对多个 chunks 进行统一压缩，例如提示“请将以下内容压缩成 3 个要点”。

**权衡**：压缩会损失细节，适用于那些答案不需要完整细节的场景（如概览、总结）。需要评估压缩前后对答案质量的影响。

---

### 2.4 父子块策略

**目的**：在检索时使用细粒度的子块（如段落）获得高精度匹配，在生成时提供粗粒度的父块（如章节）提供完整上下文，避免上下文碎片化。

**原理**：预先将文档切分为父子层级：父块（如章节、小节）和子块（如段落、句子）。入库时，子块携带父块 ID 或父块内容。检索时，使用子块进行向量检索，召回若干子块。然后根据这些子块找到对应的父块，将父块（而不是子块本身）作为证据输入给大模型。这样既利用了子块的细粒度匹配优势，又保证了模型获得完整的上下文。

**实现**：
- 存储时：每个子块记录其父块的 ID 或直接存储父块内容。
- 检索时：向量检索得到子块列表后，去重父块，或直接返回父块。
- 也可以先检索父块，再在父块内做二次搜索（两阶段检索）。

**优点**：能有效解决切分导致的上下文断裂问题，特别适合问答型场景（答案可能在段落中，但需要章节背景）。

---

### 2.5 基于问题类型选证据

**目的**：根据不同的问题类型（事实性、流程性、定义性等）动态调整证据的粒度和数量，使提供的上下文更匹配问题需求。

**原理**：不同类型的问题对证据的依赖不同：
- **事实性问答**（“某某公司的创始人是谁？”）：通常需要少量、精准的 chunk，甚至一个句子即可。
- **流程性问答**（“如何安装这个软件？”）：需要多步连续信息，可能需要多个相关 chunk 并按顺序组织。
- **定义性问答**（“什么是 Docker？”）：需要一个完整的概念描述，可能需要一个完整的章节。
- **比较/分析类问题**：需要多角度信息，可能需要多个不同来源的 chunks。

**实现**：在路由判断阶段识别问题类型（可通过规则、小模型或大模型分类），然后根据类型设置不同的检索和过滤参数。例如：
- 事实类：`top_k=3`，无需压缩。
- 流程类：`top_k=10`，按文档顺序重排，保留步骤完整性。
- 定义类：`top_k=5`，优先召回带有标题的 chunk。

**好处**：可定制化处理，提升不同类型问题的回答质量。

---

### 2.6 Map-Reduce 式回答

**目的**：当需要综合多个来源的信息回答复杂问题时，采用“分而治之”的方式，先对每个证据分别生成部分答案，再汇总成最终答案，避免上下文过长和注意力分散。

**原理**：模仿 MapReduce 思想：
- **Map 阶段**：将每个检索到的证据（或分组后的证据）单独输入大模型，生成针对该证据的部分回答（或提取关键信息）。
- **Reduce 阶段**：将所有部分回答合并，再让大模型综合生成最终答案。

**实现**：
- 将检索到的 chunks 分成若干组（如按文档来源分组）。
- 对每组调用 LLM，提问：“基于以下内容，回答用户问题：...” 得到中间结果。
- 将中间结果拼接，再次调用 LLM：“综合以下信息，给出最终答案。”
- 整个过程可并行执行 Map 阶段，减少总耗时。

**适用场景**：
- 需要从多个独立文档中提取信息并综合。
- 上下文总量超过模型窗口限制（可通过 Map-Reduce 分批处理）。
- 对答案的全面性要求高，且允许多次模型调用。

**缺点**：增加了模型调用次数和延迟，适用于离线或对实时性要求不高的场景。

---

## 总结

这六种方法并非互斥，在实际 RAG 系统中常常组合使用：

- **限制 topn** 是所有方法的前置基础，控制总量。
- **去重** 和 **压缩** 用于精炼证据。
- **父子块策略** 优化了上下文完整性。
- **基于问题类型选证据** 提供了自适应能力。
- **Map-Reduce** 则适用于超长上下文的复杂综合任务。

合理运用这些后处理技术，可以在保持检索召回率的同时，显著提升最终答案的准确性和流畅度。

---

在 RAG 系统的检索后处理中，去重是一个常见需求。MinHash 和 SimHash 是两种经典的**局部敏感哈希（LSH）**算法，它们能将高维数据（如文本）映射为固定长度的哈希签名，并使得相似的数据在哈希空间中也保持相似，从而高效地进行近似去重或相似性检测。

### 1. MinHash（最小哈希）

**核心思想**：用于估计两个集合的 **Jaccard 相似度**（集合交集大小与并集大小之比）。  
**原理**：将文本转化为集合（如词袋、n-gram 集合），然后通过多个哈希函数计算每个集合的“最小哈希值”，得到一个签名向量。两个集合的 Jaccard 相似度可以用它们的 MinHash 签名向量中相同位置值相等的概率来无偏估计。

**特点**：
- 适合**基于词重叠**的相似性判断（如文档、短文本）。
- 可处理大规模集合，通过构建索引（如 LSH Forest）快速找到候选相似对。
- 在 RAG 中可用于识别内容高度重复的 chunk，避免冗余。

### 2. SimHash（相似哈希）

**核心思想**：将文本映射为一个固定长度的二进制指纹（如 64 位），并通过**海明距离**衡量相似度。  
**原理**：对文本的每个特征（如词、n-gram）计算哈希值，并加权累加，最终根据累加结果的正负生成二进制位。两篇文本的 SimHash 指纹的海明距离越小，文本越相似。

**特点**：
- 适合**整体相似度**判断，尤其擅长检测近似重复（如网页去重、论文抄袭）。
- 生成指纹快，比较海明距离也非常快（可用位运算）。
- 在 RAG 中可用于快速过滤掉与已选 chunk 过于相似的候选块。

### 3. 对比与选择

| 维度                    | MinHash                               | SimHash                        |
| ----------------------- | ------------------------------------- | ------------------------------ |
| **输入形式**            | 集合（如词袋、n-gram）                | 带权重的特征（词频、TF-IDF）   |
| **相似度度量**          | Jaccard 相似度                        | 余弦相似度（通过海明距离近似） |
| **输出**                | 整数签名向量（长度通常 64~256）       | 固定长度的二进制串（如 64 位） |
| **适用场景**            | 文档去重、聚类、推荐系统              | 近似网页去重、文本抄袭检测     |
| **在 RAG 中的典型用法** | 检测 chunk 间的内容重叠，避免重复召回 | 快速过滤相似度高的冗余 chunk   |

在实际 RAG 系统中，如果希望精确控制去重粒度，MinHash 更适合；如果追求极速近似去重，SimHash 更高效。两者都可与 LSH 索引配合，实现大规模候选集的高效去重。

# 八、如果答案不在当前检索段，而在上一个段落怎么办

这是 chunk 边界问题，本质是**切片粒度和上下文恢复机制**的问题。

## 解决思路

### 1. overlap

切片时保留重叠区域

### 2. 邻接扩展

召回一个 chunk 时，把前后 chunk 一并取出

### 3. 父子块

用子块召回，父块作上下文

### 4. 标题树恢复

如果 chunk 属于某个小节，可以把小节标题和摘要一起给模型

### 5. sentence window retrieval

不是固定 chunk，而是以命中句子为中心扩展句窗

这几个方法里，工程上最常见且稳定的是：

**子块召回 + 父块还原 + 邻接扩展**

# 九、如果用户问题很复杂，是多跳问题怎么办

比如：

- “A 公司收购 B 之后，其 CEO 在收购前后分别是谁？”
- “某功能的退款规则和会员规则结合起来看，用户这种情况能否退款？”

这种问题不是单条证据能回答的。

## 1. 多跳问题的核心困难

- 需要多个证据拼接
- 证据之间可能来自不同文档
- 需要中间推理步骤
- 单次 topk 可能只召到其中一跳

## 2. 解决方式

### 2.1 问题分解

先把复杂问题拆成多个子问题。

例如：

1. A 公司收购 B 的时间
2. 收购前 CEO
3. 收购后 CEO
4. 综合生成答案

### 2.2 迭代检索

第一轮检索拿到中间实体，再用中间结果发起第二轮检索。

### 2.3 图式检索

利用实体关系、知识图谱、文档引用关系做跨文档跳转。

### 2.4 agentic RAG

让模型自己决定：

- 是否继续检索
- 检索哪个子问题
- 什么时候停止

这类系统比单轮 RAG 更复杂，但对多跳问题明显更有效。

当用户的问题涉及多个步骤、需要从多个文档中收集信息并进行推理时，这种**多跳问题**对 RAG 系统提出了更高要求。普通的单次检索往往无法一次性获取所有必要信息，因为每个子问题可能需要不同的检索策略或不同来源的知识。下面从**挑战、核心策略、实现路径**三个方面展开。

---

## 1. 多跳问题的典型特征

- 需要结合多个事实才能回答，例如“那位出演《盗梦空间》的演员在 2024 年上映的电影是什么？”（需先找到《盗梦空间》的演员，再找该演员的新电影）。
- 问题中隐含中间实体或关系，单次检索很难直接命中。
- 答案可能分布在不同文档甚至不同数据源中。

---

## 2. 应对多跳问题的常见策略

### 2.1 查询分解（Query Decomposition）
将复杂问题拆解为多个简单子问题，依次检索并汇总答案。

**实现方式**：
- **基于 LLM 的分解**：使用大模型将原问题拆分成若干子问题（例如通过提示：“将以下问题分解为 2-3 个独立的子问题”）。
- **顺序执行**：先回答第一个子问题，将其结果作为第二个子问题的上下文，再检索并回答，直到得到最终答案。
- **并行执行**：如果子问题相互独立，可以并行检索，最后合并结果。

**示例**：
> 原问题：“张艺谋导演的第一部国际获奖作品是哪一年上映的？”  
> 分解为：①“张艺谋导演的第一部国际获奖作品是哪部？” → ②“该作品是哪一年上映的？”

### 2.2 迭代检索 + 推理（ReAct / Self-Ask）
采用**行动-思考-观察**循环，让模型自主决定何时检索、检索什么、如何整合。

- **Self-Ask**：模型在回答过程中会提出“我需要知道 X”然后触发检索，将检索结果融入后续推理。
- **ReAct**（Reason + Act）：结合推理轨迹与行动（检索、计算等），交替进行，直到得出最终答案。

**适用场景**：问题复杂且依赖链较长，需要动态调整检索策略。

### 2.3 基于知识图谱的检索（Graph RAG）
将知识库构建为图结构（实体-关系-实体），将多跳问题转化为图上的路径查询。

- 先用检索找到初始实体节点，然后根据问题中的关系沿着图游走，收集相关节点信息。
- 再将收集到的信息拼接后交给 LLM 生成答案。

**优点**：对多跳关系有天然支持，适合“A 与 B 的关系”类问题。

### 2.4 多路检索 + 融合
同时执行多个不同的检索策略（如关键词检索、向量检索、基于实体检索），将结果合并后交给 LLM 综合回答。

- 可以避免因单一检索方式遗漏中间信息。
- 合并时需注意去重和排序。

### 2.5 递归检索 / 上下文增长
先进行一次宽泛检索，从结果中提取出关键实体或概念，再基于这些新信息进行第二轮检索。

- 类似人类“查资料时发现新关键词再继续查”的过程。
- 需控制迭代深度，避免无限循环或超时。

---

## 3. 如何在 RAG 系统中落地

### 3.1 基于 Agent 架构
将检索器包装成工具，让 LLM 作为 Agent 自主调用。例如使用 **LangChain** 的 `AgentExecutor` 或 **LlamaIndex** 的 `SubQuestionQueryEngine`。

```python
# 伪代码
tools = [RetrieveTool(name="知识库检索")]
agent = create_react_agent(llm, tools)
result = agent.run(user_question)
```

### 3.2 编排层实现查询分解
在 FastAPI 或其他后端服务中，编写一个 **多跳处理器**：

1. 调用 LLM 分解问题，得到子问题列表。
2. 对每个子问题，依次或并行执行检索（可复用之前的检索结果作为上下文）。
3. 将子问题的答案汇总，再次调用 LLM 生成最终回答。

### 3.3 结合对话记忆
多跳问题往往出现在多轮对话中，利用之前对话的 **工作记忆** 存储中间实体，可以避免重复检索。例如第一轮用户说“我想知道 A”，第二轮说“那 B 呢”，系统应能关联到 A。

---

## 4. 注意事项与挑战

- **检索次数增加**：多跳策略会多次调用检索和 LLM，导致延迟和成本上升。需设置最大迭代次数或超时。
- **错误传播**：中间步骤的错误会影响最终答案。可通过验证步骤、让模型自检来缓解。
- **召回率与精度平衡**：多跳检索可能召回大量无关内容，需配合后处理（重排序、压缩）控制。

---

## 5. 总结

处理多跳问题的核心思想是**将复杂推理过程拆解为可执行的检索-推理循环**。实践中可根据业务场景选择：

| 策略             | 适用场景                             | 复杂度 |
| ---------------- | ------------------------------------ | ------ |
| 查询分解         | 子问题相对独立，可线性组合           | 低     |
| ReAct / Self-Ask | 需要动态决定下一步，推理链较长       | 中     |
| Graph RAG        | 知识本身以实体关系为主，多跳路径明确 | 中高   |
| 多路融合         | 不确定哪种检索方式最有效，需互补     | 中     |

在真实系统中，往往将多种策略结合：先用分解规划，再用迭代检索获取细节，最后用融合提升鲁棒性。通过这样的设计，RAG 系统才能真正应对复杂、深度的用户问题。

# 十、知识冲突怎么办

你提到“检索结果知识冲突了怎么办”，这是生产系统里一定会遇到的问题。

例如：

- 一个旧文档说 CEO 是 A
- 一个新文档说 CEO 是 B

## 1. 冲突产生的来源

- 文档版本不同
- 来源权威性不同
- 更新时间不同
- 多个部门维护口径不同
- 一条是草稿，一条是正式版本

## 2. 解决优先级

系统不能把冲突责任甩给大模型，最好在检索或组装阶段就治理。

### 2.1 版本优先

优先最新有效版本

### 2.2 来源优先

官网 > 内部正式制度 > FAQ > 非正式文档

### 2.3 状态优先

已发布 > 草稿
生效中 > 已失效

### 2.4 文档类型优先

制度原文 > 二次解读

### 2.5 时间有效区间判断

问的是“现在”，就只取当前有效版本
问的是“2023 年”，则按历史版本回答

## 3. 给 LLM 的策略

如果仍有冲突，可以让模型：

- 明确指出冲突来源
- 给出各自依据
- 优先采用最新权威来源
- 必要时提示知识库存在不一致

但最理想的是**在生成前先做冲突消解**，而不是让模型瞎裁判。

---

在 RAG 系统中，检索结果出现知识冲突（即不同文档或段落对同一事实给出矛盾的信息）是常见问题。这种冲突可能源于数据源本身的差异（如不同时期的文档、不同作者的观点、错误信息等），如果不加处理直接输入大模型，可能导致模型困惑、回答摇摆或错误。以下从**冲突识别、处理策略、工程实践**三个方面给出系统性的解决方案。

## 1. 冲突的类型

- **事实冲突**：对同一实体、事件、数值给出不同说法（如“A公司成立于2010年” vs “A公司成立于2012年”）。
- **观点冲突**：对同一问题存在不同立场或评价（如“该药物疗效显著” vs “该药物副作用大”）。
- **逻辑冲突**：不同证据之间存在逻辑矛盾，无法同时成立。

## 2. 处理策略

### 2.1 基于可信度的排序与筛选
在检索后处理阶段，为每个结果赋予可信度分数，优先保留高可信度的证据。

- **来源权威性**：给官方文档、权威机构、经过验证的数据库更高的权重。
- **时效性**：对于时间敏感的事实（如公司财报、新闻），较新的文档优先。
- **一致性校验**：如果一个事实在多个独立来源中一致，则可信度更高（可看作“共识”）。

**实现**：在检索时，将文档的元数据（如来源类型、发布时间、引用次数）作为排序因子，或在重排序模型中加入这些特征。

### 2.2 冲突消解模型
使用一个专门的模型或 LLM 对冲突证据进行判断，决定采纳哪个或如何综合。

- **多数投票**：如果冲突是多个来源之间的，可以采用多数原则。
- **大模型裁决**：将冲突的证据和问题一起交给 LLM，让模型自行判断哪个更合理，或要求模型说明冲突并选择。例如提示：“以下信息存在矛盾，请根据常识和逻辑判断哪个更可信，并给出理由。”
- **人工规则**：对于特定领域，可以预置规则（如“以最新时间为准”、“以公司公告为准”）。

### 2.3 生成时处理冲突
将冲突信息全部输入给大模型，但要求模型在回答中明确指出冲突，并给出不同可能性。

- **暴露矛盾**：让模型回答“关于这个问题，存在两种说法：……。根据来源A，……；根据来源B，……。建议进一步核实。”
- **综合回答**：如果冲突可以调和（如不同视角），模型可综合呈现，让用户自行判断。
- **要求模型选择**：在提示中明确要求模型基于逻辑或常识选择最合理的一方，并说明依据。

这种方法适合对准确率要求较高、且允许一定解释的场景，避免模型强行给出错误结论。

### 2.4 数据源头治理
在构建知识库时，通过清洗和去重减少潜在冲突。

- **去重**：使用 MinHash、SimHash 去除内容高度相似的冗余文档，减少因复制粘贴带来的虚假冲突。
- **版本管理**：对同一主题的多版本文档，只保留最新版本或明确标记版本信息。
- **标注可信度**：在入库时人工或自动标注来源的可信度（如官方文档标记为高可信，用户论坛标记为低可信）。

### 2.5 图谱一致性校验
如果系统维护了知识图谱，可以利用图谱进行冲突检测。例如，实体“A公司”的“成立时间”属性如果出现两个不同值，图谱可以触发冲突报警，并依靠预定义的规则（如以最早来源为准）自动修复，或在检索时提供属性置信度。

---

## 3. 工程实践建议

### 3.1 多级处理流程
```
检索结果 → 元数据过滤（权威性/时效性） → 冲突检测（相似度聚类） → 冲突消解（规则/模型） → 生成
```

- 先通过元数据筛选掉低质量来源。
- 然后对结果进行聚类，发现可能存在冲突的证据组。
- 对冲突组进行消解（如选择最高分证据，或调用 LLM 裁决）。
- 最后将无冲突的证据交给大模型生成答案。

### 3.2 利用 LLM 的 few-shot 能力
可以设计一个提示模板，让 LLM 在遇到冲突时自动处理。例如：
```
你将获得一些来自不同文档的片段，它们可能包含矛盾信息。
请根据以下原则处理：
1. 优先采用官方来源或权威机构的信息。
2. 若时间不同，以最新信息为准。
3. 如果无法判断，请如实告知用户存在多种说法，并分别列出。
```

### 3.3 可观测性
记录冲突发生的频率、类型以及消解结果，用于持续优化知识库质量（如剔除低质量源、更新陈旧数据）。

---

## 4. 总结

| 冲突类型              | 推荐策略                                         |
| --------------------- | ------------------------------------------------ |
| 事实冲突（数值/日期） | 基于时效性+权威性筛选；多数投票；模型裁决        |
| 观点冲突              | 生成时暴露矛盾，综合呈现不同观点                 |
| 逻辑冲突              | 优先筛选高质量证据；若无法消解，告知用户信息矛盾 |

在真实系统中，通常需要组合使用多种策略，既要保证回答的准确性，又要对用户透明。对于关键业务（如医疗、金融），建议采用“保守策略”——宁可承认不确定性，也不强求输出错误结论。

# 十一、现实世界知识变化了，知识库怎么更新

你举的 CEO 从 A 变成 B，就是典型的知识新鲜度问题。

## 1. 最重要的原则

不要简单“覆盖旧知识”，而要做**版本化管理**。

因为用户可能问：

- 现在的 CEO 是谁
- 去年 6 月的 CEO 是谁

这要求系统保留时间维度。

## 2. 正确做法

每条知识最好有：

- `version`
- `updated_at`
- `valid_from`
- `valid_to`
- `is_current`

更新时不是直接改文本，而是：

1. 旧版本设为失效或非 current
2. 新版本作为新记录写入
3. 检索时按时间语义过滤

## 3. 查询时的处理

### 用户问“现在”

过滤 `is_current = true`

### 用户问“2024 年 3 月”

过滤 `valid_from <= t < valid_to`

这就是为什么 metadata 必须带时间字段。

------

# 十二、知识库如何增量更新

增量更新不是“重新全量建库”，而是让变化部分快速生效。

## 1. 增量更新链路

通常是：

**变更检测 → 差异计算 → 受影响文档解析 → 重新切片 → 重算 embedding → 更新索引 → 切换版本**

## 2. 变更检测怎么做

可以根据：

- 文件哈希
- 文档更新时间
- CDC 数据变更流
- 消息队列事件
- 定时扫描

## 3. 更新粒度

### 文档级更新

整篇重做，简单但成本高

### chunk 级更新

只更新受影响 chunk，更精细

### section 级更新

在结构化文档中很有用

# 十三、如果用 HNSW，增量更新怎么做

你专门问到了 HNSW，那我单独讲。

## 1. HNSW 的基本特点

HNSW 是分层近邻图，查询时从高层粗定位，逐层下沉到低层找近邻。

它的优势是：

- 查询快
- 召回高
- 适合在线插入

## 2. HNSW 的新增

对新 chunk 做增量插入时，大致流程是：

1. 计算新向量
2. 从图的入口点开始，从顶层往下贪心搜索
3. 每层找到若干近邻候选
4. 在底层和部分上层建立连接
5. 若某些节点连接数超过上限 M，则按启发式裁剪邻边

这意味着 **插入一般是支持在线进行的**。

## 3. HNSW 的删除

删除比插入麻烦得多。

因为图结构里的边已经建立，硬删除会影响图连通性与检索质量。

所以真实系统里经常这样做：

### 软删除

把旧 chunk 标记为 `is_deleted=true` 或 `inactive`

查询时过滤掉

### 延迟重建

当删除和更新累计到一定比例，再后台重建索引

这是非常常见的工程做法。

HNSW 索引对文档新增和删除的实现方式，体现了其作为动态图结构的核心优势。与需要完全重建的静态索引（如 Annoy、IVF）不同，HNSW 支持高效的实时更新，但在具体实现上，新增和删除的机制有显著差异。

下面的表格对比了这两种操作的核心机制：

| 操作类型          | 核心机制                                                     | 复杂度/影响                                                  | 挑战                                                     |
| :---------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :------------------------------------------------------- |
| **新增 (Insert)** | **增量构建**：为新向量在每层图中寻找最近邻并建立连接。       | 时间复杂度 O(log N)，单次插入平均耗时约 0.12ms (百万级数据)。 | 在数据密集区域插入可能导致大量连接更新，影响构建速度。   |
| **删除 (Delete)** | **“软删除”+定期重建**：通常不直接从图中移除节点，而是标记删除，查询时过滤。 | 频繁删除会使图碎片化，降低搜索效率，需要触发后台任务进行索引整理与重建。 | 直接物理删除节点并修复图链接成本极高，是HNSW的主要挑战。 |

---

### 📈 新增文档：如何动态插入？

当一个新的向量需要被添加到HNSW索引中时，过程如下：

1.  **确定层级**：为每个新节点随机生成一个最大层级 `l`，该值通常服从指数分布。这意味着大多数节点只存在于底层，而少数节点会出现在高层，用于导航。
2.  **逐层寻找邻居**：从最高层开始，贪婪地寻找离新向量最近的节点作为入口点。然后，在每一层，都会搜索该层中与新向量最接近的若干个节点。
3.  **建立连接**：从第 `l` 层向下直到最底层，将新向量与步骤2中找到的最近邻节点连接起来。为了控制图的密度，通常会使用启发式算法（如选择最邻近且不冗余的邻居）来限制每个节点的最大连接数 `M`（默认值通常为20）。
4.  **局部优化**：新向量的加入也可能会触发其邻居节点的连接列表更新，以确保图的整体质量。

这个过程就是HNSW支持**实时增量更新**的关键，它只影响索引的局部结构，完全避免了全量重建，非常适合数据频繁变化的场景。

### 🗑️ 删除文档：为何复杂且需要“软删除”？

从HNSW的图结构中物理删除一个节点非常困难，因为这不仅需要移除节点本身，还要修复其所有邻居节点之间因此断裂的连接，这可能导致昂贵的图重新平衡操作。因此，成熟的生产级系统通常不直接物理删除，而是采用更高效的两步方案：

1.  **逻辑删除（标记）**：当收到删除请求时，系统并不会立即从图中移除节点。相反，它会在一个单独的元数据存储区（例如，Oracle向量数据库中的“**共享日志（Shared Journal）**”或一个独立的布隆过滤器）中将该向量标记为“已删除”。
2.  **查询时过滤**：在执行近似最近邻搜索时，HNSW索引会返回一个候选集。随后，查询引擎会将这些候选ID与“已删除”列表进行比对，并在返回最终结果前将其过滤掉。
3.  **后台清理与索引重建**：随着“软删除”的标记越来越多，索引中的无效数据会逐渐增多，导致查询效率和内存利用率下降。为了解决这个问题，系统会监控已删除数据的比例。当达到一定阈值（例如，总数据量的20%）或满足特定条件时，会在后台自动触发一个**索引重建（Repopulation）**任务。这个任务会读取所有未被标记删除的有效数据，然后构建一个全新的、紧凑的HNSW索引，最后用新索引原子性地替换旧索引，从而彻底清理掉已删除数据的物理空间。

### ⚙️ 生产环境的工程优化

在实际应用中，为了进一步提升性能和资源利用率，成熟的系统（如腾讯云向量数据库和ToonDB）还会引入更多优化策略：

*   **增量缓冲区 (Delta Buffer)**：对于极高并发的写入场景，系统会先将新增的向量写入一个内存缓冲区。查询时同时检索缓冲区（暴力搜索）和主HNSW索引。当缓冲区满了之后，再批量将数据刷新（Flush）到主HNSW索引中。这种**批量插入**可以显著减少HNSW图结构的频繁调整，大幅提升写入吞吐量。
*   **内存与存储优化**：利用**半精度量化**（如FP16）技术将向量内存占用降低近一半；或使用**分段存储（Segment化存储）**，将索引分为多个小段，新增数据时只需追加新段，避免了频繁的内存数据拷贝。
*   **参数调优**：通过调整关键参数来平衡写入性能和查询精度，例如：
    *   **M (最大连接数)**：值越大，召回率越高但内存占用和索引时间也越大。
    *   **ef_construction (构建时搜索广度)**：值越大，图质量越高、查询越快，但索引构建越慢。
    *   **max_level (最大层数)**：根据数据总量 `N` 设置为 `floor(ln(N))`，用于控制索引的层级结构。

总的来说，HNSW的精妙之处在于通过**局部插入**实现了动态更新，同时通过**逻辑删除加定期重建**的工程策略巧妙地绕开了在图结构中直接物理删除的巨大复杂性。这套机制使得HNSW成为当前RAG应用中处理大规模、动态变化知识库的理想索引方案。

## 4. 文档更新时怎么做

如果某个文档修改了：

### 方案一：软删旧 chunk + 插入新 chunk

最稳

### 方案二：分段索引

新数据先进增量索引，后台再与主索引合并

### 方案三：多版本并存 + 查询过滤 current

适合需要时间追溯的业务

## 5. HNSW 更新时的注意点

### 图会逐渐脏

频繁更新后，局部连接质量下降

### 过滤成本增加

软删除过多会拖慢查询

### 周期性 compact / rebuild 必须有

不能无限增量而不重整

所以 HNSW 很适合增量插入，但**不适合长期无治理地频繁删除和替换**。

# 十四、如果用户的问题是域外问题怎么办

这是企业系统里非常重要的一步。

一个好的知识问答系统，不能“只要用户提问就硬检索 topk 然后硬答”。

否则会出现典型问题：

- 明明知识库里没有，还是给出似是而非答案
- topk 召回了一些边缘相关内容，模型强行编答案
- 用户误以为这是系统权威结论

## 正确做法

系统应该先判断：

**这个问题是否属于当前知识库可回答范围。**

# 十五、如何识别域外意图

可以从多层做。

## 1. 语义域分类

训练或提示一个分类器，把 query 分为：

- 域内问题
- 域外问题
- 不确定问题

## 2. 检索置信度判断

如果检索结果整体分数很低，或者 top1-topk 都缺乏明显相关性，说明可能域外。

可用信号包括：

- top1 相似度过低
- topk 分数整体低
- 分数分布平坦
- rerank 分数也低

## 3. 关键词/实体覆盖判断

如果 query 中关键实体在知识库从未出现，也很可能域外。

## 4. 基于生成校验

让一个轻量模型判断：

- 检索证据是否足以支持回答
- 如果不足，则拒答或转开放域模式

## 5. 业务白名单 / 黑名单

例如系统只服务：

- 某产品
- 某部门制度
- 某企业知识

其他一律判域外。

------

## 域外时怎么处理

不要硬答。常见策略：

### 1. 明确拒答

“当前知识库没有覆盖这个问题。”

### 2. 建议用户换问法

尤其在歧义或实体不明确时

### 3. 切到通用大模型模式

但要明确告诉用户：这是通用回答，不代表知识库依据

### 4. 引导到人工客服或其他系统

企业里很常见

# 十六、上下文组装：如何把检索结果变成 prompt

这一步很容易被忽略，但非常关键。

## 一个好的上下文组装器要做什么

### 1. 去重

同源重复 chunk 只留一份

### 2. 合并

相邻 chunk 可以合并，避免碎片化

### 3. 排序

一般不是单纯按检索分数排，而是综合：

- 相关性
- 权威性
- 新鲜度
- 是否互补

### 4. 打标签

给每段上下文附上：

- 来源
- 标题
- 时间
- 文档类型

### 5. 控制预算

每段 chunk 有 token 成本，不能无限塞

## prompt 里通常会有几部分

- 系统指令：回答风格、引用规则、拒答规则
- 用户问题
- 检索证据块
- 输出约束：只基于证据回答，证据不足要说明

如果是企业系统，还会加：

- 安全规则
- 敏感信息脱敏规则
- 角色权限说明

在 RAG 系统的真实业务中，如何将检索结果、元数据、记忆等元素组织成最终的大模型输入（prompt），直接决定了回答的质量和稳定性。下面从**数据整合策略、Prompt 结构设计、技术实现要点**三个方面展开。

---

## 一、需要纳入 Prompt 的要素

| 要素                 | 来源                                       | 作用                                         |
| -------------------- | ------------------------------------------ | -------------------------------------------- |
| **检索结果（证据）** | 向量/混合检索返回的文本块                  | 提供事实依据，回答的核心素材                 |
| **元数据**           | 文档库中的字段（来源、时间、部门、权限等） | 增强证据可信度、支持溯源、便于模型判断优先级 |
| **短期记忆**         | 当前会话的对话历史                         | 保持多轮对话连贯性，理解指代和上下文         |
| **长期记忆**         | 用户画像、历史偏好、跨会话知识             | 个性化回答，减少重复提问                     |
| **系统指令**         | 预设的 role prompt                         | 定义模型角色、回答风格、约束（如格式、长度） |
| **用户问题**         | 当前输入                                   | 明确要回答的问题                             |

---

## 二、Prompt 构建的核心原则

1. **优先级排序**：将最关键的信息放在前面（如系统指令、用户问题），确保模型注意力集中。
2. **结构化标记**：使用明确的 XML 标签或 Markdown 分隔符区分不同类型的上下文，便于模型理解。
3. **长度控制**：实时计算 token 数，超出模型上下文窗口时进行截断或压缩（优先保留最新、最相关的内容）。
4. **来源可溯**：在证据中嵌入来源标识（如 `[1]`），方便模型引用，也便于前端展示。
5. **去噪**：过滤掉冗余、低质量、重复的证据，避免干扰。

---

## 三、典型 Prompt 结构模板

下面是一个实用的 prompt 模板（以 OpenAI 的 chat 格式为例）：

```python
system_message = """
你是一个专业的智能助手，基于提供的知识库回答用户问题。
如果知识库中的信息不足以回答，请如实告知，不要编造。
回答时尽量引用来源（如[文档A]）。
"""

# 构建历史消息（短期记忆）
history_messages = [
    {"role": "user", "content": "之前的问题..."},
    {"role": "assistant", "content": "之前的回答..."}
]

# 长期记忆（用户画像）
user_profile = "用户偏好：喜欢简洁回答，技术背景强。"

# 检索结果（带元数据）
retrieved_chunks = [
    {"text": "API 认证流程需要先获取 token...", "source": "技术文档.md", "page": 12, "score": 0.95},
    {"text": "最佳实践是使用 JWT...", "source": "最佳实践指南.pdf", "page": 5, "score": 0.88}
]

# 构建上下文文本
context = f"{user_profile}\n\n" if user_profile else ""
context += "以下是相关的参考资料：\n"
for i, chunk in enumerate(retrieved_chunks):
    context += f"[{i+1}] 来源：{chunk['source']} (页 {chunk.get('page','')})\n{chunk['text']}\n\n"

# 最终用户问题
user_question = "当前用户的问题"

# 组装 messages
messages = [
    {"role": "system", "content": system_message},
    *history_messages[-6:],  # 只保留最近6轮，避免过长
    {"role": "user", "content": f"{context}\n用户问题：{user_question}"}
]
```

## 四、各要素的精细化处理

### 1. 检索结果（证据）的格式化
- **添加序号和来源**：`[1] 来自《API设计规范》第3章：...`
- **按相关性排序**：将分数最高的放在前面，但若存在时间顺序要求（如流程），可按逻辑顺序重排。
- **合并相似内容**：对于重复度高的证据，可只保留一个，或在提示中注明“多个来源一致认为...”。

### 2. 元数据的利用方式
元数据可以通过两种方式融入：
- **嵌入到文本中**：适合少量关键字段，如来源、时间、作者。
- **作为结构化信息单独提供**：如果模型支持函数调用或结构化输入（如 OpenAI 的 `tool_choice`），可以将其作为工具调用的参数传递，但大多数情况下，将其自然语言化更通用。

对于权限类元数据（如“仅限技术部门”），通常不应直接暴露给模型，而是在检索阶段就已过滤。

### 3. 短期记忆（对话历史）
- **保留最近 N 轮**（如 5-10 轮），避免上下文爆炸。
- **如果历史过长，可压缩**：用 LLM 将早期对话摘要成一段文字，代替原始记录。
- **在 prompt 中明确区分**：可使用 `[历史对话]` 标签，让模型知道哪些内容是之前发生的。

### 4. 长期记忆
- **以自然语言描述用户画像**：例如“用户张三，技术总监，关注 API 安全和性能。”
- **放在 prompt 开头**，作为系统上下文的一部分。
- **可定期更新**：每次会话结束后，根据交互内容异步更新长期记忆。

### 5. 系统指令
- **固定指令**：如角色定义、回答风格、禁止事项。
- **动态指令**：根据用户问题类型（如事实性、流程性）添加不同要求，例如“请按步骤列出操作流程”。

---

## 五、处理 Token 限制的实践

当所有元素加起来超过模型上下文窗口时，需要执行截断策略：

- **优先级顺序**：系统指令 > 用户问题 > 短期记忆 > 长期记忆 > 检索结果。
- **对检索结果**：保留高分的前几个，低分的丢弃；或对长文本进行摘要压缩。
- **对短期记忆**：保留最近的轮次，对早期的进行摘要。
- **动态调整**：在代码中实时计算 token 数（使用 tiktoken 等库），循环移除低优先级内容直到满足长度。

## 六、代码实现示例（FastAPI 中）

```python
import tiktoken
from typing import List

def build_prompt(
    query: str,
    retrieved_chunks: List[dict],
    history: List[dict],
    user_profile: str = "",
    max_tokens: int = 8000
) -> List[dict]:
    encoder = tiktoken.encoding_for_model("gpt-3.5-turbo")
    
    system = "你是一个智能助手..."
    messages = [{"role": "system", "content": system}]
    
    # 添加用户画像（如果存在）
    if user_profile:
        messages.append({"role": "system", "content": f"用户信息：{user_profile}"})
    
    # 添加历史（保留最近5轮）
    for msg in history[-10:]:
        messages.append(msg)
    
    # 构建上下文
    context = "参考资料：\n"
    for i, chunk in enumerate(retrieved_chunks):
        context += f"[{i+1}] {chunk['source']}: {chunk['text']}\n"
    context += f"\n问题：{query}"
    
    messages.append({"role": "user", "content": context})
    
    # Token 计数与截断
    while True:
        total_tokens = sum(len(encoder.encode(m["content"])) for m in messages)
        if total_tokens <= max_tokens:
            break
        # 优先截断最早的对话历史（除系统消息）
        for i in range(len(messages)-1, 0, -1):
            if messages[i]["role"] != "system":
                del messages[i]
                break
    return messages
```

## 七、高级优化技巧

1. **指令微调**：针对你的业务场景，微调模型使其更擅长理解你定义的特殊标记（如 `[来源]`、`[用户偏好]`）。
2. **动态提示选择**：根据问题类型，选用不同的 prompt 模板（如代码类、流程类、闲聊类）。
3. **分层压缩**：对长文档使用递归摘要，将多级摘要与原始 chunk 结合，形成分层上下文。
4. **异步预计算**：对长期记忆和常用检索结果预先构建 prompt 片段，加速在线组装。

---

## 八、总结

将检索结果、元数据、记忆转化为 prompt 的本质是**将多源异构信息组织成符合模型输入习惯的结构化文本**。关键步骤包括：

- **分门别类**：用标签区分系统指令、历史、证据等。
- **优先级管理**：根据重要性排序，控制长度。
- **来源透明**：让模型知道信息出处，便于引用和校验。
- **动态适应**：根据 token 限制实时裁剪。

通过精心设计的 prompt 组装策略，RAG 系统才能在复杂业务中稳定输出高质量、可溯源的答案。

# 十七、如何让模型不要乱答

这和 prompt 设计直接相关。

## 常见约束

### 1. 明确要求“只依据提供的资料回答”

### 2. 如果资料不足，必须说不知道

### 3. 输出中附带引用编号

### 4. 冲突时优先最新权威资料

### 5. 对不确定部分单独标注

这不能彻底杜绝幻觉，但能明显降低风险。

------

# 十八、大模型的结果如何及时返回前端，减少首字等待

这属于用户体验层，但非常重要。

## 1. 流式输出

大模型一边生成一边把 token 推给前端，而不是整个答案生成完再返回。

常见实现是：

- SSE
- WebSocket
- HTTP chunked response

这样用户会更快看到首字。

## 2. 为什么首字等待会长

首字延迟不仅是模型生成慢，还包括前置链路：

- query 理解
- 重写
- embedding
- 检索
- rerank
- prompt 组装
- LLM 首 token 推理

很多系统慢不是慢在生成，而是慢在生成前。

## 3. 如何降低首字等待

### 3.1 并行化前置步骤

例如：

- query rewrite 和意图识别并行
- dense 检索和 sparse 检索并行

### 3.2 减少不必要步骤

简单问题不要走完整复杂链路

### 3.3 轻量模型做前处理

不要什么都拿大模型做

### 3.4 提前返回状态

前端先显示：

- 正在检索资料
- 正在生成回答

### 3.5 流式生成

一有 token 就推送

------

# 十九、如何提高整体链路的处理效率

这个问题要从不同层一起看。

------

## 1. 数据层优化

### 更高质量的清洗

垃圾进，垃圾出

### 更合理的切片

chunk 太小召回碎，太大浪费上下文

### metadata 完整

便于过滤，减少无效检索

### 热门知识预计算

例如 FAQ 可以直接缓存答案或证据集

------

## 2. 检索层优化

### 混合检索

降低漏召回

### ANN 参数调优

比如 HNSW 的 efSearch、M 等

### 先粗召回再精排

减少 rerank 成本

### 加 metadata filter

先按租户、部门、时间过滤，再检索

### 查询改写

减少因用户表达差异带来的召回损失

------

## 3. 生成层优化

### 控制进入 prompt 的证据数

不要盲目 top10 全塞

### 对长证据先压缩

让模型只看关键内容

### 模型分级路由

简单问答走小模型，复杂问答走大模型

### 模板化回答

对于固定类 FAQ 可以减少自由生成

------

## 4. 系统工程优化

### 并行执行

- 检索并行
- 多源召回并行
- 前处理并行

### 缓存

- query cache
- embedding cache
- rerank cache
- answer cache
- 热门文档缓存

### 异步化

日志、埋点、分析不要阻塞主链路

### 连接池与批处理

embedding、数据库、向量库都要做

### 分层降级

某一层失败时要能优雅退化：

- rerank 挂了，退回基础召回
- 检索失败，改成通用回答或拒答
- 主模型忙，切小模型

------

# 二十、一个更真实的在线处理顺序

如果把整个在线问答流程写成“真实系统顺序”，通常像这样：

## 第 1 步：接收用户问题

拿到 query、会话 id、用户 id、租户信息、权限信息

## 第 2 步：对话状态恢复

从会话记忆中恢复当前主题、实体、上下文

## 第 3 步：意图识别

判断：

- 是否知识问答
- 是否域外
- 是否需要检索
- 是否需要澄清
- 是否是多跳问题

## 第 4 步：查询改写

把当前轮转成适合检索的完整 query

## 第 5 步：检索规划

决定：

- 用哪些 retriever
- 是否要 metadata filter
- topk 设多少
- 是否多轮检索

## 第 6 步：召回

BM25、向量检索、标签过滤并行执行

## 第 7 步：候选合并

去重、合并不同通道的候选

## 第 8 步：重排

筛出最可回答问题的证据

## 第 9 步：冲突与时效治理

按版本、时间、权威性筛掉不该进入 prompt 的内容

## 第 10 步：上下文扩展

必要时取父块、邻块、标题摘要

## 第 11 步：上下文预算控制

压缩、截断、筛选，确保不超窗口

## 第 12 步：生成回答

LLM 基于证据生成，必要时附引用

## 第 13 步：流式返回前端

边生成边返回

## 第 14 步：事后记录

记录：

- query
- 检索结果
- 最终证据
- 模型输出
- 用户反馈
- 延迟指标
- 是否命中缓存
- 是否拒答

这些日志后续可用于：

- 评估召回质量
- 发现知识缺口
- 优化 chunk 策略
- 构建反馈学习闭环

------

# 二十一、你这个系统真正需要关注的核心矛盾

如果把所有细枝末节收束起来，一个 RAG 知识问答系统的核心矛盾其实就几个：

## 1. 召回要广，但给模型的上下文要精

所以需要：

- 混合召回
- rerank
- context packing

## 2. 知识要新，但又要保留历史可追溯

所以需要：

- 版本化
- 时间有效区间
- current 标记

## 3. chunk 要细，但语义不能碎

所以需要：

- 结构化切片
- overlap
- 父子块
- 邻接扩展

## 4. 问题表达不稳定，但检索必须稳

所以需要：

- query rewrite
- 指代消解
- 实体抽取
- 意图识别

## 5. 不能什么都答

所以需要：

- 域外检测
- 证据充分性判断
- 拒答机制

## 6. 用户要快，但链路本身很长

所以需要：

- 并行化
- 缓存
- 小模型前处理
- 流式输出
- 分级路由

------

# 二十二、一个比较稳妥的工程落地方案

如果你不是做论文，而是做一个企业级知识问答系统，我会建议默认采用下面这套思路：

## 离线侧

- 文档清洗与结构化解析
- 结构感知切片 + 少量 overlap
- 保存完整 metadata
- dense embedding + BM25 双索引
- 文档版本化管理
- chunk 级增量更新
- HNSW 支持在线插入，删除采用软删 + 周期重建

## 在线侧

- 先做意图识别和 query rewrite
- 域内才走检索
- 稀疏 + 稠密混合召回
- reranker 精排
- 子块召回 + 父块补全
- 上下文预算控制
- 基于证据回答，不足则拒答
- 流式输出到前端

## 治理侧

- 文档来源权威性排序
- 时间/版本冲突消解
- 域外问题识别
- 用户反馈回流
- 热点问答缓存
- 定期评估召回与生成质量

------

# 二十三、一句话总结

一个真正可用的 RAG 知识问答系统，不是“把文档转向量然后 topk 拼 prompt”，而是：

**以文档治理为基础，以意图识别和查询改写为入口，以混合检索和精排为核心，以版本/冲突/域外控制为安全阀，以流式生成和缓存并行为体验优化的一整套知识服务系统。**
