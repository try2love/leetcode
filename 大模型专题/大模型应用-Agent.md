## Q24：Agent 和 RAG 的区别？

- RAG：核心是“检索证据→生成”
- Agent：核心是“规划→工具执行→状态迭代→达成目标”，可能包含RAG作为工具。

## Q25：function calling 你怎么做稳？

- 必备：
  - schema 校验、类型检查
  - 超时/重试/幂等
  - 工具输出校验（防注入）
  - 全链路日志与回放
- 追问：工具出错怎么办？（fallback策略：换工具/降级/请求澄清）

## Q26：Planning 方法你了解哪些？取舍？

- ReAct：边想边做，简单但可能发散
- Plan-Execute：先计划再执行，结构清晰但计划可能过时
- ToT：搜索更强但成本高
- 追问：如何让它不“无限循环”？（step limit、cost budget、终止条件、反思模块）

## Q27：记忆怎么做？记忆污染怎么治理？

- 短期：窗口/摘要；长期：向量库
- 污染：错误信息写入后反复被召回
- 治理：置信度、来源引用、版本控制、可撤销、写入前校验

### 模块 1：Tool Calling 与协议层（Agent 的“手脚”）

**必做题**

### 模块 2：Agent Orchestration（编排）与状态机（可靠性的核心）

很多公司已经不满足“while loop 调模型”，更偏好**可控编排**（状态、回放、人审、持久化）——这也是 LangGraph 强调的能力点：state、durable execution、human-in-the-loop、streaming ([LangChain Docs](https://docs.langchain.com/oss/python/langgraph/overview?utm_source=chatgpt.com))。

**必做题**

6) 写一个最小 **Agent Runtime**：状态 `state`（目标、已完成子任务、工具结果缓存、预算、错误历史）
7) 把流程写成 **有向图/状态机**：`PLAN → ACT(tool) → OBSERVE → UPDATE → (loop/stop)`
8) 加 **断点续跑**（durable execution）：进程挂了能从上次 step 恢复
9) 加 **Human-in-the-loop**：关键动作（发邮件/删文件/付款）必须人工确认
10) 加 **流式输出**：边思考边输出“可见的行动日志”（不是暴露隐私推理，而是可解释轨迹）

**验收**

- 任何一步失败可回放；能给出“为什么做这步、用了什么证据、下一步是什么”的可解释轨迹。

**面试必问**

- 为什么要状态机？和纯 ReAct prompt 有啥差别？
- durable execution 怎么实现？存哪些状态？
- 人审放在哪些节点？如何避免“卡住不动/无限循环”？

### 模块 3：规划范式（Planner）——ReAct/Plan-Execute/Graph Search

ReAct 是 Agent 面试最常被提到的范式之一：推理与行动交替，减少纯推理的幻觉与误传播 ([arXiv](https://arxiv.org/abs/2210.03629?utm_source=chatgpt.com))。

**必做题**

11) 实现 **ReAct-style**：每轮产出 `Thought(隐藏) / Action(可见) / Observation(可见)`（面试时讲机制即可）
12) 实现 **Plan-and-Execute**：先生成结构化计划（列表/依赖图），再逐步执行
13) 做一个 **计划评审器**：检查是否超预算、是否缺关键工具、是否存在不可执行步骤
14) 做一个 **搜索式规划**（简化版）：beam search / best-first，在多条候选计划里选性价比最高
15) 加 **预算约束**：最大步数、最大工具调用次数、最大 tokens/费用

**验收**

- 同一任务，ReAct vs Plan-Execute 在成功率/步数/成本上有可对比结果。

**面试必问**

- ReAct 为什么有效？它解决了什么问题？([arXiv](https://arxiv.org/abs/2210.03629?utm_source=chatgpt.com))
- 计划先行 vs 边走边想的取舍？何时用哪种？
- 如何避免“规划发散/循环”？你的 stop 条件是什么？
- 预算约束怎么设计？失败时如何降级？

### 模块 4：记忆（Memory）与检索（RAG as a Tool）

即使你简历没写 Agent 项目，面试官也会问：**记忆怎么做、怎么防污染、怎么和 RAG 结合**。

**必做题**

16) 短期记忆：窗口 + 摘要（摘要要有“来源引用/置信度”）
17) 长期记忆：向量库（可直接复用你的 RAG），但要做 **写入门控**（不是啥都记）
18) 记忆检索：按 task type 路由不同 memory（偏好/事实/操作历史）
19) 记忆版本化：可撤销、可过期、可追溯（谁写入、基于什么证据写入）
20) 记忆污染治理：错误信息写入后反复被召回 → 你要能检测并纠正

**验收**

- 记忆不会让错误越滚越大；你能展示“污染案例→检测→纠正→回归验证”。

**面试必问**

- Memory 和 RAG 有啥区别？
- 长期记忆写入策略是什么？（阈值、人工确认、来源可信度）
- 如何避免“越记越乱/隐私泄露”？
- 记忆更新与冲突怎么处理？

### 模块 5：可靠性（Reliability）——自检、反思、恢复

这是“会不会上线”的分水岭。

**必做题**

21) **结果校验器**：对关键输出做约束检查（schema/正则/范围/一致性）
22) **反思/纠错**（Reflexion 思路的工程化版本）：失败后生成“失败原因→修复策略→重试计划”
23) **fallback 策略**：工具不可用→换工具/换检索策略/降低目标/请求澄清
24) **循环检测**：状态 hash + 行为相似度，检测重复动作并强制跳出
25) **测试金字塔**：单元测试（工具）、集成测试（agent flow）、回归测试（失败case库）

**验收**

- 你能把成功率从【x】提升到【y】，并明确提升来自哪些 reliability 组件。

**面试必问**

- Agent 为什么容易失控？你做了哪些 guardrails？([OpenAI Developers](https://developers.openai.com/cookbook/topic/agents/?utm_source=chatgpt.com))
- 如何定义“成功/失败”？如何自动判定？
- 如何处理工具出错、网络抖动、半失败（partial failure）？
- 怎么做回归测试防止改坏？

### 模块 6：安全（Security）——提示注入、越权、工具链风险

Agent 的攻击面比 RAG 更大，因为它能“行动”。最近围绕 MCP/工具链的安全讨论也非常多（包括真实漏洞事件），面试官会顺手加一道。([The Verge](https://www.theverge.com/news/669298/microsoft-windows-ai-foundry-mcp-support?utm_source=chatgpt.com))

**必做题**

26) **权限模型**：每个工具定义 scope；敏感操作必须二次确认（human-in-the-loop）
27) **注入防护**：外部内容（网页/文档/工具输出）一律视为不可信指令；做指令隔离
28) **敏感信息处理**：PII/密钥/Token 永不进入模型上下文；日志脱敏
29) **审计**：每次关键工具调用都可追溯（谁触发、输入、输出、影响面）
30) **红队用例**：写 10 条 prompt injection / tool injection / data exfiltration 的攻击样例并修复

**验收**

- 攻击成功率显著下降，同时误杀率可控；能解释 trade-off。

**面试必问**

- prompt injection 在 Agent 里怎么发生？为什么比纯聊天更危险？
- 为什么“工具输出也可能注入”？你怎么防？
- MCP/工具生态带来哪些新风险？([Model Context Protocol](https://modelcontextprotocol.io/specification/2025-11-25?utm_source=chatgpt.com))

## 0）MVP 目标与边界

### 目标

做一个**可上线风格**的 Agent：能规划、能调用工具、能失败恢复、能回放轨迹、能评测闭环、能做基本安全防护。

### 非目标（先不做也不扣分）

- 多 Agent 协作、复杂 GUI、真实支付/真实删库等高风险动作
- 大规模长时记忆系统（先做“门控写入+可撤销”即可）

------

## 1）系统架构（面试口径）

### 核心组件

1. **Planner**：把目标拆成可执行步骤（结构化 plan）
2. **Executor**：按状态机执行步骤，调用工具，更新状态
3. **Tool Layer**：schema 校验、超时、重试、幂等、熔断、输出校验
4. **Memory**：短期（窗口/摘要）+ 长期（向量库/kv），带写入门控
5. **Guardrails**：注入/越权/敏感信息/高风险动作的人审
6. **Evaluator**：任务集 + 指标 + 报告 + 回归测试

### 状态机（推荐）

```
INIT → PLAN → (ACT→OBSERVE→VALIDATE→UPDATE)* → FINISH / FAILSAFE
```

面试一句话：

> “我不是 while-loop 乱跑，我是状态机可控编排：每步都有输入、工具调用、校验、失败恢复与可回放 trace。”

## 2）工具列表（MVP 必须有的 6 个工具）

工具不用接真实外部系统也行，**先做本地/模拟**，关键是工程语义完整：schema/权限/超时/重试/审计。

### Tool A：`kb_search`

- **功能**：对本地知识库/文档做检索（你可复用 RAG：embedding + ANN + rerank 也行）
- **输入 schema**：`query: str, top_k: int(1..20), filters?: {source, time_range, tags}`
- **输出**：`hits: [{doc_id, chunk_id, text, score, metadata}]`
- **面试可讲点**：Agent 把 RAG 当工具；何时检索/何时不检索；如何做引用与可追溯

### Tool B：`calc`

- **功能**：安全计算器（只允许白名单表达式，禁止 eval 任意代码）
- **输入**：`expression: str`
- **输出**：`value: number, steps?: str`
- **讲点**：工具输出也要校验；错误要可恢复

### Tool C：`todo_store`

- **功能**：读写一个 TODO/任务列表（本地 JSON）
- **输入**：`action: add/list/done, item?: {title, due, tags}`
- **输出**：`items: [...]`
- **讲点**：持久化状态、断点续跑、幂等写入（idempotency_key）

### Tool D：`web_fetch`（可选但加分）

- **功能**：抓取网页文本（MVP 可用固定白名单域名或直接 mock）
- **输入**：`url: str, mode: text_only`
- **输出**：`content: str, title?: str`
- **讲点**：外部内容=不可信输入→注入防护（“内容不可执行”）

### Tool E：`file_db`

- **功能**：本地文件读写（限制目录、只读优先）
- **输入**：`op: read/write/list, path: str, content?: str`
- **输出**：`content/paths`
- **讲点**：权限控制、路径白名单、防越权

### Tool F：`policy_check`

- **功能**：规则/轻量模型做安全检查（注入、PII、越权意图）
- **输入**：`text: str, context?: {tool, user_role}`
- **输出**：`flags: [INJECTION/PII/…], severity: low/med/high, rationale`
- **讲点**：Guardrails 不靠一句 prompt，而是“前置检测 + 执行门控 + 审计”

> MVP 工具数量控制在 6 个以内，面试讲起来清晰；但每个工具都要“像真的能上线”。

## 3）工具协议与执行器规范（你实现时照这个写）

### 3.1 ToolSpec（每个工具都必须有）

- `name`
- `description`
- `input_schema`（JSON Schema）
- `output_schema`
- `timeout_ms`
- `retry_policy`（max_retries, backoff）
- `rate_limit`（可选）
- `required_scope`（权限：read/write/admin）
- `idempotent`（是否幂等；写操作必须支持 `idempotency_key`）

### 3.2 ToolExecutor（必须实现的能力）

- **输入校验**：schema 不过就拒绝（不调用工具）
- **超时**：超时返回可恢复错误
- **重试**：仅对可重试错误（timeout / 502 / rate limit）重试
- **幂等**：写工具必须带 `idempotency_key`；重试不重复写
- **输出校验**：返回结构不对→标记工具不可信并走 fallback
- **审计日志**：每次调用记录 trace_id、参数摘要、耗时、错误码

## 6）Guardrails 与人审门控（MVP 的“上线感”来源）

### 6.1 风险分级（每个 plan step 都标 risk_level）

- `low`：读取、计算、检索
- `med`：写入 todo、写文件（非敏感路径）
- `high`：删除、覆盖、发外部请求、涉及权限/隐私（MVP 直接 require human confirm 或禁用）

### 6.2 必做门控

- **任何外部内容**（web_fetch、kb_search 命中内容、工具返回）→ 先 `policy_check`
- **任何写操作**（todo_store add/done、file_db write）→ 先检查 scope + `idempotency_key`
- **任何 high risk** → `AGENT_CONFIRMATION_REQUIRED`

# 问题与回答

## 一、Agent 基础认知

### 1. 概念与边界

#### 什么是 Agent？
**Agent（智能体）** 是一个能够**自主感知环境、进行推理决策、并执行行动**以完成特定目标的软件实体。在人工智能领域，Agent 通常指基于大语言模型（LLM）构建的系统，它能够**理解用户意图、制定计划、调用外部工具、执行操作**，并在执行过程中根据反馈自我调整，最终达成目标。

```python
Agent = LLM（推理核心）+ 工具（行动能力）+ 记忆（状态维护）+ 规划（任务分解）
        ↓           ↓            ↓            ↓
      思考"做什么"   执行"怎么做"   记住"做过什么"  拆解"复杂任务"
```

#### Agent 和普通 Chatbot 的区别是什么？
| 维度         | Chatbot                      | Agent                                  |
| ------------ | ---------------------------- | -------------------------------------- |
| **交互模式** | 被动响应，单轮或简单多轮对话 | 主动规划，可执行复杂任务流             |
| **能力边界** | 仅生成文本回答               | 可调用工具（API、数据库、代码执行等）  |
| **决策方式** | 无自主决策，依赖预设回复逻辑 | 具备推理、规划、反思能力，动态选择行动 |
| **目标导向** | 回答用户问题                 | 完成用户指定的任务（如订票、分析数据） |
| **闭环程度** | 开环（输出即结束）           | 闭环（行动→观察→调整→再行动）          |

#### Agent 和 Workflow 的区别是什么？
| 维度         | Workflow                       | Agent                                  |
| ------------ | ------------------------------ | -------------------------------------- |
| **路径确定** | 固定流程，分支由规则预定义     | 动态路径，由模型根据上下文实时决策     |
| **适应性**   | 不适应意外情况，超出规则即失败 | 能处理不确定性，可自我纠错             |
| **控制方式** | 硬编码或低代码编排             | 模型驱动，无需预先定义所有步骤         |
| **典型场景** | 数据 ETL、审批流程             | 开放任务如“帮我研究这个主题并生成报告” |

Workflow 适合确定性、重复性任务；Agent 适合开放、动态、需要推理的复杂任务。

```python
Workflow：if A then B else C（人规定所有分支）
Agent：   观察 → 思考 → 行动 → 再观察（自主循环）
```

#### Agent 和 RAG 的区别与联系是什么？
- **RAG（检索增强生成）** 是一种**能力模块**，专注于“检索外部知识 + 生成回答”，本身不包含决策、规划或行动执行。
- **Agent** 是一个**任务执行框架**，可以**调用包括 RAG 在内的多种能力**（搜索、计算、代码执行、工具调用等），并根据目标自主编排这些能力。

**联系**：RAG 常常作为 Agent 的一个核心组件，为 Agent 提供实时外部知识。Agent 可以在需要时动态决定是否使用 RAG，以及如何使用。

#### 为什么说 RAG 是能力模块，而 Agent 是任务执行框架？
- **RAG** 解决的是“如何获取知识”这一单一问题，它包含检索器、嵌入模型、向量库等组件，输入查询，输出增强后的上下文。它是一个相对标准化的组件，可以被其他系统调用。
- **Agent** 解决的是“如何自主完成一个开放任务”，它需要整合规划、记忆、工具调用、执行反馈等多个模块，是一个完整的架构范式。Agent 可以内置 RAG 作为知识获取工具，但它的核心是决策与行动循环。

#### 什么任务适合做成 Agent，什么任务不适合？
| 适合 Agent 的任务                            | 不适合 Agent 的任务                      |
| -------------------------------------------- | ---------------------------------------- |
| 多步骤、依赖外部工具（如预订行程、数据分析） | 简单事实问答（可用 RAG 直接解决）        |
| 需要根据中间结果调整策略（如研究一个主题）   | 确定性、重复性操作（用 Workflow 更高效） |
| 开放领域、目标模糊（如“帮我策划一个活动”）   | 对成本、延迟、可解释性要求极高的场景     |
| 需要与外部系统交互（调用 API、操作数据库）   | 完全可在模型内部完成的任务               |

#### 为什么不是所有场景都应该 Agent 化？
- **成本高**：Agent 多次调用 LLM（规划、反思、工具调用），token 消耗大，延迟高。
- **可靠性低**：模型自主决策可能出错，需设计 fallback，增加复杂度。
- **过度设计**：简单任务用 Agent 反而降低效率，不如硬编码或固定工作流。
- **可解释性差**：Agent 决策路径复杂，难以调试和审计。

#### 单轮 Agent 和多轮 Agent 的区别是什么？
- **单轮 Agent**：接收一次输入，执行一系列行动后直接输出结果，不保留中间状态（如一次性调用工具生成报告）。常见于一次性任务。
- **多轮 Agent**：支持持续对话，维护对话历史、记忆、计划状态，可根据用户后续输入调整行动（如“帮我看机票” → “再筛选一下早班机”）。具备更复杂的状态管理。

**多轮 Agent 的核心挑战**：

- **状态管理**：记忆不会无限增长，需压缩、摘要、遗忘
- **错误累积**：早期错误导致后续偏离，需自我修正机制
- **用户介入**：何时让用户确认，何时自主执行
- **终止条件**：怎么知道"做完了"？

#### 开环系统和闭环系统的区别是什么？
- **开环系统**：一次性执行，不根据反馈调整。例如：简单 Chatbot 输出答案后即结束。
- **闭环系统**：形成“行动 → 观察 → 评估 → 调整行动”的循环，能够自我纠错、持续优化。Agent 本质是闭环系统，它能在执行过程中感知结果，决定下一步动作。

#### Agent 的最小工作闭环是什么？
```
感知（用户输入/环境状态）
   ↓
规划（拆解目标、选择工具）
   ↓
行动（调用工具、生成输出）
   ↓
观察（获取行动结果）
   ↓
反思（评估是否达成目标，决定继续或结束）
```
这个循环反复进行，直到任务完成或主动停止。

### 2. 高频追问

#### 你如何用一句话定义 Agent？
**Agent 是一个能够自主规划行动、调用工具、并在执行中自我纠错以完成复杂目标的智能系统。**

#### 你觉得 Agent 的核心不是“会调用工具”，而是什么？
Agent 的核心是**自主决策与目标驱动的行动闭环**。工具调用只是手段，真正区分 Agent 的是它能否根据目标自主规划行动序列、在遇到障碍时调整策略、并在执行过程中保持对最终目标的跟踪。一个没有工具调用的系统，只要具备规划、反思、状态管理能力，仍然可以称为 Agent（如简单的计划执行器）；反之，一个只会机械调用工具的系统，如果没有决策能力，只能算工具调用器。

#### 一个系统只要用了 function calling，就一定算 Agent 吗？
**不一定。** Function calling 只是工具调用的实现方式。如果系统仅根据用户指令直接调用一个工具，没有规划、反思、多步决策，那它只是“工具增强的 Chatbot”。Agent 强调**自主性**和**目标导向的闭环**，function calling 可以是它的一个能力，但非充分条件。

#### 如果一个系统只有固定分支判断，没有动态决策，它算 Agent 吗？
**不算。** 固定分支判断属于 Workflow 或决策树，其路径在开发时已完全确定，系统不会根据中间结果动态调整。Agent 必须具有基于模型推理的动态决策能力，能够应对未知情况，并在执行中修正路径。

#### 为什么“可执行性”是 Agent 和普通对话系统的重要分界线？
普通对话系统只输出文本，不产生实际影响；而 Agent 的最终输出可以是**可执行的操作**（如发送邮件、创建工单、执行代码、修改数据库），这些操作会改变外部世界状态。具备“可执行性”意味着 Agent 不仅理解意图，还能**真正完成任务**，而不仅仅是“告诉用户怎么做”。这是 Agent 从“对话”走向“行动”的关键跃迁。

| 问题                  | 一句话答案                              |
| --------------------- | --------------------------------------- |
| Agent vs Chatbot      | Chatbot 说，Agent 做                    |
| Agent vs Workflow     | Workflow 预定义，Agent 动态决策         |
| Agent vs RAG          | RAG 是工具，Agent 是框架                |
| Agent 核心能力        | 自主决策、闭环执行、工具编排            |
| 最小工作闭环          | Thought → Action → Observation → Memory |
| 为什么不是全 Agent 化 | 成本、延迟、确定性、安全约束            |

## 二、Agent 核心组成

### 1. 基本模块

#### 1.1 一个 Agent 系统通常由哪些模块组成？
一个完整的 Agent 系统通常包含以下核心模块：
- **目标（Goal）**：明确任务要达成的最终状态或结果。
- **状态（State）**：记录当前环境、历史交互、中间结果等信息。
- **策略（Policy/Planner）**：决定下一步行动的逻辑，可以是规则、模型或两者结合。
- **工具（Tools）**：Agent 可调用的外部能力，如 API、数据库、代码执行器、搜索引擎等。
- **记忆（Memory）**：存储短期上下文和长期知识，支持持续学习和多轮交互。
- **反馈（Feedback）**：环境或用户对行动的响应，用于评估和调整后续行为。

```python
┌─────────────────────────────────────────┐
│           Agent 系统架构                  │
├─────────────────────────────────────────┤
│  1. 感知模块 (Perception)                │
│     └─ 接收用户输入、环境观察、工具返回      │
├─────────────────────────────────────────┤
│  2. 记忆模块 (Memory)                    │
│     └─ 短期记忆（上下文）、长期记忆（知识库）  │
├─────────────────────────────────────────┤
│  3. 规划模块 (Planning)                  │
│     └─ 任务分解、策略制定、路径优化          │
├─────────────────────────────────────────┤
│  4. 推理模块 (Reasoning)                 │
│     └─ LLM 核心、决策生成、下一步行动判断     │
├─────────────────────────────────────────┤
│  5. 工具模块 (Tools/Action)              │
│     └─ 外部 API、代码执行、数据库操作等        │
├─────────────────────────────────────────┤
│  6. 反馈模块 (Feedback/Reflection)       │
│     └─ 结果评估、错误修正、自我改进          │
└─────────────────────────────────────────┘
```

#### 1.2 目标、状态、策略、工具、记忆、反馈分别起什么作用？

- **目标**：定义任务终点，是 Agent 决策的“锚点”。所有规划、行动都围绕达成目标展开。
- **状态**：保存 Agent 对当前世界的认知，包括环境信息、历史操作、中间结果。状态决定了策略的输入。
- **策略**：决定“下一步做什么”。它根据目标和当前状态，选择调用哪个工具、生成什么内容、或调整计划。
- **工具**：扩展 Agent 的能力边界，使其能执行实际动作（如搜索、计算、发送请求）。没有工具，Agent 只能“说”不能“做”。
- **记忆**：解决状态容量的限制。短期记忆用于维护对话上下文和任务进度；长期记忆用于存储经验、知识或用户偏好。
- **反馈**：提供执行结果或环境变化，使 Agent 能自我评估，判断行动是否有效，并据此修正后续动作。

#### 1.3 为什么 state 对 Agent 很重要？
状态是 Agent 决策的“上下文窗口”。没有状态，Agent 无法知道当前进度、已尝试过的失败路径、用户历史输入。状态决定了 Agent 能否从错误中恢复，能否保持多轮对话的一致性，能否完成复杂任务链。良好的状态设计能让 Agent 在长时间运行中保持“记忆”和“清醒”。

#### 1.4 为什么工具对 Agent 很重要？
工具是 Agent 从“理解”到“执行”的桥梁。Agent 的最终价值在于完成真实任务，而不仅仅是输出文本。工具让 Agent 能操作外部世界（发送邮件、查询数据库、控制设备），从而产生实际影响。同时，工具也扩展了 Agent 的能力边界，使其能处理超越语言模型本身知识范围的问题。

#### 1.5 为什么 memory 对 Agent 很重要？
记忆解决了状态容量的限制（如 LLM 上下文窗口有限）和持久化问题。短期记忆让 Agent 能跟踪多轮对话和任务步骤；长期记忆让 Agent 能记住用户偏好、过往成功经验，实现个性化服务和持续学习。没有记忆，Agent 会“失忆”，每次交互都像第一次见面，无法积累。

| 场景       | 记忆作用                         | 无记忆后果               |
| ---------- | -------------------------------- | ------------------------ |
| 多轮对话   | 理解指代消解，"刚才说的那个"     | 每轮独立，用户需重复背景 |
| 跨会话服务 | "像上次一样帮我订机票"           | 完全失忆，无法个性化     |
| 长文档处理 | 第 10 页的内容影响第 50 页的理解 | 上下文截断，前后矛盾     |
| 错误避免   | "上次这个方法失败了，换另一种"   | 重复踩坑，无法学习       |

#### 1.6 为什么 planning 对复杂任务很重要？
复杂任务通常包含多个子任务、依赖关系、不确定性。如果没有规划，Agent 容易陷入“贪心”行动（只关注眼前），导致步骤混乱、重复或遗漏。规划能力让 Agent 能预先拆解目标、安排执行顺序、预见可能的障碍，从而提高任务完成率和效率。

#### 1.7 observation 在 Agent 中是什么意思？
Observation 是 Agent 对环境或工具执行结果的“感知”。它可能是工具返回的数据、API 调用的响应、用户新输入，或环境状态的改变。Agent 通过观察获取反馈，判断行动是否成功，并决定下一步。没有观察，闭环就无法形成。

#### 1.8 success condition 和 stop condition 分别是什么？
- **Success condition**：达成目标的条件。例如“成功预订机票”可能是“返回确认号”。Agent 会持续行动直到满足该条件。
- **Stop condition**：强制终止的条件，无论目标是否达成。例如达到最大步数、用户主动打断、出现致命错误等。它保证 Agent 不会无限循环或消耗过多资源。

### 2. 高频追问

#### 2.1 如果没有 memory，Agent 还能工作吗？
可以，但只能处理单轮、无状态任务。例如一次性的工具调用（“帮我查一下天气”）。但对于多轮交互、需要上下文的任务（如“帮我订票，我再说日期”）就会失败。没有记忆的 Agent 本质上退化为无状态的函数调用器。

#### 2.2 如果没有 planning，Agent 会出现什么问题？
Agent 会变得短视，只能执行线性、预先设定的步骤，无法处理分支和依赖。例如面对“组织一次会议”的任务，没有规划可能先发邀请再订会议室，结果发现会议室已满，导致失败。规划缺失时，Agent 往往需要依赖人工预设的工作流，失去自主性。

#### 2.3 如果没有 observation，Agent 还能称为闭环吗？
不能。闭环的核心是“行动 → 观察 → 调整”。没有观察，Agent 无法知道行动结果，只能盲目执行，无法纠错或适应环境变化。这样的系统是开环的，更像一次性脚本。

#### 2.4 如果 state 设计不好，会带来哪些连锁问题？
- **信息丢失**：重要上下文被遗忘，导致决策错误。
- **状态爆炸**：存储无关信息，浪费 token 和内存。
- **推理混乱**：状态中混入噪声，干扰模型判断。
- **可扩展性差**：难以添加新功能或维护。
- **调试困难**：状态不可回溯，问题难以定位。

#### 2.5 工具很多一定更好吗？为什么？
不一定。工具过多会带来：
- **选择困难**：模型可能选错工具，增加决策开销。
- **上下文膨胀**：工具描述占用 prompt，减少有效信息。
- **安全风险**：更多工具意味着更多攻击面。
- **维护成本**：工具需持续更新和测试。

好的工具设计应遵循“最小必要”原则，根据任务域选择最精简、最可靠的工具集，并对工具进行清晰的描述和权限控制。

## 三、任务理解与目标建模

### 1. 任务理解

#### 1.1 Agent 如何从用户输入中抽取目标、约束和成功条件？
Agent 通常使用以下组合方式：
- **基于 LLM 的意图解析**：通过提示词要求模型输出结构化目标（如 JSON），明确任务类型、关键实体、约束条件。
- **实体识别与约束提取**：利用 NER 或正则识别时间、地点、金额等约束，并区分“硬约束”（必须满足）和“软约束”（尽量满足）。
- **成功条件推导**：根据任务类型预设成功模板，例如“订票”的成功条件可能是“生成订单号”；“查询”的成功条件可能是“返回有效结果”。
- **多轮澄清**：当信息不足时，通过追问补充必要信息，确保目标完整。

**三层抽取架构**：

```
┌─────────────────────────────────────────┐
│  原始输入："帮我下周去北京出差，预算3000，要住得舒服点" │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  第一层：意图识别（Intent Classification） │
│  └─ 类型：任务执行类（非闲聊/查询）          │
│  └─ 领域：差旅预订                          │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  第二层：槽位填充（Slot Filling）           │
│  ├─ 目标：安排北京出差行程                   │
│  ├─ 时间约束：下周（需解析为具体日期）        │
│  ├─ 预算约束：3000元                         │
│  ├─ 偏好约束：住宿舒适度高                     │
│  └─ 隐含需求：交通、住宿、可能需报销凭证       │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│  第三层：成功条件生成（Success Criteria）    │
│  ├─ 必须：行程在下周、总费用≤3000、有住宿      │
│  ├─ 偏好：酒店评分≥4.5、交通便利              │
│  └─ 交付：完整行程单+预订确认+发票            │
└─────────────────────────────────────────┘
```

**技术实现**：

| 方法                       | 适用场景             | 实现方式                      |
| -------------------------- | -------------------- | ----------------------------- |
| **结构化抽取（NER+意图）** | 限定域、高频任务     | BERT-CRF、UIE、GPT 结构化输出 |
| **Prompt 工程**            | 开放域、快速迭代     | Few-shot 示例 + JSON 格式约束 |
| **微调专用模型**           | 复杂领域、高精度要求 | 领域数据微调 T5/LLaMA         |
| **对话澄清**               | 信息缺失、歧义严重   | 主动询问，多轮交互补全        |

**Prompt 示例（GPT-4 结构化抽取）**：

```python
extraction_prompt = """
从用户输入中提取任务要素，按 JSON 格式返回：

用户输入：{user_input}

输出格式：
{
    "goal": {
        "primary": "主要目标（动词+宾语）",
        "type": "information_query | action_execution | creative_generation",
        "urgency": "low/medium/high"
    },
    "constraints": {
        "hard": [{"type": "time/budget/permission/format", "value": "..."}],
        "soft": [{"type": "preference", "value": "...", "weight": 0.8}]
    },
    "success_criteria": [
        "可验证的完成标准1",
        "可验证的完成标准2"
    ],
    "missing_info": ["需要澄清的缺失信息"],
    "conflicts": ["检测到的潜在冲突"]
}

规则：
- hard 约束必须满足，否则任务失败
- soft 约束尽量满足，用于权衡选择
- success_criteria 必须可客观验证
"""

response = llm.generate(extraction_prompt)
task_spec = json.loads(response)
```

#### 1.2 用户问题模糊时，Agent 应该直接执行还是先澄清？
**先澄清，但需平衡**。模糊问题直接执行容易出错或产生无效结果。Agent 应主动提出澄清性问题，列出可能理解的选项，让用户确认。但若用户明确表示“就这样做”或上下文已明确，则可在风险可控时直接执行并告知用户可后续调整。关键原则：**不确定性高、影响大的操作必须先澄清；低风险、可撤销的操作可尝试执行并允许撤回**。

#### 1.3 如何判断用户输入是“信息查询任务”还是“操作执行任务”？
- **信息查询**：用户目的是获取知识、数据或建议，无需改变外部状态。典型关键词：什么、为什么、怎么、查找、解释。
- **操作执行**：用户意图是让系统代表自己完成一个动作，改变现实世界状态。典型关键词：帮我…、设置、发送、创建、删除、预订。
- 可通过意图分类模型或提示词判断，也可结合工具定义：若任务对应可写操作（如 API 写入），则为操作；若仅为只读查询，则为信息查询。

#### 1.4 如何区分主目标和子目标？
- **主目标**：用户最终想要达成的结果，通常由任务根节点表达。
- **子目标**：为达成主目标必须完成的中间步骤，如“订票”包含“查询航班”“选择座位”“支付”等子目标。
- 区分方法：使用任务分解模型（如 LLM 的 CoT）将复杂任务拆解为 DAG 依赖图，根节点为主目标，叶子节点为可执行原子任务。子目标通常依赖主目标的存在，且无法独立满足用户原始意图。

#### 1.5 如何识别隐含约束，比如时间、预算、权限、格式要求？
隐含约束常隐藏在语境、历史或常识中。识别方法：
- **时间约束**：如“下周”、“尽快” → 需要转化为具体时间范围。
- **预算约束**：如“性价比高”、“控制在500以内”。
- **权限约束**：如“我能访问的吗”、“内部文档”。
- **格式要求**：如“用表格”、“要邮件正文”。
- 通过 LLM 抽取这些隐含信息，并在状态中标记为约束；若无法确定，可在执行前向用户确认。

#### 1.6 用户给出的目标本身不合理时怎么办？
- **检测不合理**：通过与常识、规则库、可用资源比对，识别矛盾或不可行目标（如“1小时内完成跨国出差往返”）。
- **反馈策略**：礼貌告知用户不合理之处，说明原因，并提供替代建议或请求调整。
- **不可妥协**：若目标违反安全、法律或基本逻辑，应明确拒绝并说明原因。

| 不合理类型     | 示例                         | 检测方法                 | 处理策略                     |
| -------------- | ---------------------------- | ------------------------ | ---------------------------- |
| **资源不可行** | "1万元买北京二环房"          | 知识库查询、数值范围检查 | 明确告知不可行，提供替代方案 |
| **逻辑矛盾**   | "明天之前完成需要一周的任务" | 时间计算、依赖分析       | 指出矛盾，协商调整           |
| **权限不足**   | "查看 CEO 的邮件"            | RBAC 校验                | 拒绝并解释权限边界           |
| **违反合规**   | "帮我伪造发票"               | 敏感词+规则库            | 明确拒绝，记录审计           |
| **信息不全**   | "订个票"（缺目的地）         | 必填字段检查             | 询问补全                     |
| **目标模糊**   | "弄个好东西"                 | 语义模糊度检测           | 澄清具体需求                 |

#### 1.7 用户在执行过程中修改目标怎么办？
Agent 需支持**动态目标更新**：
- 将新目标与当前进度比较，判断是追加、替换还是调整约束。
- 若未开始相关步骤，可直接更新目标。
- 若已执行部分步骤，需评估已执行工作与新目标的兼容性：可复用则继续；冲突则询问用户是否回退或继续。
- 建议设计“任务快照”机制，允许回滚到目标变更前的状态。

### 2. 高频追问

#### 2.1 你会如何给 Agent 设计 success criteria？
成功条件应满足 **SMART** 原则（具体、可度量、可达成、相关、有时限）。设计方法：
- 为每个任务定义可验证的状态：例如“邮件发送成功” → 返回 API 成功码；“查询完成” → 结果集非空。
- 使用布尔表达式组合：如“订单已支付且收到确认邮件”。
- 提供超时机制和失败条件，避免无限等待。
- 允许用户自定义成功条件（如“按我给的格式整理好”）。

| 原则                   | 说明             | 反例→正例                        |
| ---------------------- | ---------------- | -------------------------------- |
| **S**pecific（具体）   | 明确无歧义       | "做好"→"生成包含5个维度的对比表" |
| **M**easurable（可测） | 能量化验证       | "满意"→"用户评分≥4星"            |
| **A**chievable（可行） | 资源范围内可完成 | "1小时写完博士论文"→"完成大纲"   |
| **R**elevant（相关）   | 与主目标直接关联 | 避免无关指标                     |
| **T**ime-bound（限时） | 有截止时间       | "尽快"→"24小时内"                |
| **C**heckable（可检）  | 有明确验收方式   | 自动化测试或人工确认             |

**分层设计**：

```python
success_criteria = {
    "hard_constraints": [  # 必须全部满足
        {"metric": "budget", "condition": "<=", "value": 3000},
        {"metric": "deadline", "condition": "<=", "value": "2024-04-01T18:00:00Z"},
        {"metric": "completeness", "condition": ">=", "value": 0.9}  # 核心项完成率
    ],
    "soft_constraints": [  # 加权优化
        {"metric": "comfort_score", "weight": 0.4, "target": "maximize"},
        {"metric": "convenience_score", "weight": 0.3, "target": "maximize"},
        {"metric": "cost_efficiency", "weight": 0.3, "target": "maximize"}
    ],
    "validation_method": {  # 验证方式
        "automated": ["budget_check", "deadline_check"],
        "manual": ["user_confirmation", "quality_review"]
    },
    "termination_conditions": {
        "success": "hard_constraints 全部满足",
        "good_enough": "加权得分>0.8 且 无硬约束违反",
        "failure": "任一硬约束违反 或 超时"
    }
}
```

#### 2.2 为什么成功条件不明确会导致 Agent 反复兜圈子？
**缺乏明确成功条件**时，Agent 无法判断何时停止，可能不断尝试相似操作（如反复搜索、重试），造成资源浪费和用户体验下降。例如，若未定义“已找到答案”，Agent 可能一直输出“我再查一下”，陷入无限循环。明确成功条件是闭环终止的必要条件。

#### 2.3 如果用户目标本身是冲突的，系统如何处理？
例如“给我订最便宜的头等舱”。处理方式：
- **冲突检测**：通过领域知识或约束求解发现矛盾。
- **优先级排序**：要求用户明确哪个约束更重要，或系统按默认优先级（如安全 > 合规 > 成本 > 效率）选择可行方案。
- **折中建议**：提供多个妥协方案，让用户选择（如“没有最便宜的头等舱，是否接受经济舱？”）。
- **拒绝执行**：若无法调和，明确告知用户并请求调整。

#### 2.4 “帮我整理一下资料”和“帮我发出去”在系统设计上有什么本质差别？
- **“整理资料”**：是信息处理任务，主要涉及数据筛选、格式化、摘要生成，不涉及外部写操作，通常只需与知识库、文件系统交互，属“读”类任务。
- **“帮我发出去”**：是操作执行任务，涉及对外部系统的写操作（如邮件发送、文件传输），需要权限校验、日志记录、结果反馈，且有不可逆风险。
- 系统设计差异：前者更注重数据处理精度；后者更注重安全性、可追溯性、错误恢复机制。

#### 2.5 用户意图识别错误会如何传导到后续模块？
意图错误是上游问题，会像“蝴蝶效应”一样影响整个系统：
- **规划模块**：可能选择错误工具或拆解出无关子任务。
- **工具调用**：调用不必要或不正确的 API，浪费资源甚至造成不良后果。
- **记忆模块**：存储错误上下文，导致后续交互持续偏离。
- **反馈与反思**：基于错误假设的评估可能误判成功或失败。
- **最终结果**：输出与用户期望完全不符，甚至造成数据错误或安全事故。

因此，Agent 设计必须包含意图确认环节（如追问、摘要确认），并在执行关键操作前与用户二次确认。

| 问题             | 核心要点                                     |
| ---------------- | -------------------------------------------- |
| 目标抽取三层     | 意图识别 → 槽位填充 → 成功条件生成           |
| 模糊处理策略     | 关键信息必须澄清，可伸缩任务边执行边确认     |
| 查询 vs 执行判别 | 动词特征、副作用、可逆性、确认需求           |
| 隐含约束来源     | 时间词、用户画像、业务规则、上下文推断       |
| 目标变更处理     | 影响评估 → 状态调整 → 优雅迁移               |
| 成功条件设计     | SMART-C 原则，可自我验证，明确终止信号       |
| 冲突解决策略     | 优先级仲裁、帕累托优化、约束松弛、分阶段执行 |
| 意图错误传导     | 早期错误低成本，执行后高成本，需多层防御     |

## 四、状态 State 与上下文管理

### 1. State 设计

#### 1.1 Agent 的 state 一般包含哪些内容？
Agent 的 state 是系统在当前时刻对世界的完整认知记录，通常包括：
- **用户输入与意图**：原始问题、解析后的目标、约束、成功条件。
- **任务进度**：当前执行到哪个子任务、已完成步骤、待办列表。
- **中间结果**：各工具调用的返回数据、推理中间结论。
- **历史交互**：对话轮次、用户反馈、Agent 已做出的行动。
- **环境快照**：关键外部状态（如页面URL、文件列表、当前时间等）。
- **元信息**：任务开始时间、已消耗资源、重试次数等。

#### 1.2 当前任务状态和长期用户记忆应该如何区分？
- **当前任务状态**：仅针对本次会话的瞬时信息，如当前任务拆解、临时变量、未完成的步骤，通常在一次会话结束后可丢弃或摘要后归档。
- **长期用户记忆**：跨会话保留的用户偏好、历史行为模式、个人知识库、重要事件等，需持久化存储，用于个性化服务和持续学习。
- 区分方式：通过存储位置（短期内存 vs 数据库）、生命周期（会话级 vs 永久级）和更新策略（每次会话独立 vs 累积更新）来分离。

```python
┌─────────────────────────────────────────┐
│  短期记忆 (Working Memory)                │
│  ├─ 存储：当前任务 State（L1-L5）          │
│  ├─ 介质：内存（Redis/Memory）              │
│  ├─ 生命周期：任务期间（分钟-小时级）        │
│  ├─ 访问延迟：<10ms                        │
│  └─ 容量限制：受上下文窗口约束               │
├─────────────────────────────────────────┤
│  中期记忆 (Session Memory)                │
│  ├─ 存储：会话历史、跨任务上下文             │
│  ├─ 介质：数据库（PostgreSQL/MongoDB）       │
│  ├─ 生命周期：会话期间（小时-天级）           │
│  ├─ 访问延迟：<100ms                       │
│  └─ 容量：MB 级，结构化存储                 │
├─────────────────────────────────────────┤
│  长期记忆 (Long-term Memory)              │
│  ├─ 存储：用户画像、偏好、历史模式            │
│  ├─ 介质：向量数据库 + 知识图谱              │
│  ├─ 生命周期：永久（需持续更新）              │
│  ├─ 访问延迟：100-500ms（检索+重排序）       │
│  └─ 容量：GB-TB 级，需索引优化               │
└─────────────────────────────────────────┘
```

#### 1.3 中间推理结果是否应该写入 state？
**应该写入**。中间推理结果（如“用户想订明天去北京的机票”）是后续行动的重要依据，写入 state 能避免重复计算，保证决策链完整。但需注意：
- 只保留必要推理结论，避免冗长推理链。
- 可标记推理来源（如“来自工具A”），便于追溯。
- 若推理结果可能被后续证据推翻，应保留置信度或更新机制。

#### 1.4 工具调用历史是否应该进入 state？
**必须进入**。工具调用历史是闭环中的“观察”部分，记录了执行了什么、返回了什么、是否成功。它帮助 Agent：
- 避免重复调用相同工具。
- 根据返回结果调整后续行动。
- 提供反思和错误恢复的依据。
- 支持用户追问“你刚才做了什么”。

建议以结构化方式存储（如列表），包含工具名、参数、返回结果、时间戳、状态（成功/失败）。

#### 1.5 state 太大有什么问题？
- **上下文溢出**：若 state 用于 LLM 输入，会超出 token 限制，导致截断或高成本。
- **推理噪音**：无关信息干扰模型，降低决策质量。
- **响应延迟**：序列化、传输、解析大 state 耗时。
- **存储成本**：内存或数据库压力增加。
- **维护困难**：调试、更新、同步更复杂。

#### 1.6 如何控制 state 的大小与信息密度？
- **摘要压缩**：将长对话历史、工具返回结果用 LLM 摘要为关键点。
- **分层存储**：高频使用的核心信息放短时 memory，低频或历史信息放长期 memory，按需加载。
- **滑动窗口**：只保留最近 N 轮交互或 K 步工具调用。
- **字段裁剪**：丢弃冗余字段（如工具返回的全量数据，只保留必要字段）。
- **重要性评分**：为信息分配权重，优先保留高价值信息。

#### 1.7 如何避免 state 污染？
State 污染指无关、错误或过时信息影响决策。防范措施：
- **明确来源标注**：每条信息注明来源（用户、工具、推理），便于追溯和信任评估。
- **定期清理**：删除已完成子任务相关的临时变量。
- **冲突检测**：当新旧信息矛盾时，标记冲突并触发澄清。
- **权限隔离**：不同模块只访问自己需要的 state 子集，避免相互污染。
- **校验机制**：对工具返回结果进行 schema 校验，过滤异常数据。

#### 1.8 如何处理过时状态、脏状态和冲突状态？
- **过时状态**：当外部环境变化（如时间流逝、数据更新），标记旧状态为“可能过时”，并在使用时重新验证。
- **脏状态**：指未同步的最新状态（如用户修改了目标但 state 未更新）。通过事件监听或显式更新接口确保状态一致性。
- **冲突状态**：如两个工具返回矛盾结果。可采用投票、优先级、或向用户澄清的方式解决，并在 state 中记录冲突标记。

### 2. 高频追问

#### 2.1 为什么很多 Agent 失败不是因为模型不够强，而是因为 state 管理混乱？
因为 state 是 Agent 的“工作记忆”，混乱的 state 会导致：
- 模型无法获得正确的上下文，即使模型本身很强，也会基于错误或缺失信息做出错误决策。
- 重复调用同一工具，浪费资源和时间。
- 无法从错误中恢复（因为丢失了失败记录）。
- 在多轮交互中“忘记”之前达成的共识，用户感到困惑。
- 最终表现为任务失败、无限循环或答非所问，而这些往往源于 state 设计缺陷，而非模型能力。

#### 2.2 多轮任务中，哪些信息必须保留，哪些可以摘要？
**必须保留**：
- 用户明确给出的约束和目标。
- 已完成的子任务及其结果。
- 未完成的任务列表和当前步骤。
- 关键工具调用结果（如订单号、确认信息）。
- 用户最近的反馈和确认。

**可以摘要**：
- 早期对话中的冗余阐述。
- 长工具返回结果中非关键字段。
- 已经执行过且不再需要的中间推理过程。
- 历史状态中的非必要上下文。

#### 2.3 state summary 会带来什么信息损失？
- **细节丢失**：摘要可能省略某些细节，导致后续决策缺乏依据。
- **歧义引入**：摘要可能改变原意，造成误解。
- **因果关系断裂**：省略的步骤可能隐含关键逻辑，影响推理。
- **引用困难**：无法精确定位信息来源，影响可解释性。

为减少损失，摘要应保留关键实体、关系、动作和结果，并尽可能保留原始引用的ID，允许需要时展开。

#### 2.4 如何保证状态更新的一致性？
- **原子操作**：状态更新应作为一个原子事务，要么全成功，要么全回滚。
- **版本控制**：为 state 增加版本号或时间戳，更新时检查版本，防止并发覆盖。
- **单一来源**：避免多处同时修改 state，通过中心化状态管理器（如 Actor 模型）串行化更新。
- **事件驱动**：所有状态变更通过事件触发，确保订阅方同步更新。
- **持久化快照**：定期保存状态快照，便于故障恢复和回溯。

#### 2.5 如果 state 中混入错误信息，后续会发生什么？
错误信息会在 Agent 的决策链中传播放大：
- 规划模块可能基于错误信息制定无效计划。
- 工具调用可能选择错误参数或目标。
- 反馈模块可能误判成功/失败。
- 记忆模块会将错误信息纳入长期记忆，影响未来任务。
- 最终导致任务失败、产生错误输出，甚至引发安全风险（如基于错误权限执行操作）。

因此，必须建立错误检测和纠正机制（如定期验证、用户确认、回溯修正），防止错误信息在 state 中持久化。

| State 五层结构   | 元信息、目标、进度、数据、上下文                |
| ---------------- | ----------------------------------------------- |
| 三层记忆         | 短期（任务）、中期（会话）、长期（用户）        |
| 工具历史必须记录 | 防重复、追踪依赖、成本审计、故障诊断            |
| State 太大问题   | 上下文溢出、延迟、成本、注意力稀释、一致性风险  |
| 问题             | 核心要点                                        |
| 压缩四层策略     | 无损压缩、语义压缩、分层存储、智能加载          |
| 污染防御         | 跨任务/用户隔离、工具校验、LLM 输出标记、并发锁 |
| 三类状态问题     | 过时（同步）、脏（持久化）、冲突（并发）        |
| 失败根因         | 常非模型问题，是 state 管理混乱                 |
| 摘要损失         | 细节、时序、置信度、来源、失败上下文            |
| 一致性保障       | ACID 事务、WAL、乐观锁、快照回滚                |
| 错误信息传导     | 直接错误→级联放大→信任侵蚀→系统固化             |

## 五、记忆 Memory

### 1. 记忆分类

#### 1.1 Agent 为什么需要 memory？
记忆使 Agent 能够：
- **保持上下文**：在多轮对话中理解指代、延续话题，避免“失忆”。
- **积累经验**：从历史交互中学习用户偏好和有效策略，提升后续任务效率。
- **避免重复劳动**：记住已执行的操作和结果，防止冗余调用（如重复查询同一 API）。
- **实现个性化**：基于长期用户画像提供定制化服务。
- **支持复杂任务**：维护任务进度、中间状态，实现断点续传和错误恢复。

#### 1.2 working memory、short-term memory、long-term memory 有什么区别？
- **Working Memory（工作记忆）**：当前任务正在使用的临时信息，如当前对话轮次、中间变量、待处理队列。生命周期极短（几秒到几分钟），通常对应进程内存。
- **Short-term Memory（短期记忆）**：存储近期交互历史，如最近 N 轮对话、最近 K 次工具调用。通常以滑动窗口方式存储，用于维持上下文连贯性，生命周期为一次会话。
- **Long-term Memory（长期记忆）**：持久化存储用户长期信息、知识、历史任务结果，可跨会话检索。通常使用外部存储（数据库、向量库），生命周期长（天、月、年）。

| 维度         | Working Memory<br>工作记忆 | Short-term Memory<br>短期记忆 | Long-term Memory<br>长期记忆 |
| ------------ | -------------------------- | ----------------------------- | ---------------------------- |
| **时间尺度** | 秒级（当前推理）           | 分钟-小时（单任务/会话）      | 天-永久（跨会话累积）        |
| **容量限制** | 极小（7±2 组块）           | 中等（上下文窗口）            | 极大（外部存储）             |
| **存储介质** | LLM 激活状态               | 上下文窗口 + 内存缓存         | 向量数据库 + 图数据库        |
| **访问速度** | 即时                       | <100ms                        | 100ms-秒级（检索）           |
| **衰减方式** | 注意力转移即丢失           | 会话结束或超时清理            | 主动管理，选择性遗忘         |
| **典型内容** | 当前聚焦实体、中间计算     | 本轮对话、任务进度            | 用户画像、领域知识           |
| **技术实现** | LLM 内部 attention         | Redis/内存 State              | Milvus/Neo4j + 对象存储      |

#### 1.3 episodic memory 和 semantic memory 有什么区别？
- **Episodic Memory（情景记忆）**：记录特定事件、经历，带有时间戳和情境。例如“用户上周三询问过 A 产品的价格”。用于回忆具体历史交互，通常包含时间、地点、人物等上下文。
- **Semantic Memory（语义记忆）**：存储抽象事实、概念、知识，不绑定具体情境。例如“用户偏好简约风格”、“A 产品的价格是 100 元”。用于构建用户画像和领域知识，是长期稳定的信息。

#### 1.4 会话历史和长期用户画像记忆有什么区别？

- **会话历史**：记录当前会话中的原始对话轮次，是短期、顺序性的，用于保持对话流畅和指代消解。生命周期通常限于一次会话。
- **长期用户画像**：从历史会话中抽取出的稳定特征（如偏好、习惯、身份信息），是结构化、跨会话的，用于个性化服务和预测用户意图。生命周期跨多次会话。

#### 1.5 RAG 知识库和 Agent memory 的边界是什么？
- **RAG 知识库**：存储静态的、客观的外部知识（文档、FAQ、产品信息），通常与用户无关，用于回答事实性问题。它是“世界知识”。
- **Agent Memory**：存储与用户交互相关的动态信息（历史对话、偏好、任务状态），是 Agent 自身状态的一部分，用于决策和个性化。它是“用户知识”和“过程状态”。
- **边界**：RAG 提供外部信息，Memory 提供内部状态。两者可能交互（如从 RAG 中检索到的信息可暂存到 memory），但存储内容和生命周期不同。RAG 通常只读，Memory 可读写。

---

### 2. 记忆写入与检索

#### 2.1 什么样的信息应该写入长期记忆？
- **稳定的用户偏好**：如“用户喜欢简洁回答”、“用户经常使用英文”。
- **重要事实**：用户提供的个人身份信息、关键约束（如预算上限）。
- **成功任务经验**：哪些工具组合有效、哪些策略失败。
- **频繁重复的模式**：用户反复询问相同类型的问题。
- **用户明确要求记住的信息**（如“记住我的地址是…”）。

#### 2.2 什么样的信息不应该写入长期记忆？
- **临时会话噪声**：如闲聊、无意义的确认、临时性的试探。
- **一次性临时数据**：如验证码、临时生成的会话 ID、临时计算结果。
- **敏感信息**：除非用户明确允许，否则不存储密码、支付信息、生物特征等。
- **过时或易变信息**：如实时天气、股价，应通过实时检索而非记忆。
- **错误或未确认的信息**：未经验证的信息不应写入长期记忆。

#### 2.3 记忆是每轮都写，还是按阈值写？
通常采用**按阈值写**（即事件驱动）：
- 每轮先缓存到短期记忆，当信息重复出现或达到重要性阈值（如用户明确表示“记住这个”、信息出现频率高、或模型判断为长期偏好）时，再写入长期记忆。
- 可以通过 LLM 判断信息的重要性和持久性，决定是否写入。
- 避免每轮都写，减少噪声、存储成本，并防止过度记录。

#### 2.4 如何检索与当前任务最相关的记忆？
- **向量检索**：将当前上下文嵌入后，在记忆向量库中搜索相似片段（如使用 Sentence-BERT）。
- **关键词匹配**：结合实体抽取，检索包含当前实体的历史记录。
- **时间衰减**：给近期记忆更高权重，假设近期的信息更相关。
- **多路召回+重排**：综合多种检索结果（如向量+关键词+时间），用重排模型（如 Cross-Encoder）选出最相关记忆。
- **上下文增强**：将当前任务目标、关键实体作为查询条件，提高检索精准度。

#### 2.5 记忆检索错误会造成什么问题？
- **上下文错配**：引入不相关记忆，干扰当前决策，导致答非所问。
- **固化错误**：错误记忆被反复使用，导致系统持续犯错，难以纠正。
- **隐私泄露**：检索到不应暴露的用户信息（如他人隐私）。
- **效率下降**：加载无关记忆，浪费 token 和时间，增加延迟。
- **决策混乱**：可能基于错误信息做出错误动作（如重复已执行的操作）。

#### 2.6 如何处理记忆冲突、记忆过期和错误记忆？
- **冲突解决**：对同一事实的不同版本，可采用时间戳优先（最新为准）、用户确认（请求用户判断）、或多数投票（当有多个来源时）。
- **过期处理**：为记忆设置有效期（如基于时间或基于事件），过期后标记为“待验证”或自动删除；也可通过定期检查外部数据源更新。
- **错误纠正**：当用户明确指出错误时，应立即更新或删除相应记忆，并在系统中记录修正历史，防止再次被检索到。

#### 2.7 如何设计 memory update 策略？
- **增量更新**：新信息与旧信息合并，而非简单覆盖（例如将新偏好追加到现有偏好列表中）。
- **版本控制**：保留历史版本，支持回滚和审计。
- **反馈驱动**：根据用户反馈（如“不是这样的”）触发更新或删除。
- **定期重评估**：基于新对话，重新评估已有记忆的准确性和时效性，淘汰过时信息。

#### 2.8 如何做 memory pruning 和 forgetting？
- **基于时间**：删除超过一定期限未访问的记忆（LRU）。
- **基于重要性**：保留重要记忆，删除低价值记忆（如通过重要性评分，或通过用户互动频率）。
- **基于容量**：当记忆库达到阈值，通过 LRU 或 LFU 淘汰。
- **基于冲突**：当新信息与旧记忆矛盾时，用新信息替代旧记忆（主动遗忘）。
- **主动遗忘**：设计“遗忘”机制，允许用户或系统明确删除某些记忆。

### 3. 高频追问

#### 3.1 为什么长期记忆系统很容易把临时信息误当成长期事实？
因为缺乏有效的“是否写入”判断机制。如果系统不加区分地记录所有交互，就会把一次性闲聊、试探性询问当作长期偏好存储。需要设计门控机制，结合**用户确认**、**重复模式**、**重要度评估**来筛选。此外，若系统没有时间衰减或过期机制，临时信息会一直留存。

| 原因             | 说明                      | 示例                                     |
| ---------------- | ------------------------- | ---------------------------------------- |
| **频率幻觉**     | 短期高频提及被误判为重要  | 用户临时项目连续问3天，被记为长期兴趣    |
| **缺乏上下文**   | 孤立判断，不了解信息背景  | "帮我订个蛋糕"（临时生日）→ 记为喜欢蛋糕 |
| **确认偏误**     | 系统倾向于记住"成功"交互  | 临时任务完成好，被纳入成功模式           |
| **衰减缺失**     | 无主动遗忘机制，信息累积  | 所有历史平等对待，噪声淹没信号           |
| **测试数据污染** | 开发/测试交互混入生产记忆 | 测试账号的偏好影响真实用户               |

**防御策略**：

| 策略             | 实现                                 |
| ---------------- | ------------------------------------ |
| **时间衰减加权** | 近期信息高权重，但需持续强化才入长期 |
| **显式确认机制** | "您希望我以后记住这个偏好吗？"       |
| **意图识别增强** | 区分"临时请求" vs "长期偏好声明"     |
| **多会话验证**   | 同一信息跨会话出现才入长期记忆       |
| **用户控制面板** | 展示已记忆内容，允许删除纠正         |

#### 3.2 用户明确否认过的旧记忆该怎么处理？

应立即标记为“无效”或直接删除，并在后续检索中排除。同时，应在系统中记录此次修正（如增加一个“否定”标签），防止再次被召回。如果记忆是用户画像的一部分，还应更新画像，使其不再包含该错误信息。

#### 3.3 如何防止错误记忆反复被召回强化？
- 设置“纠错计数器”，对每次被用户否定或修正的记忆，降低其检索权重，甚至当否定次数超过阈值时删除。
- 在记忆条目中增加“置信度”字段，每次被否定时降低置信度，低于阈值则删除。
- 定期人工审核或使用交叉验证（如从多个来源对比）来识别错误记忆。
- 确保记忆更新后，旧版本被清除或标记为历史，避免被再次检索。

#### 3.4 你会如何设计“是否写入记忆”的 gating？
- **用户显式指令**：如用户说“记住这个”、“下次自动执行”。
- **重复检测**：同一信息在不同会话中出现多次，可自动写入。
- **重要性分类器**：用模型判断信息是否对长期决策重要（如偏好、约束），或通过规则（如包含“我喜欢”、“我习惯”等关键词）。
- **交互反馈**：用户后续引用或强调某信息，触发写入。
- **安全边界**：敏感信息（如密码）一律不写入，除非有更高权限确认。

#### 3.5 如果 memory 和当前检索证据冲突，优先信哪个？
- 如果记忆是稳定的用户长期偏好，而当前检索是实时信息，应优先考虑**当前检索证据**（因为更及时，且可能用户意图已改变）。
- 如果记忆是历史事实，而当前检索可能是过时的，应优先**记忆**，但需向用户确认。
- 最佳实践：**向用户呈现冲突，由用户决定**，或根据信息源的可信度、时效性、一致性进行加权（如权威来源优先）。在关键操作中，必须用户确认。

| 问题                 | 核心要点                                                 |
| -------------------- | -------------------------------------------------------- |
| 三层记忆             | Working（秒级）、Short-term（会话级）、Long-term（持久） |
| Episodic vs Semantic | 个人经历事件 vs 一般知识事实                             |
| RAG vs Memory 边界   | 通用知识库 vs 个性化经验                                 |
| 写入标准             | VALUE：有价值、准确、持久、独特、显式                    |
| 写入策略             | 事件驱动 + 阈值批处理 + 周期性聚合                       |
| 检索架构             | 多路召回（向量/标签/时序/图谱）+ RRF + 重排序            |
| 三类记忆问题         | 冲突（解决策略）、过期（TTL）、错误（标记隔离）          |
| 遗忘机制             | 容量/时效/价值修剪，模拟遗忘曲线                         |
| 临时信息误记         | 缺乏门控、频率幻觉、衰减缺失                             |
| 否认处理             | 立即响应、标记隔离、反向学习、写入正确                   |
| 错误强化防止         | 隔离、负样本、纠正链、置信度惩罚                         |
| 门控三层             | 规则过滤 → 价值评估 → 冲突检查                           |
| 冲突优先级           | 当前陈述 > 实时证据 > 验证记忆 > 未验证记忆              |

## 六、规划 Planning 与推理 Reasoning

### 1. Planning

#### 1.1 什么是 planning？
Planning 是 Agent 将复杂目标分解为一系列可执行的子任务、并确定其执行顺序和依赖关系的过程。它是将“用户意图”转化为“具体行动序列”的桥梁，帮助 Agent 在面对复杂任务时做到有条不紊。

#### 1.2 复杂任务为什么要做 planning？
- **降低认知负载**：将大问题拆解为可管理的小步骤，避免模型一次性处理过多信息。
- **保证执行顺序**：某些步骤存在依赖（如先查航班再订票），规划可避免逻辑错误。
- **提高成功率**：通过预先设计路径，减少试错，提升任务完成率。
- **支持并行**：识别无依赖的子任务，可同时执行，提升效率。
- **便于监控与恢复**：规划提供了进度基准，当某步失败时，可定位并回滚。

#### 1.3 一次性全局规划和逐步规划分别适合什么场景？
- **一次性全局规划**：适合目标清晰、结构稳定、步骤可预测的任务（如“订机票”）。在任务开始前生成完整计划，然后依次执行。优点是执行快、可预测性强；缺点是若中间出现意外，整个计划可能失效。
- **逐步规划（动态规划）**：适合开放、不确定、需要探索的任务（如“研究一个主题”）。每完成一步，根据当前结果决定下一步。优点是灵活、能适应变化；缺点是可能过度试错，需谨慎设计停止条件。

#### 1.4 plan-and-execute 架构是什么？
这是一种经典的 Agent 架构模式：
1. **规划阶段**：根据用户目标和当前状态，生成一个完整的执行计划（通常是一个步骤列表）。
2. **执行阶段**：按顺序执行计划中的每一步，每步可能调用工具或生成输出。
3. **监控与反馈**：在每一步后观察结果，若出现偏差或失败，可重新规划（re-plan）或调整当前计划。

该架构将决策与执行分离，使系统更模块化，易于调试。

#### 1.5 子任务拆分的依据是什么？
- **原子性**：每个子任务应是可独立执行的、不可再分的最小操作单元。
- **依赖关系**：识别任务间的先后顺序（如先查数据再计算）。
- **工具边界**：根据可用的工具能力拆分，每个子任务对应一个工具调用或一个简单推理。
- **粒度平衡**：避免过细（增加调度开销）或过粗（难以处理中间失败）。

#### 1.6 子任务粒度太粗和太细分别有什么问题？
- **太粗**：单个子任务可能过于复杂，导致模型难以准确执行；失败时损失大，难以部分回滚。
- **太细**：计划步骤过多，增加调度和通信开销；模型可能因频繁切换而失去上下文；容易因微小错误导致整体失败。

#### 1.7 如何识别哪些步骤可以并行？
- 分析步骤间的数据依赖关系：若两个步骤不共享输入、不修改同一资源、不依赖彼此结果，则可并行。
- 使用有向无环图（DAG）建模，找出所有无依赖的节点。
- 在任务执行时，利用并发机制（如异步调用）同时启动这些步骤。

#### 1.8 执行到一半发现计划错误怎么办？
- **检测**：通过观察结果与预期不符、工具返回错误、超时等方式发现。
- **回滚**：若已执行步骤可撤销（如删除创建的资源），则执行补偿操作。
- **重新规划**：从当前状态出发，重新生成剩余部分的计划，避免从头开始。
- **用户介入**：若无法自动修正，向用户报告当前进度并请求指导。

#### 1.9 什么时候需要 re-plan？
- 计划中的某个步骤失败且无法重试。
- 外部环境发生变化（如目标价格变动、时间已过）。
- 用户中途修改目标或提供新信息。
- 执行过程中发现更优路径。
- 当前计划超出资源限制（如预算超支）。

#### 1.10 如何设置计划终止条件？
- **成功条件达成**：所有子任务完成且满足用户目标。
- **用户主动停止**：用户发出“停止”指令。
- **步数上限**：达到预设的最大执行步数。
- **时间超时**：任务执行超过指定时间。
- **成本超限**：API 调用费用或计算资源超出阈值。
- **无法继续**：所有可能尝试都已失败，且无可用替代方案。

### 2. Reasoning

#### 2.1 Agent 中的 reasoning 和普通 CoT 有什么区别？
- **普通 CoT（Chain of Thought）**：在回答问题时，模型显式写出中间推理步骤，但仅用于生成最终答案，不涉及与外部环境交互或状态更新。
- **Agent 中的 reasoning**：不仅包括推理链条，还包括**基于推理结果的决策和行动**。它需要结合当前状态、历史记忆、工具返回，动态调整后续步骤，且推理结果会直接影响外部世界（如调用 API）。Agent reasoning 是嵌入在闭环中的，而非一次性生成。

#### 2.2 为什么推理链不是越长越好？
- **错误累积**：每一步推理都可能引入误差，链条越长，错误概率越高。
- **成本与延迟**：长链需要更多 token，增加 API 调用成本和时间。
- **上下文稀释**：长链可能使模型忘记早期关键信息。
- **过度拟合**：模型可能陷入过度复杂的推理，反而忽略简单有效的方案。

#### 2.3 长推理可能带来哪些问题？
- 逻辑不一致或自我矛盾。
- 模型在中间步骤中“编造”不存在的证据。
- 难以调试（链路过长，难以定位错误源头）。
- 用户等待时间过长，体验差。

#### 2.4 如何控制 reasoning budget？
- **设置最大推理步数**（如 5 步）。
- **限制每次推理的 token 数**（如 1024）。
- **使用结构化输出**（如 JSON）强制精简。
- **采用“先计划后执行”**，将推理与执行分离，减少动态推理次数。
- **早期终止**：当置信度达到阈值时停止进一步推理。

#### 2.5 如何避免模型在中间推理阶段自我强化错误？
- **引入外部事实验证**：将中间结论与 RAG 知识库对比，检测矛盾。
- **多路径推理**：并行生成多个推理链，投票选择一致性高的。
- **元认知提示**：要求模型在推理时自我质疑（如“这个结论可靠吗？”）。
- **人工反馈**：在关键节点让用户确认。

#### 2.6 什么时候应该让模型显式输出步骤，什么时候不应该？
- **应该显式输出**：当需要可解释性、调试、审计时；当任务需要用户参与（如多轮澄清）；当步骤之间依赖复杂，需要人工检查时。
- **不应该显式输出**：当步骤简单且标准（如单次工具调用），可直接执行；当需要保护推理过程隐私（如内部策略）；当追求响应速度，可跳过中间展示。

#### 2.7 结构化推理和自由推理各有什么优缺点？
| 类型                          | 优点                                                   | 缺点                                                        |
| ----------------------------- | ------------------------------------------------------ | ----------------------------------------------------------- |
| **结构化推理**（如 JSON/XML） | 易于解析、验证、组合；适合与工具交互；便于存储和检索。 | 表达能力受限，难以处理非结构化或复杂逻辑；需要设计 schema。 |
| **自由推理**（自然语言）      | 灵活，可表达复杂逻辑；无需预先定义结构。               | 不易解析和自动处理；容易产生歧义；浪费 token。              |

### 3. 高频追问

#### 3.1 planning 的价值体现在哪些任务中最明显？
- **多步骤任务**（如“帮我规划一次旅行”）
- **有依赖关系的任务**（如“先搜索资料，再写报告”）
- **需要资源协调的任务**（如“同时查机票和酒店”）
- **容错要求高的任务**（如“生成数据分析报告”）
- **用户需要看到进度和路径的任务**（如“帮我做研究，并告诉我你的思路”）

#### 3.2 如果任务很简单，还要不要规划？
简单任务（如单次工具调用）可以跳过规划，直接执行，以提高效率。但若任务虽简单但用户希望看到流程（如“帮我把这段文字翻译成英文，再朗读出来”），还是需要简单规划以确保顺序。

#### 3.3 为什么过度规划会拖慢系统？
- 规划本身消耗时间（尤其是调用 LLM 生成计划）。
- 生成冗长的计划列表，增加执行开销。
- 过度细化导致频繁的状态切换，降低吞吐量。
- 在任务变化时，需要重新规划，造成资源浪费。

#### 3.4 为什么“先规划再执行”通常比“边想边做”更稳？
- **全局视野**：先规划能避免因局部最优而导致的整体次优路径。
- **资源预分配**：可提前检查所需工具、权限是否就绪。
- **错误可控**：在规划阶段发现潜在问题（如资源不足），可提前调整或拒绝，避免执行一半才失败。
- **可预测性**：用户可提前预览计划，减少意外。

#### 3.5 reasoning 和 planning 的边界在哪里？
- **planning**：侧重于“做什么”，即任务分解、步骤排序、资源分配。它关注的是行动序列，不涉及深层逻辑推导。
- **reasoning**：侧重于“为什么这么做”，即基于当前状态和知识进行推断、假设、验证。它关注的是决策依据，通常用于选择下一步行动或评估结果。
- **重叠**：在复杂规划中，也需要推理（如判断依赖关系）；在推理中，也会产生新的子目标。二者常交织进行。一般可将 planning 视为更高层的决策，而 reasoning 是规划中每一步的具体思考。

| 问题                       | 核心要点                                                     |
| -------------------------- | ------------------------------------------------------------ |

## 七、ReAct、反思与纠错

### 1. 执行循环

#### 1.1 ReAct 是什么？
ReAct（Reason + Act）是一种将推理与行动交织的Agent范式，由Yao等人于2022年提出。其核心是交替进行**Thought（思考）**、**Act（行动）**、**Observation（观察）** 三个步骤，形成一个闭环。与传统Chain-of-Thought只输出推理不同，ReAct允许模型在推理中动态调用外部工具，并根据观察结果更新推理，使Agent能够与环境交互并适应变化。

#### 1.2 为什么 Thought-Act-Observation 这种模式有效？
- **解耦推理与执行**：将“想”和“做”分离，使每一步清晰可追溯。
- **信息驱动**：观察为下一轮思考提供真实反馈，避免纯粹依靠模型内部知识。
- **适应性**：可处理开放域、需要外部知识的任务，并在执行中调整计划。
- **可解释性**：每一步的推理和行动都显式记录，便于调试和用户理解。

#### 1.3 反思 reflection 在 Agent 中起什么作用？
反思是Agent对自身过去行为、决策、结果的再评估，目的是识别错误、总结经验、优化后续行动。它使Agent具备**元认知能力**，能够回答“我做得对吗？”、“有没有更好的方式？”、“为什么失败了？”等问题，从而自我改进。

#### 1.4 self-critique 和 verifier 有什么区别？
- **self-critique（自我批判）**：Agent自己对自己生成的内容或决策进行评价，指出不足或提出改进建议。它通常由同一模型完成，依赖模型的自我意识。
- **verifier（验证器）**：一个独立的模块或模型，专门用于评估Agent的输出或决策是否正确。它可以是规则、训练好的分类器、或另一个LLM。verifier更客观，不易受模型自身偏见影响，但需要额外资源。

#### 1.5 反思应该每一步都做，还是结束后做？
取决于任务复杂度和成本：
- **每一步都做**：适合高风险、需要高精度的任务（如财务操作），能及时发现错误。但会显著增加延迟和token消耗。
- **阶段性反思**：在完成一个子目标或遇到异常时进行反思，平衡效率与可靠性。
- **结束后反思**：用于整体任务复盘，学习经验，不干预当前执行。

#### 1.6 如何判断当前步骤需要反思？
- **异常信号**：工具返回错误、超时、结果为空。
- **置信度低**：模型输出时概率低，或自我评分低。
- **与预期不符**：观察结果与先前的推理矛盾。
- **达到阈值**：已尝试次数超过设定，或步数过多。
- **用户反馈**：用户表示不满意或纠正。

#### 1.7 什么时候反思会适得其反？
- **过度反思**：在简单、确定性高的步骤中反复检查，浪费时间。
- **反思能力不足**：模型本身反思能力差，可能产生错误判断，误导后续行动。
- **成本过高**：频繁调用LLM进行反思导致预算超支。
- **陷入循环**：反思可能引发新的反思，形成死循环。

---

### 2. 纠错与回退

#### 2.1 Agent 如何发现自己做错了？
- **工具返回错误码或异常信息**。
- **结果验证器**：通过规则或模型判断输出是否符合预期（如格式、内容）。
- **一致性检查**：将新结果与历史记忆或外部知识比对，发现矛盾。
- **用户反馈**：用户明确指出错误或选择纠正。
- **超时或资源耗尽**：说明当前路径可能不可行。

#### 2.2 如何设计执行失败后的 retry 机制？
- **立即重试**：适用于瞬时错误（如网络抖动），可设定最大重试次数。
- **退避策略**：指数退避，避免频繁请求。
- **参数调整**：改变工具参数（如扩大搜索范围）后重试。
- **降级**：使用备选工具或简化操作。

#### 2.3 重试和重规划的区别是什么？
- **重试**：针对同一工具或步骤，以相同或微调参数再次尝试，不改变计划。
- **重规划**：放弃当前子任务或重新生成剩余计划，改变后续执行路径。重规划发生在重试多次无效、或步骤依赖关系失效时。

#### 2.4 如何避免重复犯同一个错误？
- **记录失败经验**：将错误原因写入记忆，在后续决策中参考。
- **更新策略**：根据错误调整工具的调用方式（如添加校验、选择替代工具）。
- **增加验证环节**：在关键操作后增加结果确认，确保正确后再继续。

#### 2.5 如何防止 Agent 进入死循环？
- **步数限制**：设置最大执行步数。
- **状态哈希**：记录历史状态（如工具调用参数、结果），检测重复状态，一旦重复则强制终止或切换策略。
- **循环检测**：在规划中识别循环依赖，或通过模型判断是否在兜圈子。
- **用户干预**：当检测到可疑循环时，请求用户确认。

#### 2.6 如何设计 step limit、budget limit 和 timeout？
- **step limit**：基于任务复杂度设定，如一般任务50步，复杂任务100步，达到后触发终止或用户介入。
- **budget limit**：限制总API调用成本或token数，实时监控，超限则中止并提示用户。
- **timeout**：设定总任务时间（如10分钟），超时则停止并返回当前结果。

---

### 3. 高频追问

#### 3.1 reflection 为什么有时能提升效果，有时却会让结果更差？
- **提升效果**：当模型有足够能力自我批判时，能修正错误、补充遗漏。
- **变差原因**：
  - 模型批判能力不足，反而引入错误假设。
  - 过度批判，导致放弃原本正确的路径。
  - 反思消耗了本可用于执行的资源，拖延时间。
  - 批判与执行共享模型，造成自我强化错误。

#### 3.2 如何区分“当前工具坏了”还是“上一步思路错了”？
- **工具错误特征**：返回明确错误码、空结果、异常；多次重试仍失败；其他替代工具成功。
- **思路错误特征**：工具返回正常但结果不合理；结果与预期不符但无错误提示；通过不同工具得到相同矛盾结果。
- 可通过**对比实验**：用不同工具完成同一子任务，若都失败则可能是思路问题；若仅单一工具失败，则可能是工具问题。

#### 3.3 如果 Agent 一直在尝试但没有进展，怎么判定该终止？
- **进度停滞**：连续多步状态无变化（如重复查询同一信息）。
- **资源消耗**：步数、时间、成本超过预设阈值。
- **用户反馈**：用户表示不想继续。
- **循环检测**：检测到历史状态重复出现。

#### 3.4 如果反思模块本身也不稳定，怎么办？
- **使用更可靠的verifier**：用独立模型或规则替代自我批判。
- **多次采样**：对同一问题多次反思，投票决定。
- **限制反思范围**：仅在关键步骤或出现明确错误时触发。
- **人工介入**：在反思模块不稳定时，降级为人工审核。

#### 3.5 verifier 比 self-reflection 更稳的原因是什么？
- **独立性**：verifier与决策模型解耦，避免自我强化偏见。
- **专门优化**：可针对特定任务训练，更准确。
- **可解释性**：输出明确（通过/不通过），易于集成。
- **稳定性**：不受决策模型内部状态波动影响，结果更一致。

| 问题                      | 核心要点                                                     |
| ------------------------- | ------------------------------------------------------------ |
| ReAct 定义                | Reasoning + Acting 交织，Thought-Action-Observation 循环     |
| ReAct 有效性              | 认知卸载、行动 grounding、反馈闭环、可解释、错误恢复         |
| Reflection 作用           | 元认知评估，错误检测、策略调整、知识提取、目标校准           |
| Self-Critique vs Verifier | 自我批评（第一人称、低成本、可能有偏见）vs 外部验证（第三人称、高成本、更客观） |
| 反思频率                  | 自适应：高风险每步，常规阶段，简单跳过                       |
| 反思触发信号              | 结果异常、置信度低、超时、成本超支、一致性冲突、用户反馈、目标偏离 |
| 反思适得其反              | 过度反思、确认偏误、分析瘫痪、错误归因、创意扼杀             |
| 错误检测层                | 语法、语义、执行、目标、用户、对比                           |
| Retry 策略                | 立即、指数退避、切换备选、参数调整、降级、人工介入           |
| Retry vs Replan           | Retry：同策略重复；Replan：改变策略                          |
| 错误学习                  | 短期黑名单、中期经验记忆、长期模型微调、系统规则更新         |
| 死循环防御                | 步骤上限、状态重复检测、行动序列检测、进展检测               |
| 三层防护                  | Step Limit、Budget Limit、Timeout                            |
| Reflection 效果波动       | 有明确标准、可发现错误时提升；原本正确、标准模糊时恶化       |
| 工具 vs 思路诊断          | 隔离测试工具，验证前置条件、逻辑链条、目标一致性             |
| 无进展终止                | 状态相似度、目标距离、信息增益、成功率、资源效率             |
| 反思不稳定应对            | 元反思、多反思器投票、规则兜底、人工介入                     |
| Verifier 更稳原因         | 独立性、客观性、专精、外部知识、对抗性、可审计               |

## 八、工具调用与 Function Calling

### 1. Tool Use 基础

#### 1.1 Agent 为什么需要工具，而不能只靠模型参数？
模型参数虽存储大量知识，但存在天然局限：
- **实时性**：模型知识固化于训练数据，无法获取最新信息（如实时天气、股价）。
- **外部操作**：模型无法执行写操作（发送邮件、修改数据库、控制设备）。
- **计算能力**：复杂计算（如微积分、大规模数据聚合）远超模型能力边界。
- **领域深度**：垂直领域需要访问专有数据库或 API。
工具让 Agent 突破模型本身的“象牙塔”，连接真实世界，实现从“知道”到“做到”的跨越。

#### 1.2 function calling 的本质是什么？
Function calling 是一种让 LLM 在生成响应时输出结构化调用请求的机制。其本质是**将模型的语言能力转化为结构化指令**，使 Agent 能够与外部系统进行确定性交互。它通常包括：
- 模型输出一个 JSON 对象，包含函数名和参数。
- 系统解析后执行对应函数。
- 将执行结果以结构化形式返回模型，供其继续决策。

#### 1.3 tool schema 为什么重要？
Tool schema 定义了工具的输入输出结构，它是模型理解工具能力的唯一依据。清晰、准确的 schema 能：
- 降低模型选择错误工具的概率。
- 确保参数抽取准确，减少调用失败。
- 支持模型进行类型校验和参数补全。
- 便于人类开发者维护和扩展。

#### 1.4 工具描述应该包含哪些关键信息？
一份好的工具描述应包含：
- **名称**：简洁、语义清晰（如 `get_weather`）。
- **功能描述**：一句话说明用途，以及何时使用。
- **输入参数**：每个参数名称、类型、是否必需、取值范围/格式、示例。
- **输出格式**：返回结果的结构和字段含义。
- **错误说明**：可能出现的错误码及含义。
- **使用示例**：典型调用和返回值示例。

#### 1.5 工具输入输出为什么需要结构化？
结构化使模型能精准构造调用，并可靠解析结果。优势：
- **减少歧义**：JSON 等格式天然支持类型和嵌套，避免自然语言的模糊。
- **便于校验**：可自动验证参数是否合法。
- **易于组合**：工具输出可直接作为另一工具的输入，形成流水线。
- **降低错误率**：结构化数据比自由文本更稳定。

#### 1.6 工具返回值如何反馈给模型继续决策？
通常通过“观察”环节将返回值注入上下文。常见做法：
- 将返回值格式化后附加到对话历史（如 `[Observation] 工具返回：...`）。
- 保留原始结构，但用自然语言摘要关键信息，避免超长 token。
- 同时提供成功/失败标志，帮助模型判断下一步。

---

### 2. 工具选择与路由

#### 2.1 多个工具都能完成任务时如何选择？
需要综合考虑：
- **工具成本**：优先选择更便宜的 API。
- **精度**：选择更可靠、更专业的工具。
- **权限**：根据当前用户权限过滤。
- **历史表现**：记录各工具在类似任务上的成功率，动态调整偏好。
- **用户偏好**：如用户指定使用特定服务。

#### 2.2 tool router 可以怎么做？
- **基于规则**：关键词匹配或预定义映射（如“天气” → get_weather）。
- **基于分类器**：训练一个分类器，输入用户意图，输出推荐工具。
- **基于 LLM 决策**：将工具列表作为上下文，让 LLM 直接选择。这是当前最灵活的方式，但成本高。

#### 2.3 基于规则、分类器、LLM 决策的工具路由各有什么优缺点？
| 方法         | 优点                               | 缺点                         |
| ------------ | ---------------------------------- | ---------------------------- |
| **规则**     | 快速、可解释、零成本               | 扩展性差，难以处理复杂意图   |
| **分类器**   | 轻量、可训练、泛化性好             | 需标注数据，无法处理新工具   |
| **LLM 决策** | 灵活、语义理解强、可处理多工具组合 | 成本高、延迟大、可能产生幻觉 |

#### 2.4 tool selection 错误会如何影响后续链路？
- **无效调用**：浪费资源，可能返回错误，打断流程。
- **误导后续决策**：若错误工具返回看似合理但实际无关的结果，模型可能基于错误信息继续行动。
- **连锁失败**：一次错误选择可能导致后续所有依赖该结果的任务失败。
- **用户体验下降**：用户看到无关或错误结果，降低信任。

#### 2.5 如何做 fallback 和兜底？
- **备选工具**：主工具失败时自动切换备用工具（如先用付费 API，失败则用免费公共 API）。
- **人工介入**：多次失败后，转人工处理或请求用户澄清。
- **降级输出**：返回通用回答或提示无法完成，避免错误扩散。
- **重试**：对瞬时错误采用指数退避重试。

**多级 Fallback 架构**：

| 层级             | 触发条件       | 兜底策略                         |
| ---------------- | -------------- | -------------------------------- |
| **L1: 参数修正** | 参数格式错误   | 自动修正（如日期格式转换）       |
| **L2: 工具重选** | 工具调用失败   | 选择功能相似的备选工具           |
| **L3: 功能降级** | 无可用工具     | 简化需求，用基础工具完成核心功能 |
| **L4: 缓存返回** | 实时工具不可用 | 返回过期缓存，标注时效           |
| **L5: 人工介入** | 全部自动化失败 | 转人工处理，记录失败模式         |
| **L6: 优雅失败** | 完全无法完成   | 明确告知用户限制，提供替代建议   |

---

### 3. 工具健壮性

#### 3.1 工具超时、失败、返回空值怎么办？
- **超时**：设置合理超时时间，超时后视为失败，触发重试或降级。
- **失败**：捕获错误码，区分可重试错误（如网络）和不可重试（如参数错误），针对性处理。
- **空值**：判断是否正常（如查询无结果），若异常则尝试扩大范围或询问用户。

#### 3.2 工具结果部分成功怎么办？
例如批量查询中部分成功。策略：
- 返回成功部分，附带失败列表，让模型决定是否重试失败项。
- 如果部分成功足以完成任务，继续执行；否则报告给用户并询问是否继续。

#### 3.3 如何做 retry、timeout、熔断和降级？
- **retry**：指数退避，最大次数限制，对瞬时错误有效。
- **timeout**：设置请求超时（如 5 秒）和整体任务超时（如 30 秒）。
- **熔断**：当工具错误率超过阈值时，暂时禁用该工具，切换到备用方案。
- **降级**：从复杂工具降级到简单工具（如从精确 API 降级到搜索引擎），或返回缓存结果。

#### 3.4 如何验证工具输出是否合法？
- **Schema 校验**：检查返回数据是否符合预期结构。
- **业务规则校验**：如返回值应在合理范围内。
- **交叉验证**：与另一个工具或知识库比对，确认一致性。

#### 3.5 工具返回错误事实时，Agent 如何发现？
- **外部验证**：通过第二个工具交叉确认（如查两个气象站的数据）。
- **内部知识**：模型自身可能识别出明显错误（如“北京今天温度 50°C”不合理）。
- **用户反馈**：询问用户“您确定吗？”。
- **历史记录**：对比以往相似查询的结果，发现异常。

---

### 4. 高频追问

#### 4.1 为什么 API Agent 通常比 UI Agent 更稳定？
- API 接口稳定、参数明确、返回结构化，易于解析和校验。
- UI 操作依赖视觉、元素定位，易受界面变化、渲染延迟影响。
- API 调用可幂等设计，方便重试；UI 操作难以回滚。

#### 4.2 为什么浏览器操作型 Agent 更容易失败？
- 页面结构动态变化，元素选择器易失效。
- 网络延迟、异步加载导致时序问题。
- 缺乏标准 API，需模拟人类操作，容错性差。
- 安全策略限制（如跨域、弹窗）。

#### 4.3 参数抽取错误通常发生在哪些地方？
- 实体歧义（如“苹果”指水果还是公司）。
- 缺少上下文（如用户说“明天”需结合当前时间）。
- 参数类型错误（将字符串传给了数字参数）。
- 多参数依赖（如“从 A 到 B”，需同时识别起点和终点）。

#### 4.4 工具描述写得过长或过短会有什么问题？
- **过短**：模型可能无法理解工具用途，选错工具或漏填参数。
- **过长**：占用大量 token，增加成本，且可能分散模型注意力，导致关键信息被忽略。

#### 4.5 你如何减少“明明有工具却不用”或者“没必要却乱调用工具”的问题？
- **提示优化**：在系统指令中明确强调“仅在必要时调用工具”。
- **工具描述优化**：写明使用场景，让模型知道何时该用。
- **路由层**：先用规则或分类器判断是否需要工具，避免模型过度调用。
- **成本惩罚**：在奖励函数中增加调用成本项，训练模型节约工具使用。
- **后校验**：对模型决策进行审查，若发现不必要调用，可拦截并重试。

| 问题                  | 核心要点                                                     |
| --------------------- | ------------------------------------------------------------ |
| 工具必要性            | 弥补 LLM 知识截止、计算、执行、存储、多模态局限              |
| Function Calling 本质 | 结构化接口协议，让 LLM 理解、决策、生成、接收反馈            |

| 工具描述要素          | 功能摘要、使用场景、输入参数、返回值、错误、限制、示例、注意事项 |
| 结构化原因            | 可解析、可验证、错误处理、链式调用、可观测                   |
| 结果反馈流程          | 结果处理 → 上下文整合 → LLM 继续决策                         |
| 工具选择维度          | 功能精确度、成本效率、响应速度、可靠性、数据新鲜度、用户偏好 |

| 部分成功              | 分类结果、立即返回、后台重试、最终合并                       |
| 健壮性四机制          | Retry、Timeout、熔断、降级                                   |
| 输出验证四层          | 语法、类型、范围、逻辑、业务                                 |

| API vs UI 稳定        | 契约接口 vs 视觉模拟，契约更稳定                             |
| UI Agent 失败         | 页面动态、加载不确定、状态复杂、视觉歧义、环境依赖、反爬     |

| 工具使用优化          | 明确场景、正反示例、参数约束、使用门槛、验证层               |

## 九、环境交互与执行控制

### 1. 环境交互

#### 1.1 Agent 中的 environment 指什么？
Environment 是 Agent 能够感知和操作的**外部世界**，包括：
- **数字环境**：API、数据库、文件系统、浏览器、操作系统。
- **物理环境**：机器人、物联网设备、传感器。
- **社交环境**：人类用户、对话伙伴。
- **内部环境**：Agent 自身的状态、记忆、已执行步骤。

Environment 提供 Agent 执行动作的场所，并产生反馈（observation）。

#### 1.2 observation 的本质是什么？
Observation 是 Agent 从环境接收到的**反馈信息**，是闭环的关键。它可以是：
- 工具返回的结构化数据（如 API 响应）。
- 用户输入（文本、点击）。
- 环境状态变化（页面加载完成、文件写入成功）。
- 错误信息、超时信号。
观察的本质是**证据**，让 Agent 知道行动的效果，从而调整下一步决策。

**Observation 的核心特性**：

| 特性         | 说明                 | 对 Agent 的影响                    |
| ------------ | -------------------- | ---------------------------------- |
| **不完全性** | 无法观测环境全部状态 | 需基于不完整信息决策，存在不确定性 |
| **有噪声**   | 观测包含错误或干扰   | 需容错处理，验证信息可靠性         |
| **有延迟**   | 观测滞后于实际变化   | 决策基于过时信息，需预测补偿       |
| **有成本**   | 获取观测需消耗资源   | 需权衡信息价值与获取成本           |
| **可选择性** | 可主动选择观测什么   | 需设计高效的信息获取策略           |

**Observation 的类型**：

| 类型           | 来源               | 时效性 | 可靠性       |
| -------------- | ------------------ | ------ | ------------ |
| **直接观测**   | 工具返回、API 响应 | 实时   | 高（结构化） |
| **间接观测**   | 日志、状态变化推断 | 延迟   | 中（需推理） |
| **用户反馈**   | 显式评价、隐式行为 | 异步   | 主观但关键   |
| **第三方观测** | 监控系统、告警     | 近实时 | 需验证       |

#### 1.3 部分可观测环境对 Agent 有什么挑战？

部分可观测意味着 Agent 无法直接获取环境的完整状态，只能通过有限的观察推断。挑战包括：
- **信息不足**：难以做出最优决策，需通过多次交互积累信息。
- **不确定性**：相同观察可能对应不同环境状态，易误判。
- **隐藏状态**：需要维护内部信念状态（belief state）来估计真实情况。
- **探索-利用**：需要主动获取信息（如询问用户）来减少不确定性。

#### 1.4 环境动态变化时，Agent 如何保持鲁棒？
- **持续监测**：在执行过程中定期重新获取环境状态（如刷新页面）。
- **重规划**：当检测到环境变化时，重新生成剩余计划。
- **状态快照**：保存关键点状态，便于回滚。
- **冗余设计**：多路径备选方案，应对环境突变。
- **超时与重试**：对不稳定环境设置合理的超时和重试机制。

#### 1.5 外部系统延迟或异步返回时怎么办？
- **异步处理**：采用回调、轮询或 Webhook 机制，不阻塞主流程。
- **超时管理**：设置等待上限，超时后按失败处理或询问用户。
- **状态追踪**：记录请求 ID，后续通过查询接口获取结果。
- **用户反馈**：告知用户正在处理，允许后续查询。

#### 1.6 为什么说环境反馈决定了 Agent 是否真正闭环？
闭环的核心是“行动 → 观察 → 调整”的循环。没有环境反馈，Agent 只能开环执行（一次输出），无法验证行动效果，也无法适应变化。只有通过观察获取真实反馈，Agent 才能评估是否达成目标、是否需要调整策略，从而形成真正的自主闭环。

---

### 2. 执行控制

#### 2.1 如何决定下一步是继续执行还是终止？
- **成功条件满足**：检查是否达成用户目标，若是则终止。
- **失败条件触发**：步数超限、时间超时、用户叫停、无法恢复的错误。
- **置信度阈值**：当模型判断任务已无可行路径，或已取得足够结果，可主动终止。
- **用户确认**：在关键节点询问用户是否继续。

#### 2.2 如何避免无效重复操作？
- **状态去重**：记录历史调用参数和结果，避免重复执行相同操作。
- **循环检测**：监测状态序列，若发现重复则中断或切换策略。
- **推理优化**：在规划时识别重复步骤并合并。
- **用户干预**：当检测到可能循环时，请求用户确认。

#### 2.3 如何做 checkpoint？
- **定期保存**：在关键步骤后保存当前状态（目标、已完成步骤、中间结果、记忆）。
- **版本标记**：为每个 checkpoint 赋予唯一 ID，便于恢复。
- **持久化**：将 checkpoint 写入外部存储（数据库、文件）。
- **恢复机制**：提供从任意 checkpoint 恢复的能力，支持断点续传。

#### 2.4 长任务如何实现暂停、恢复、回滚？
- **暂停**：保存当前执行状态（包括未完成队列、上下文）到持久化存储，释放资源。
- **恢复**：加载状态，从断点继续执行。
- **回滚**：回到上一个 checkpoint，撤销已执行的副作用（如删除已创建的资源）。可通过补偿操作（如取消订单、删除文件）实现。

#### 2.5 什么情况下需要 human-in-the-loop？
- **高风险操作**：支付、删除数据、发送重要邮件。
- **歧义或冲突**：用户意图不明，或记忆与当前证据矛盾。
- **超出权限**：Agent 无法执行的操作需用户授权。
- **决策关键点**：多路径选择、确认成功条件等。
- **任务失败后**：Agent 无法自动恢复时，需人工介入。

#### 2.6 如何设计用户确认点？
- **明确提示**：清晰说明即将执行的操作及其影响。
- **提供选项**：给出“确认”、“修改”、“取消”等选项，而非简单的是/否。
- **允许跳过**：高级用户可关闭确认，减少打扰。
- **记录确认**：保留用户确认历史，便于审计和后续学习。

---

### 3. 高频追问

#### 3.1 为什么同一个 Agent 在实验环境中表现很好，上线后却容易崩？
- **环境差异**：实验环境可控、低延迟、无并发；生产环境网络波动、资源竞争、数据分布变化。
- **数据分布**：测试集与真实用户输入分布不同，模型泛化不足。
- **外部依赖**：API 限流、服务降级、第三方不稳定。
- **并发与状态**：多用户同时执行时，状态隔离不当，导致相互干扰。

| 维度         | 实验环境         | 生产环境         | 影响                 |
| ------------ | ---------------- | ---------------- | -------------------- |
| **数据分布** | 干净、典型       | 噪声、异常、长尾 | 未覆盖场景失败       |
| **负载压力** | 低并发、充足资源 | 高并发、资源竞争 | 超时、死锁、OOM      |
| **外部依赖** | Mock/稳定        | 真实/波动        | API 变更、限流、故障 |
| **用户行为** | 配合、明确       | 随意、模糊、对抗 | 意图理解失败         |
| **数据规模** | 小规模测试       | 大规模真实       | 性能瓶颈、边缘 case  |
| **安全合规** | 宽松             | 严格             | 权限拒绝、审计阻断   |
| **时效要求** | 可容忍延迟       | 严格 SLA         | 超时失败             |

**系统性解决方案**：

```
上线前：
├─ 混沌测试：模拟依赖故障、网络延迟
├─ 压力测试：验证高并发下的稳定性
├─ 对抗测试：模拟恶意/异常输入
├─ 影子流量：并行处理生产流量，对比结果
└─ 灰度发布：小流量验证，逐步扩大

上线后：
├─ 全面监控：成功率、延迟、错误分类
├─ 自动降级：故障时切换备用策略
├─ 快速回滚：发现问题立即回退
└─ 持续学习：从生产数据改进模型
```

#### 3.2 执行环境变化对 Agent 的影响通常体现在哪些地方？

- **工具可用性**：API 版本升级、接口变更、服务下线。
- **响应格式**：返回数据结构变化，导致解析失败。
- **性能**：延迟增加导致超时，影响决策节奏。
- **权限**：认证过期、权限调整，导致操作被拒。

#### 3.3 为什么 UI 微小变动会导致 Agent 大面积失败？
UI Agent 依赖视觉或 DOM 元素定位。微小变动（如按钮位置、颜色、文本）可能使选择器失效，导致操作失败。与 API 的稳定接口相比，UI 是脆弱的。这也是为什么许多生产级 Agent 优先使用 API 而非 UI 操作。

#### 3.4 如何让 Agent 对环境不确定性更鲁棒？
- **松耦合**：通过 API 而非 UI 交互，减少对界面依赖。
- **容错设计**：对操作结果进行多轮验证，而非一次信任。
- **降级策略**：主路径失败时自动切换备用方案。
- **异常处理**：捕获所有异常，记录日志，支持人工介入。
- **自适应性**：根据历史成功率动态调整工具选择和重试策略。

| 原则             | 实现                               | 示例                     |
| ---------------- | ---------------------------------- | ------------------------ |
| **假设不确定性** | 所有观测带置信度，决策考虑最坏情况 | "数据可能过时，需验证"   |
| **快速检测**     | 持续监控环境状态，及时发现漂移     | 心跳检测、异常告警       |
| **优雅降级**     | 完整功能不可用时，提供简化替代     | 实时 API 失败 → 返回缓存 |
| **冗余设计**     | 多路径达成目标                     | 主工具失败 → 备用工具    |
| **保守策略**     | 不确定时选择安全选项               | 高置信度才执行，否则确认 |
| **快速恢复**     | 失败时快速切换或重试               | 自动重试、自动切换节点   |
| **持续学习**     | 从环境反馈改进策略                 | 在线学习、策略更新       |

#### 3.5 为什么执行控制是工程成败的关键？
执行控制决定了 Agent 的**可靠性、安全性和用户体验**：
- **防止失控**：限制步数、时间、成本，避免无限循环和资源耗尽。
- **保证可恢复**：通过 checkpoint 和回滚，降低失败影响。
- **提升可维护性**：清晰的执行状态便于调试和监控。
- **确保安全**：在关键操作前确认，防止误操作。
- **优化资源**：合理控制并发和重试，避免浪费。没有健全的执行控制，再强大的模型也难以稳定运行。

| 问题              | 核心要点                                                     |
| ----------------- | ------------------------------------------------------------ |
| Environment 定义  | Agent 外部一切，包括物理层、工具层、信息层、用户层、社会层   |
| Observation 本质  | 不完全、有噪声、有延迟、有成本、可选择的环境感知             |
| 部分可观测挑战    | 状态推断、历史依赖、隐藏变量、对抗欺骗、信息成本             |
| 动态环境鲁棒      | 持续监控、快速检测、自适应调整、保守回退、冗余设计           |
| 异步延迟处理      | 可预测延迟轮询、长时任务回调、不确定延迟超时降级、批量队列   |
| 环境反馈关键      | 反馈是闭环核心，决定 Agent 是否真正适应、学习、进化          |
| 终止决策          | 安全 > 成功 > 资源 > 失败 > 用户，均不满足则继续             |
| 避免重复          | 动作级缓存、意图级语义去重、模式级学习、系统级循环检测       |
| Checkpoint        | 触发策略、完整状态、分层存储、版本管理、恢复机制             |
| 长任务生命周期    | 暂停（保存+释放）、恢复（加载+适配）、回滚（撤销+重建）      |
| Human-in-the-loop | 高风险、高不确定、超能力、用户要求、连续失败、伦理敏感       |
| 确认点设计        | 风险分级、信息充分、操作便捷、可撤销、学习记忆               |
| 实验 vs 生产差异  | 数据、负载、依赖、用户、规模、安全、时效                     |
| 环境变化影响      | 工具 API、数据 Schema、UI DOM、基础设施、安全策略、业务规则  |
| UI 脆弱性         | ID、class、XPath、文本、位置、视觉特征均易变                 |
| 鲁棒性设计        | 假设不确定、快速检测、优雅降级、冗余、保守、快速恢复、持续学习 |
| 执行控制关键      | 资源、安全、体验、质量、运维的保障，模型到价值的桥梁         |
