# 题目回答

## 一、先把 Skill 讲明白

### 1. 什么是 skill？它和 tool 的区别是什么？

**Skill** 是 Agent 中一个**可复用的、封装完整业务逻辑的能力单元**。它通常由多个原子操作（如工具调用、条件判断、错误处理）组合而成，对外暴露一个清晰的语义接口。例如，“预订会议室”这个 skill 内部可能包含：查询空闲会议室 → 选择会议室 → 调用预订 API → 发送确认通知 → 记录日历。Skill 隐藏了内部复杂性，让 Agent 只需理解“预订会议室”这一意图，就能完成整个任务。

**Tool** 是 Agent 可调用的**最小原子操作**，通常对应一个外部 API、函数或系统命令。它执行单一、确定性的动作，如“发送邮件”、“查询天气”、“获取用户信息”。

| 维度         | Skill                                | Tool                           |
| ------------ | ------------------------------------ | ------------------------------ |
| **粒度**     | 粗粒度，可能包含多步、逻辑、错误处理 | 细粒度，单一功能               |
| **内部结构** | 可包含多个工具调用、条件分支、循环   | 通常无内部逻辑，仅执行具体操作 |
| **抽象层次** | 业务级（“完成一次会议预订”）         | 技术级（“调用会议室 API”）     |
| **依赖关系** | 依赖一个或多个 Tool 或子 Skill       | 独立，或依赖外部系统           |
| **示例**     | “整理月度报表并发送给领导”           | “发送邮件”、“查询数据库”       |

### 2. 为什么企业做 Agent 会越来越重视 skill，而不是只做 function calling？

- **封装业务逻辑，降低 LLM 负担**：企业业务流程往往包含多步、条件判断、异常处理。若仅依赖 function calling，Agent 需每次推理如何组合工具，既易出错又消耗大量 token。Skill 将业务逻辑固化，Agent 只需调用一个高层能力，大幅降低决策复杂度。
- **提高稳定性和可靠性**：Skill 内部可实现重试、熔断、回滚、数据校验等工程保障，而让 LLM 动态组合很难保证这些健壮性。
- **便于安全与合规管控**：Skill 可作为权限控制的最小单元，统一记录审计日志，避免每个工具单独授权带来的风险。
- **支持复用与协作**：多个 Agent 可共享同一套 Skill，减少重复开发，且业务人员也可通过低代码方式配置 Skill，而不必修改 Agent 核心逻辑。
- **提升可维护性**：当底层 API 变更或业务规则调整时，只需修改 Skill 内部实现，所有调用该 Skill 的 Agent 自动受益，避免全局修改。

### 3. skill 和 prompt、workflow、plugin 分别有什么区别？

| 对比项              | Skill                        | Prompt                  | Workflow                     | Plugin                         |
| ------------------- | ---------------------------- | ----------------------- | ---------------------------- | ------------------------------ |
| **本质**            | 可执行的业务能力单元         | 文本指令，引导 LLM 行为 | 预定义的步骤序列             | 外部可插拔的功能模块           |
| **形态**            | 代码/脚本 + 配置，可能有状态 | 自然语言文本            | 流程定义（如 DAG）           | 独立组件，如浏览器插件         |
| **执行方式**        | Agent 调度执行               | LLM 解读并执行          | 引擎按图执行                 | 宿主环境调用                   |
| **是否包含逻辑**    | 可包含复杂逻辑、分支、循环   | 无逻辑，仅文本          | 通常为固定逻辑（可条件分支） | 提供功能，内部逻辑不可见       |
| **与 Agent 的关系** | Agent 的能力组件             | Agent 决策的一部分      | Agent 可调用工作流作为技能   | 外部扩展，Agent 可调用其接口   |
| **示例**            | “生成周报并邮件发送”         | “用友好语气回复客户”    | 数据清洗 pipeline            | 代码高亮插件、浏览器开发者工具 |

- **Skill vs Prompt**：Prompt 是“软”能力，告诉模型如何思考；Skill 是“硬”能力，直接执行操作。一个 Skill 内部可以调用 Prompt（如让 LLM 生成邮件正文），但 Skill 本身不是 Prompt。
- **Skill vs Workflow**：Workflow 强调“流程编排”，通常无动态决策（或仅按规则分支）；Skill 可以更灵活，包含动态决策（如根据 LLM 判断选择不同路径）。此外，Workflow 是编排，Skill 是可被 Workflow 调用的组件。
- **Skill vs Plugin**：Plugin 通常是第三方开发的、可独立安装的扩展，往往以 API 形式暴露功能；Skill 则是 Agent 系统内建或定制的能力模块，更贴近业务逻辑，且可与 Agent 的记忆、状态深度集成。Plugin 可作为一种 Tool 被 Skill 调用。

**总结**：Skill 是连接原子 Tool 与复杂业务流程的桥梁，它让 Agent 从“知道如何调用工具”升级到“掌握业务能力”，是企业级 Agent 工程从“Demo 可用”走向“生产可靠”的关键抽象。

| 问题                 | 一句话回答                                               |
| -------------------- | -------------------------------------------------------- |
| Skill 是什么         | 封装完整业务能力的、可复用的、高阶任务单元               |
| Skill vs Tool        | Tool 是原子操作，Skill 是完整业务方案                    |
| 为什么企业重视 Skill | 降低门槛、提升可靠、降低成本、标准化复用、可控审计       |
| Skill vs Prompt      | Prompt 是"怎么做"的指令，Skill 是"做什么"的封装          |
| Skill vs Workflow    | Workflow 固定执行，Skill 预编排+自适应                   |
| Skill vs Plugin      | Plugin 是扩展机制，Skill 是业务封装，Skill 可调用 Plugin |

## 二、什么能力值得做成 Skill

### 1. 什么样的任务适合沉淀成 skill？什么样的不适合？

**适合沉淀为 skill 的任务特征**：
- **高频复用**：多个 Agent 或多个场景都会用到的业务能力（如“生成周报并发送”、“客户信息脱敏”）。
- **多步且逻辑稳定**：涉及多个工具调用、条件判断、异常处理，且业务流程相对固定（如“预订机票”需要查询、比价、下单、支付、发确认）。
- **有明确业务边界**：能力可被清晰命名和定义，输入输出明确，内部实现可以黑盒化（如“分析财报关键指标”）。
- **需要工程保障**：需要重试、熔断、日志、权限控制等标准化能力（如“调用第三方 API 获取数据”）。
- **可独立测试和版本管理**：能够单独迭代，不影响调用方。

| 原则                         | 说明                         | 判断标准                     | 示例                       |
| ---------------------------- | ---------------------------- | ---------------------------- | -------------------------- |
| **V**aluable（高价值）       | 业务价值高，频繁使用         | 周调用 >100 次，或单次价值高 | 竞品调研、客户画像生成     |
| **A**ggregated（需聚合）     | 多工具协同，非单一工具可完成 | 涉及 3+ 个工具或 2+ 个决策点 | 从需求到代码的完整开发     |
| **S**tandardized（可标准化） | 流程相对固定，最佳实践可沉淀 | 同类任务 80% 步骤可复用      | 标准财报分析、常规招聘流程 |
| **T**rusted（需可信）        | 对可靠性要求高，需严格测试   | 失败代价高，需人工兜底       | 合同审查、合规检查         |
| **E**volving（持续进化）     | 需要持续优化，积累数据       | 有明确优化指标和数据反馈     | 推荐策略、定价模型         |

**不适合沉淀为 skill 的任务特征**：
- **一次性或临时性任务**：只会在某个特定场景出现，且不会复用（如“帮我把这个临时文件重命名”）。
- **极度简单且无复用的原子操作**：若只是一个简单的 tool 调用，且无额外逻辑，直接让 Agent 调用 tool 更灵活。
- **业务逻辑频繁变化**：若流程每周都在变，沉淀为 skill 反而增加维护成本，不如让 Agent 动态组合。
- **依赖强上下文难以固化**：例如需要用户实时确认、多轮交互且路径不可预测的任务，更适合由 Agent 动态决策而非固化在 skill 中。

| 类型         | 说明                       | 示例                 | 替代方案                 |
| ------------ | -------------------------- | -------------------- | ------------------------ |
| **过于简单** | 单工具调用，无编排需求     | 查天气、计算器       | 直接 Tool 调用           |
| **过于动态** | 每次执行路径完全不同       | 开放式头脑风暴       | 基础 LLM + Prompt        |
| **过于低频** | 年调用 <10 次              | 年度审计特殊场景     | 临时 Workflow 或人工处理 |
| **过于敏感** | 需高度人工判断，不可自动化 | 高管决策、伦理裁决   | Human-in-the-loop 流程   |
| **快速变化** | 流程每周都变，无法稳定     | 实验性业务、探索阶段 | 轻量 Prompt + 动态编排   |

### 2. 什么时候应该新增一个 skill，什么时候应该新增一个 tool？

| 场景             | 新增 Tool             | 新增 Skill                             |
| ---------------- | --------------------- | -------------------------------------- |
| **功能粒度**     | 原子操作，单一职责    | 组合多个 Tool，封装业务逻辑            |
| **复用性**       | 可能被多个 Skill 调用 | 面向业务场景，被多个 Agent 复用        |
| **稳定性**       | 接口相对稳定，变化少  | 内部可变化，但对外接口保持稳定         |
| **是否需要状态** | 通常无状态            | 可能需要维护中间状态（如批量处理进度） |
| **测试要求**     | 单元测试即可          | 需要集成测试、端到端测试               |
| **权限管控**     | 按 API 授权           | 按业务能力授权（如“财务分析”技能）     |

**决策原则**：
- 若一个功能是**独立的、基础的、可被其他能力组合**，应做成 Tool。
- 若一个功能是**面向业务的、组合了多个工具和逻辑、且会被频繁使用**，应做成 Skill。
- 当多个 Agent 重复编写相同逻辑时，就应该考虑将其抽取为 Skill。

### 3. 为什么不是所有能力都应该 skill 化？

- **过度抽象增加维护成本**：每个 Skill 都需要设计接口、编写文档、维护版本。对于简单或临时的能力，直接用 Tool 更轻量。
- **降低灵活性**：Skill 封装了内部逻辑，可能会限制 Agent 在某些边缘场景下的创造性发挥。例如，固定流程可能不适用于所有变体。
- **增加系统复杂度**：Skill 数量过多会导致依赖关系混乱，难以管理。
- **开发迭代成本**：每次业务规则变化都需要修改 Skill 代码并重新部署，而若由 Agent 动态组合，可能只需调整 prompt。
- **可能造成性能浪费**：如果 Skill 内部包含不必要的步骤，调用时就会引入额外开销。而 Agent 按需调用 Tool 可能更高效。

**正确做法**：采用“渐进式 skill 化”策略。先由 Agent 使用 Tool 动态完成任务，当发现某种组合被频繁使用、且逻辑稳定后，再将其固化为 Skill，提升复用性和稳定性。避免“先设计后使用”的过度工程。

| 问题                | 核心要点                                                     |
| ------------------- | ------------------------------------------------------------ |
| 适合 Skill 的任务   | VALUE 原则：高价值、需聚合、可标准化、需可信、持续进化       |
| 不适合 Skill 的任务 | 过于简单、过于动态、过于低频、过于敏感、快速变化             |
| 新增 Tool vs Skill  | 简单原子能力 → Tool；复杂业务场景 → Skill；已有 Skill 扩展 > 新建 |
| 不全部 Skill 化原因 | 开发维护成本高、抑制创新、Skill 爆炸、响应迟缓、资源浪费     |
| 最优策略            | 分层治理，金字塔结构，上层少而精，下层多而全，严格准入       |

## 三、Skill 应该怎么设计

### 1. 一个好的 skill 至少应该包含哪些内容？

一个高质量的 Skill 应具备以下核心要素，使其成为可复用、可维护、可信赖的业务能力单元：

- **明确的元信息**
  - **名称**：语义清晰，符合业务认知（如 `BookMeetingRoom`、`GenerateMonthlyReport`）。
  - **描述**：说明 Skill 的用途、适用场景、输入输出，帮助 Agent（或开发者）理解何时调用。
  - **版本**：支持语义化版本，便于演进。
  - **作者/归属**：便于问题追溯。

- **标准化的输入规范**
  - **参数定义**：每个参数的类型、是否必需、默认值、取值范围/格式、示例。
  - **约束条件**：如权限要求、前置条件（如“用户已登录”）。
  - **输入校验逻辑**：确保调用方传入正确数据，提前发现错误。

- **可靠的执行逻辑**
  - **步骤编排**：明确执行流程，可包含工具调用、条件分支、循环、并行处理。
  - **错误处理**：定义各类异常的应对策略（重试、降级、熔断、回滚）。
  - **超时控制**：设置整体超时和子步骤超时，防止阻塞。
  - **状态管理**：若 Skill 有状态（如批量处理进度），需明确如何存储和恢复。

- **规范的输出结构**
  - **成功输出**：包含结果数据、状态标识、元信息（如耗时、版本）。
  - **失败输出**：包含错误码、错误信息、建议的补救措施。
  - **可追溯性**：输出中可包含内部执行日志或关键步骤的摘要，便于调试。

- **安全与审计**
  - **权限声明**：Skill 需要的权限列表（如“读写邮箱”、“访问数据库”）。
  - **日志记录**：自动记录调用者、参数、结果、耗时，便于审计。
  - **数据脱敏**：对于敏感信息，在日志中自动脱敏。

- **测试与文档**
  - **单元测试**：覆盖主要路径和异常场景。
  - **示例调用**：提供典型使用示例，降低接入成本。
  - **API 文档**：以机器可读（如 OpenAPI）和人类可读两种形式提供。

```python
┌─────────────────────────────────────────┐
│  1. 元信息（Metadata）                    │
│     ├─ id: 全局唯一标识符                  │
│     ├─ name: 可读名称（业务语言）           │
│     ├─ version: 语义化版本（major.minor.patch）│
│     ├─ description: 一句话功能描述          │
│     ├─ owner: 负责团队/个人                │
│     ├─ tags: [领域, 场景, 复杂度]           │
│     └─ status: active/deprecated/beta      │
├─────────────────────────────────────────┤
│  2. 接口契约（Interface）                  │
│     ├─ input_schema: JSON Schema 定义      │
│     ├─ output_schema: JSON Schema 定义     │
│     ├─ examples: 输入输出示例（few-shot）   │
│     └─ constraints: 前置条件、资源限制       │
├─────────────────────────────────────────┤
│  3. 触发条件（Trigger）                    │
│     ├─ intent_patterns: 意图匹配模式        │
│     ├─ entity_requirements: 必需实体        │
│     └─ confidence_threshold: 触发置信度      │
├─────────────────────────────────────────┤
│  4. 执行逻辑（Execution）                  │
│     ├─ orchestration: 工具链编排（DAG）      │
│     ├─ reasoning_nodes: 关键决策点 LLM 配置  │
│     ├─ error_handling: 异常处理策略         │
│     └─ fallback_chain: 降级链路            │
├─────────────────────────────────────────┤
│  5. 上下文管理（Context）                   │
│     ├─ required_memory: 依赖的长期记忆        │
│     ├─ working_memory_schema: 工作内存结构    │
│     └─ checkpoint_policy: 检查点策略         │
├─────────────────────────────────────────┤
│  6. 质量保障（Quality）                     │
│     ├─ test_cases: 自动化测试用例            │
│     ├─ evaluation_metrics: 效果评估指标       │
│     ├─ monitoring_events: 监控埋点           │
│     └─ safety_checks: 安全/合规检查          │
├─────────────────────────────────────────┤
│  7. 运维配置（Operations）                  │
│     ├─ resource_limits: 超时/成本/并发限制     │
│     ├─ retry_policy: 重试策略               │
│     ├─ circuit_breaker: 熔断配置            │
│     └─ human_escalation: 人工介入条件         │
└─────────────────────────────────────────┘
```



### 2. skill 的粒度应该怎么控制？太大或太小各有什么问题？

**粒度控制原则**：Skill 应是一个**完整的、可独立理解的业务能力**，其边界应遵循“单一职责”与“业务语义完整性”。

**粒度太小的问题**：
- **过度拆分**：导致 Agent 需要多次调用 Skill 才能完成一个业务目标，增加交互开销。
- **丧失业务语义**：例如将“预订机票”拆成“查航班”“比价”“下单”三个独立 Skill，Agent 仍需自己编排，无法享受高层封装的好处。
- **维护成本上升**：数量激增，依赖关系复杂。

**粒度太大的问题**：
- **缺乏灵活性**：一个超大 Skill 内部包含太多可能的分支，可能导致在特定场景下执行多余步骤，效率低。
- **难以复用**：大 Skill 往往面向特定完整场景，很难被其他场景复用（例如“组织会议”可能包含预订会议室、发送邀请、准备资料等，但有时只想复用其中“发送邀请”部分）。
- **调试困难**：内部逻辑复杂，出问题时难以定位。
- **版本耦合**：任何微小调整都可能需要发布整个 Skill，影响所有调用方。

**推荐粒度**：
- Skill 应**对应一个具有明确业务价值的最小完整能力**。例如，“发送会议邀请邮件”可以是一个 Skill，而“预订会议室并发送邀请”可能是更上层的另一个 Skill（可组合前者）。
- 通常以“一个业务人员能够理解和描述的任务”作为粒度参考。例如“获取客户画像”、“生成合同摘要”、“自动归档文件”都是合适的粒度。

### 3. skill 的触发条件、执行步骤、输出规范，分别应该怎么写？

#### 3.1 触发条件（Trigger）

触发条件定义了 Skill 在什么情况下应该被调用，通常用于 Agent 的决策路由。写法应包含：

- **语义匹配**：用自然语言描述适合调用该 Skill 的用户意图示例，帮助 Agent（或分类器）判断。
- **前置状态**：例如“用户已登录”、“当前处于任务编辑模式”。
- **参数条件**：某些参数必须存在或满足特定条件（如“日期未过去”）。
- **优先级/互斥**：与其他 Skill 的关系，如“若用户要求快速响应，优先使用此 Skill”。

示例：
```
触发条件：
- 用户意图包含“预订会议室”、“订个会议室”、“安排会议场地”
- 用户已认证且具有会议室预订权限
- 会议开始时间晚于当前时间
- 无其他更紧急的会议冲突
```

#### 3.2 执行步骤（Execution Steps）

执行步骤应清晰描述 Skill 内部的工作流，可采用结构化方式（如伪代码、流程图、步骤列表）。写法应包含：

- **顺序依赖**：明确各步骤的前后关系。
- **工具调用**：列出具体调用的工具及其参数映射。
- **条件分支**：根据中间结果选择不同路径（如“如果会议室空闲则预订，否则查询其他时段”）。
- **错误处理**：定义每一步失败时的应对（重试、跳过、回滚、上报）。
- **并行**：可并行执行的步骤明确标出。
- **循环**：如多次尝试、遍历列表。

示例（简化）：
```
步骤：
1. 解析用户输入，提取：日期、开始时间、时长、参会人列表。
2. 调用 get_available_rooms(date, start_time, duration) 获取空闲会议室列表。
3. 若列表为空：
   - 调用 suggest_alternative_times(date, duration) 生成备选时段。
   - 返回“无空闲会议室，推荐以下时段”并终止（需用户确认）。
4. 若列表不为空：
   - 按优先级（容量匹配、楼层偏好）选择最优会议室。
   - 调用 book_room(room_id, date, start_time, duration)。
   - 若预订成功，调用 send_calendar_invite(attendees, room_info)。
   - 记录预订结果到数据库。
5. 返回预订确认信息（含会议室、时间、确认号）。
```

#### 3.3 输出规范（Output Specification）

输出规范应让调用方（Agent 或其他 Skill）能明确理解执行结果，并决定下一步。应包含：

- **结构**：推荐 JSON 格式，包含固定字段。
- **成功输出**：
  - `status`: "success"
  - `data`: 业务结果（如确认号、会议室详情）
  - `message`: 友好提示
  - `duration_ms`: 执行耗时（可选）
- **失败输出**：
  - `status`: "failure"
  - `error_code`: 业务错误码（如 `ROOM_UNAVAILABLE`、`AUTH_FAILED`）
  - `error_message`: 详细错误描述
  - `suggestions`: 建议的后续操作（如“可尝试其他时间”）
- **部分成功**：若技能支持部分成功，可用 `partial_results` 字段携带已完成的数据。
- **元数据**：版本号、请求 ID，便于追踪。

示例：
```json
{
  "status": "success",
  "data": {
    "booking_id": "B123456",
    "room": "Room 301",
    "start_time": "2025-03-25T10:00:00Z",
    "end_time": "2025-03-25T11:00:00Z",
    "attendees": ["alice@example.com", "bob@example.com"]
  },
  "message": "会议室预订成功，已发送日历邀请。",
  "duration_ms": 320
}
```

通过以上设计，Skill 才能成为 Agent 生态中可靠、可复用、可维护的基础组件。

| 问题         | 核心要点                                                     |
| ------------ | ------------------------------------------------------------ |
| Skill 7 要素 | 元信息、接口契约、触发条件、执行逻辑、上下文管理、质量保障、运维配置 |
| 粒度控制     | 单一业务目标、可独立完成、可复用、可测试、可优化；避免过小（碎片化）或过大（难维护） |
| 触发条件     | 意图模式（显式/隐式/否定）、实体要求、上下文条件、置信度阈值、优先级、互斥组合 |
| 执行步骤     | DAG 编排、步骤定义（类型、参数、输入输出、重试、超时）、错误处理、检查点、进度通知 |
| 输出规范     | JSON Schema 结构、质量验证规则、格式变体、溯源可解释性、版本兼容性 |

## 四、你准备怎么开发 Skill

### 1. 你会如何从零开发一个 skill？

从零开发一个 Skill 是一个系统化工程，需要兼顾业务语义、工程质量和可维护性。我通常遵循以下步骤：

1. **需求分析与边界定义**
   - **明确业务场景**：与业务方或产品经理沟通，确定 Skill 要解决的业务问题、预期输入输出、使用频率。
   - **定义输入输出**：明确 Skill 的输入参数（类型、是否必需、取值范围）和输出结构（成功/失败格式、业务数据）。
   - **划定边界**：确定 Skill 的“职责边界”，哪些逻辑应该内聚，哪些应该交由上层 Agent 或其它 Skill 处理。例如，“发送会议邀请” Skill 不应包含会议室的预订逻辑。

2. **接口设计**
   - 设计 Skill 的调用接口（通常为 JSON schema），包括输入参数、输出格式、错误码。
   - 确定同步/异步模式：若技能可能耗时较长，设计异步回调或轮询机制。
   - 设计版本号，预留兼容性。

3. **内部逻辑拆解**
   - 将 Skill 拆解为一系列子步骤（工具调用、计算、条件判断）。
   - 绘制流程图或伪代码，标注依赖关系、并行可能性、分支条件。
   - 识别可能的外部依赖（API、数据库、文件系统），并明确调用方式。

4. **实现与编码**
   - 使用稳定的编程语言（如 Python）和框架（如 FastAPI），将步骤转化为代码。
   - 采用**依赖注入**模式，便于单元测试和替换外部服务。
   - 引入重试、超时、熔断等工程保障（见第三部分）。
   - 实现结构化日志，记录关键节点和耗时，便于监控和排查。

5. **测试**
   - **单元测试**：覆盖核心逻辑、分支、异常处理。
   - **集成测试**：与真实或模拟的外部依赖（API、数据库）联调。
   - **端到端测试**：在真实或类生产环境中用典型输入验证输出。
   - **边界测试**：空值、超大输入、并发调用等。

6. **文档与示例**
   - 编写 Skill 的使用文档，包括功能描述、输入输出说明、错误码、调用示例。
   - 提供最小可运行示例，方便调用方快速集成。

7. **部署与监控**
   - 将 Skill 打包为服务或库，纳入 CI/CD 流程。
   - 配置监控（调用量、成功率、延迟、错误分布），设置告警。
   - 建立版本管理，支持灰度发布和回滚。

8. **迭代优化**
   - 收集线上日志和用户反馈，识别频繁错误或性能瓶颈。
   - 定期 review Skill 的准确性、复用率，决定是否拆分或合并。

### 2. 你会如何把业务 SOP 抽象成一个可复用的 skill？

业务 SOP（标准作业程序）通常是人工操作的步骤清单，将其转化为 Skill 需要做“语义化”和“工程化”两层抽象：

1. **解读 SOP 文档**
   - 与业务专家访谈，理解每一步的业务含义、决策依据、异常处理方式。
   - 区分“必须步骤”和“可选步骤”，识别依赖关系和并行可能性。

2. **提取原子操作，映射为 Tool**
   - 将 SOP 中每个对系统/外部工具的操作（如“登录 CRM 系统”、“查询客户信息”）识别为潜在的 Tool。
   - 若这些 Tool 已存在，直接复用；否则先开发对应的 Tool（如 API 封装）。

3. **构建步骤流程**
   - 将 SOP 转化为流程图或 DAG，明确步骤顺序、分支条件、循环。
   - 例如，SOP 中的“若库存不足则查询替代仓库”转化为条件分支。

4. **封装业务规则**
   - 将 SOP 中隐含的业务规则（如“优先级高的订单优先处理”）显式化为代码逻辑或规则引擎。
   - 对于复杂规则，可使用决策表或与专家系统集成。

5. **添加工程化保障**
   - 在步骤间添加状态保存，支持断点续传（尤其是长流程）。
   - 设计补偿操作：若某步失败，如何回滚（如取消已创建的订单）。

6. **测试与验证**
   - 使用真实业务数据模拟运行，对比 Skill 输出与人工 SOP 执行结果的一致性。
   - 收集业务方反馈，迭代优化。

7. **沉淀为 Skill**
   - 将封装好的能力注册为 Skill，提供清晰的输入输出接口，隐藏内部复杂逻辑。
   - 编写业务友好的描述，让 Agent 或业务人员能理解何时使用。

### 3. 你会如何把异常处理、失败经验和人工确认点写进 skill？

Skill 在生产环境中必须能够应对各种异常，同时支持必要时的人工介入。以下是具体做法：

#### 3.1 异常处理机制

- **异常分类**：
  - **可重试异常**（网络超时、服务暂时不可用）→ 自动重试，采用指数退避，限制最大重试次数。
  - **不可重试异常**（参数错误、权限不足）→ 直接返回错误，附带明确错误码和建议。
  - **业务异常**（库存不足、会议冲突）→ 返回业务错误，并提供建议（如备选方案）。

- **重试策略**：
  - 在调用外部依赖时，使用统一的重试装饰器，配置最大重试次数、退避时间、重试条件（如仅对 5xx 错误重试）。
  - 对于长耗时操作，设计异步任务队列，支持手动重试。

- **超时与熔断**：
  - 为每个外部调用设置超时（如 5 秒），避免单个依赖拖垮整个 Skill。
  - 实现熔断器（Circuit Breaker）：当某依赖错误率超过阈值时，暂时熔断，快速返回错误，避免雪崩。

- **回滚与补偿**：
  - 对于多步操作，记录已执行的步骤。当某步失败时，自动执行补偿操作（如取消已创建的订单、释放已占用的资源）。
  - 使用 Saga 模式或事务日志实现最终一致性。

#### 3.2 失败经验的沉淀

- **错误码体系**：
  - 定义统一的错误码规范，区分系统错误、业务错误、用户输入错误。
  - 每个错误码附带建议的补救措施，供 Agent 或上层决策。

- **经验库**：
  - 将常见失败案例记录到知识库中，包括触发条件、根本原因、解决方案。
  - 当类似情况再次发生时，Agent 可检索经验库，快速决策（如“之前此类错误尝试过方案 A 无效，改用方案 B”）。

- **自我诊断**：
  - Skill 内部可集成自检模块，在返回错误时附上诊断信息（如“调用 X API 返回 500，可能服务异常”），帮助调用方或运维定位。

#### 3.3 人工确认点设计

- **识别需要确认的场景**：
  - **高风险操作**：支付、删除数据、发送重要邮件。
  - **信息不足或歧义**：用户意图模糊，需澄清。
  - **超出自动处理能力**：如需要人工判断的复杂情况。
  - **用户主动要求**：某些用户希望在关键步骤确认。

- **确认点实现方式**：
  - **同步确认**：Skill 在执行到关键步骤时，返回一个“等待确认”状态，包含待确认信息和建议选项。上层 Agent 暂停执行，向用户展示确认请求，收集用户选择后，携带确认结果再次调用 Skill（或专用 confirm 接口）继续执行。
  - **异步通知**：对于长耗时任务，可通过邮件、App 推送通知用户确认，用户点击链接后回调继续。

- **确认信息设计**：
  - **明确告知**：清晰说明即将执行的操作、影响范围、可选项。
  - **提供默认建议**：如“推荐方案 A（立即执行）”、“方案 B（稍后提醒）”、“取消”。
  - **超时处理**：若用户长时间未确认，可设置超时后自动执行默认安全动作（如取消或暂缓）。

- **示例代码结构**：
```python
def book_room_skill(params):
    # 步骤1: 检查权限
    if not has_permission(params.user):
        return error("PERMISSION_DENIED", "需要管理员权限")
    # 步骤2: 查询空闲会议室
    rooms = query_rooms(params.date, params.time)
    if not rooms:
        # 返回业务错误，附建议
        return error("NO_ROOM", "无空闲会议室，建议更换时间", suggestions=alternative_times)
    # 步骤3: 选择最优会议室
    selected = select_best(rooms)
    # 步骤4: 需要用户确认（高风险操作）
    confirm_info = {
        "room": selected.name,
        "time": params.time,
        "cost": selected.cost
    }
    # 返回“等待确认”状态，而非直接执行
    return {"status": "need_confirmation", "data": confirm_info, "confirm_id": generate_id()}
```

通过以上设计，Skill 不仅具备健壮性，还能在必要时与人类协作，真正成为企业级可用的能力单元。

| 失败经验编码   | 记录 → 聚类 → 提取模式 → 生成防御策略 → 更新 Skill           |
| 人工确认点     | 触发条件（风险/置信度/不可逆/合规/复杂/用户要求）、对话框设计、接管流程、返回机制 |

## 五、Skill 怎么触发、怎么评估

### 1. skill 是如何被触发的？如何避免误触发和漏触发？

**触发方式**  
Skill 的触发通常由 Agent 的**意图识别与路由模块**负责。常见触发方式包括：

- **关键词/实体匹配**：用户输入中包含与 Skill 强相关的关键词或实体（如“预订会议室”、“生成周报”），通过规则或正则快速匹配。
- **语义匹配**：将用户输入与 Skill 的描述（如名称、功能、触发示例）进行向量相似度计算，超过阈值则触发。适用于自然语言表达多样的场景。
- **分类器/LLM 决策**：训练一个轻量分类器，或直接调用 LLM 判断当前用户意图应匹配哪个 Skill。LLM 方式更灵活，但成本高。
- **状态触发**：当 Agent 处于特定状态（如任务进行中、等待用户补充信息）时，某些 Skill 可被自动触发（如“重新发送验证码”）。

**避免误触发（不该触发时触发了）**  
- **多级过滤**：先快速规则过滤，再语义匹配，最后通过前置条件校验（如检查必要参数是否齐全、权限是否满足）来确认。
- **上下文校验**：结合对话历史判断，例如“预订”在“我想了解预订流程”中不应触发实际预订 Skill。
- **用户确认机制**：对于高风险或模糊匹配，Skill 不直接执行，而是返回“等待确认”状态，由 Agent 向用户询问“您是想预订会议室吗？”，用户确认后再执行。
- **负例训练**：在分类器或 LLM 的触发判断中，加入负例样本，学习何时不应触发。

**避免漏触发（应该触发时没触发）**  
- **扩大匹配范围**：使用同义词、别名扩展，或通过向量检索匹配语义相近的描述。
- **降级策略**：当主触发方式失效时，可回退到更宽松的规则或让 LLM 再次判断。
- **用户主动调用**：提供明确的 Skill 调用指令（如“使用预订会议室 Skill”），让用户显式触发。
- **动态学习**：记录历史中用户实际意图与触发结果的对比，持续优化触发模型。

### 2. 多个 skill 同时匹配时，应该怎么路由和选择？

当多个 Skill 同时满足触发条件时，需要路由机制决定最终调用哪个（或哪些）。常见策略：

- **优先级路由**  
  - 为每个 Skill 预设静态优先级（如业务重要性、权限等级），优先匹配高优先级 Skill。  
  - 动态优先级：根据历史成功率、用户偏好、当前上下文实时计算优先级。例如用户最近频繁使用的 Skill 权重更高。

- **LLM 作为路由器**  
  - 将匹配到的候选 Skill 列表（名称、描述、适用场景）连同用户输入一起提供给 LLM，让模型选出最合适的 Skill。优点是可利用语义理解处理复杂情况，缺点是有成本和延迟。

- **多级匹配与互斥规则**  
  - 某些 Skill 之间存在互斥（例如“预订会议室”和“查询会议室空闲”不应同时执行）。可预先定义互斥关系，当同时匹配时，根据规则只选一个。
  - 若 Skill 可组合，则允许并行或顺序执行多个 Skill（如先“查询航班”再“预订机票”）。

- **用户选择**  
  - 当多个 Skill 高度匹配且无法自动区分时，Agent 可向用户提供选项（如“您是想预订会议室，还是查询会议室信息？”），由用户选择。

- **上下文融合**  
  - 若多个 Skill 分别对应同一任务的不同子步骤，Agent 可规划一个包含多个 Skill 的执行计划，而非仅选其一。例如“生成周报”可能需要先后调用“提取数据”和“格式化输出”两个 Skill。

**工程实践**：通常采用“轻量规则 + LLM 辅助”的混合路由：先通过规则或分类器筛选出 Top-K 候选，再用 LLM 进行最终选择，兼顾效率与准确性。

### 3. 你会如何评估一个 skill 是否有效？看哪些核心指标？

评估 Skill 的有效性需要从业务价值、技术质量、成本效益三个维度综合考量。

#### 3.1 业务指标
- **任务成功率**：Skill 被调用后，成功完成预期目标的比例。根据输出中的 `status` 字段统计。需区分“业务成功”和“技术成功”（例如工具返回成功但业务逻辑未完成）。
- **用户满意度**：可通过用户反馈（点赞/踩）、满意度调查或间接指标（如用户是否继续使用）衡量。
- **业务影响**：如“预订会议室” Skill 带来的会议组织效率提升、取消率降低等。

#### 3.2 技术指标
- **调用量**：反映 Skill 的复用程度。
- **响应时间**：平均延迟、P95 延迟，影响用户体验。
- **错误率**：按错误类型分类（参数错误、依赖超时、业务异常等），统计各类错误占比。
- **重试率**：因临时错误触发的自动重试比例，过高可能说明依赖不稳定。
- **熔断次数**：触发熔断保护的频率，反映外部依赖健康状况。
- **回滚/补偿频率**：因执行失败而触发补偿操作的次数，反映逻辑健壮性。

#### 3.3 成本与资源
- **Token 消耗**：若 Skill 内部调用 LLM，需统计每次调用的 token 量。
- **API 调用成本**：Skill 调用的外部 API 费用。
- **计算资源**：CPU/内存占用，尤其是并发场景。

#### 3.4 可维护性指标
- **平均修复时间（MTTR）**：从发现故障到修复上线的时间。
- **变更频率**：Skill 迭代版本的速度，反映业务变化活跃度。
- **测试覆盖率**：单元测试、集成测试的覆盖程度，影响长期稳定性。

#### 3.5 评估方法
- **A/B 测试**：将流量分流到不同版本的 Skill，对比核心指标。
- **用户行为分析**：观察用户调用 Skill 后的行为（如是否继续交互、是否完成任务）。
- **日志分析**：定期分析错误日志，识别高频错误和优化点。
- **定期复盘**：与业务方、产品经理共同回顾 Skill 的复用情况与业务价值，决定是否继续维护、升级或废弃。

通过以上多维度评估，可以持续优化 Skill 的质量，确保其真正服务于业务目标。

| 问题          | 核心要点                                                     |
| ------------- | ------------------------------------------------------------ |
| 触发机制      | 三层级联：L1 快速过滤（关键词/正则）→ L2 语义匹配（向量检索）→ L3 精确决策（LLM 重排） |
| 防误触发      | 否定模式、高置信度阈值、混淆检测、上下文验证                 |
| 防漏触发      | 隐式模式、语义扩展、实体推断、兜底 Skill                     |
| 多 Skill 路由 | 冲突检测（互斥/依赖/组合）→ 优先级裁决（置信度+偏好+上下文+效率+业务）→ 决策执行 |
| 优先级评分    | 基础置信 × 用户偏好 × 上下文连续 × 资源效率 × 业务优先级     |
| 评估指标      | HEART+：满意度、参与度、采纳度、留存、任务成功、效率；技术质量：触发/执行/输出/性能 |
| 健康评分      | 加权综合，A/B 测试验证，持续监控趋势                         |

## 六、Skill 怎么上线、治理和安全

### 1. skill 上线后如何做版本管理、灰度发布和回滚？

**版本管理**  
- **语义化版本**：采用 `MAJOR.MINOR.PATCH` 规范，如 `1.2.3`。  
  - **MAJOR**：不兼容的 API 变更。  
  - **MINOR**：向后兼容的功能新增。  
  - **PATCH**：向后兼容的问题修复。  
- **代码与配置**：所有 Skill 代码、配置文件、依赖清单（如 `requirements.txt`）均纳入 Git 仓库，每次发布打标签，并维护 `CHANGELOG.md` 记录变更。  
- **接口版本**：Skill 的输入/输出 JSON Schema 也应版本化，并尽量保持兼容性。大版本升级时，允许新旧版本并存，逐步迁移调用方。  
- **注册中心**：Skill 的元数据（名称、版本、描述、接口、负责人、依赖）存储于企业服务目录，支持查询和版本对比。

**灰度发布**  
- **流量分流**：通过 API 网关或服务网格（如 Istio）配置路由规则，按比例（如 1% → 5% → 20% → 50% → 100%）或按条件（如特定用户、IP 段）将请求导向新版本。  
- **内部先行**：先在预发环境由测试团队验证，再在线上向内部员工开放，最后逐步扩大至外部用户。  
- **A/B 测试**：同时运行新旧版本，对比业务指标（成功率、用户满意度）。  
- **监控与自动止损**：对关键指标（成功率、延迟、错误率、CPU/内存）设置阈值，一旦异常自动将流量切回稳定版本，并触发告警。

**回滚**  
- **一键回滚**：通过发布平台（如 Kubernetes 的 Rollback）将版本回退至上一个稳定版本，同时更新路由权重。  
- **数据兼容性**：若新版本修改了数据结构（如数据库 Schema），回滚时需确保旧版本能处理新数据，或设计补偿脚本。建议升级时尽量保持向后兼容。  
- **快照与备份**：对 Skill 依赖的数据定期备份，便于紧急恢复。

**环境隔离**：保持开发、测试、预发、生产环境独立，版本逐级推进。

---

### 2. 企业内部如何治理 shared skill 和项目私有 skill？

**分类与定义**  
- **Shared Skill**：企业级通用能力，跨项目复用，由平台团队或治理委员会统一管理，需遵循企业标准（接口规范、安全要求、文档）。  
- **Project Private Skill**：特定项目或业务线专属，由项目团队自行开发维护，但仍需遵守基础技术规范（如日志、监控、安全基线）。

**注册与发现**  
- **企业 Skill 目录**：建立统一的内部注册中心，记录每个 Skill 的元数据（名称、版本、负责人、描述、输入输出、依赖、权限等级、调用示例）。  
- **可见性控制**：Shared Skill 对所有项目可见；Private Skill 仅对所属项目成员可见，可通过标签或访问控制列表隔离。

**生命周期管理**  
- **创建**：提交 Skill 申请，需通过接口规范审查、安全评估、代码质量检测（如单元测试覆盖率）。  
- **发布**：经过测试后，由平台团队（对 shared）或项目负责人（对 private）审核发布至目录。  
- **废弃**：标记为 deprecated，给出替代方案，设置过渡期（如 6 个月），之后下线并通知调用方迁移。

**调用审计**  
- 所有 Skill 调用均需记录日志（调用方、时间、参数、结果、耗时），便于分析调用关系和排查问题。  
- 对 Shared Skill 的调用量、成功率进行统计分析，辅助优化。

**依赖管理**  
- Shared Skill 应避免绑定特定私有环境，确保可移植性。若依赖其他 Shared Skill，应在元数据中显式声明依赖关系，并保证依赖版本兼容。

**权限控制**  
- 调用 Shared Skill 需申请权限（尤其是高权限 Skill），由负责人审批。  
- Private Skill 的权限由项目管理员自行控制。

### 3. 第三方 skill 或高权限 skill 有哪些安全风险，怎么防？

**主要安全风险**  
- **数据泄露**：第三方 Skill 可能将敏感信息（用户数据、业务数据）外传至未经授权的外部服务。  
- **权限滥用**：高权限 Skill 可能执行越权操作（如删除生产数据、修改配置、访问未授权系统）。  
- **供应链攻击**：恶意代码或依赖库漏洞被植入，在运行时窃取数据或破坏系统。  
- **注入攻击**：通过恶意输入（如 SQL 注入、命令注入）利用 Skill 漏洞执行非预期操作。  
- **权限提升**：攻击者利用 Skill 漏洞获取更高权限，进而控制其他系统。  
- **逻辑漏洞**：业务逻辑缺陷（如重复支付、无限制提现）造成资金损失或业务错误。

**防护措施**

| 风险类别       | 防护措施                                                     |
| -------------- | ------------------------------------------------------------ |
| **数据泄露**   | - 对 Skill 输入/输出进行严格脱敏（如手机号、身份证掩码）。<br>- 限制 Skill 的网络访问（仅允许白名单域名）。<br>- 敏感数据在传输和存储时加密。 |
| **权限滥用**   | - 遵循最小权限原则，仅授予 Skill 执行任务所需的最小权限（如只读数据库、只写日志）。<br>- 使用 IAM 角色或 API 密钥绑定具体操作，避免使用超级用户凭证。<br>- 定期审计 Skill 的权限配置，移除冗余权限。 |
| **供应链攻击** | - 对第三方 Skill 进行代码审计、依赖库漏洞扫描（如 SCA 工具）。<br>- 优先选择官方或知名供应商，要求提供安全合规证明。<br>- 使用可信镜像仓库，限制外部依赖的引入。 |
| **注入攻击**   | - 对 Skill 的所有输入参数进行严格校验（类型、长度、范围、白名单）。<br>- 使用参数化查询（PreparedStatement）防止 SQL 注入。<br>- 避免动态拼接命令，使用安全 API 替代系统调用。 |
| **权限提升**   | - 将高权限 Skill 运行在隔离环境（容器、沙箱），限制其访问宿主机资源。<br>- 采用安全容器（如 gVisor）或虚拟化技术隔离。<br>- 定期进行渗透测试，发现并修复漏洞。 |
| **逻辑漏洞**   | - 对高风险操作（支付、删除）强制要求用户二次确认（human-in-the-loop）。<br>- 设计幂等性，防止重复执行。<br>- 记录完整的操作审计日志，支持回滚和追溯。 |
| **通用监控**   | - 对 Skill 的调用行为进行实时监控（频率、来源 IP、参数模式），设置异常告警（如短时间内大量调用、参数异常）。<br>- 实施限流、熔断，防止资源耗尽。 |

**特别针对第三方 Skill**：  
- 要求第三方提供安全自评报告或第三方安全审计报告。  
- 将第三方 Skill 部署在独立的、受控的环境，与核心系统隔离。  
- 建立应急响应机制，一旦发现安全问题可立即下线该 Skill。

通过以上多层次防护，可以显著降低 Skill 带来的安全风险，保障企业应用的安全稳定运行。
