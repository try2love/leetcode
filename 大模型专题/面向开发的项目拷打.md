# 回答

## 一、项目总览与架构

### 1. 你负责的这个系统，核心要解决什么业务问题？

我负责的是一个**规则驱动的文本检索与研判后端系统**。它要解决的问题不是单纯“查数据”，而是把规则检索、上下文拼接、过滤、RAG 增强、模型判定、MySQL 落库、人工标注和结果导出串成一条可上线的业务链。

### 2. 这个系统的输入、处理流程、输出分别是什么？

输入主要是**规则配置**和外部 ES 中的原始文本数据。处理流程是：规则转 ES 查询 → 检索命中 → 过滤词过滤 → 上下文补全 → 根据 method 进入纯检索、异常检测或 RAG/意图识别分支 → 结果落库并进入标注与导出链路。输出是**按规则组织的研判结果、任务状态、人工标注数据和导出结果**。

### 3. 为什么你们要把它做成一个后端服务，而不是离线脚本？

因为这个系统不是一次性实验，而是**长期运行的业务系统**。它需要规则管理、任务调度、状态查询、人工标注、结果导出、重复执行和线上维护，这些都更适合做成服务，而不是分散的脚本。

### 4. 你这个系统里，FastAPI 主要承担什么角色？

FastAPI 在这里更像**业务编排层的服务外壳**。它负责对外暴露规则管理、任务触发、状态查询、标注和导出接口，把内部的 ES 检索、算法调用和 MySQL 落库能力包装成统一后端服务。

### 5. 整个链路里，哪些是你自己服务内完成的，哪些是依赖外部服务完成的？

服务内完成的主要是**规则解析、任务编排、过滤、上下文拼接、任务状态管理、结果表写入、人工标注与导出**。外部依赖主要是 **ES 检索、MySQL 存储、远程 LLM 推理、异常检测接口、实体识别接口**；另外 embedding + FAISS 是项目内自带的本地能力。

### 6. 这个系统为什么会强依赖 ES、MySQL、LLM 服务和其他算法服务？

因为它本质上是一个**业务编排后端**，不是把所有计算都塞进自己进程里。ES 负责高效检索原始数据，MySQL 负责规则和结果持久化，LLM 和其他算法服务负责模型能力，这样各模块职责更清晰，也更容易替换。

### 7. 你这个系统是单体应用、微服务，还是业务编排层？为什么这么设计？

当前更准确地说，它是一个**单体部署的业务编排层**。不是典型微服务，因为大部分代码在一个服务里；但它也不是孤立单体，因为核心能力大量依赖外部服务。这样设计的原因是：项目早期优先保证业务闭环和上线效率。

### 8. 服务启动时为什么要做数据库初始化、规则同步、模型初始化、定时任务注册，而不是懒加载？

因为这类系统的特点是**启动后要马上可用**，而且很多能力不是按单次请求触发的，比如定时任务和规则同步。把这些初始化放在启动阶段，可以把依赖问题、配置错误、索引未就绪等问题尽早暴露，而不是等到第一次请求时才出故障。

### 9. 如果让你画系统架构图，你会怎么拆模块？

我会拆成六层：**API 层、任务编排层、规则与配置层、检索与上下文层、算法调用层、存储与结果管理层**。外部再挂上 ES、MySQL、远程 LLM/异常检测/NER 服务，本地则挂 embedding + FAISS。

### 10. 你项目里最核心的模块是哪一个？为什么不是 HTTP 接口层？

最核心的是**围绕规则任务的处理流水线**，也就是把规则转查询、执行检索、补上下文、调用算法、落库的那条链路。HTTP 接口只是触发和查看入口，真正决定业务价值的是内部编排逻辑，不是路由本身。

### 11. 规则管理、任务调度、结果管理、人工标注，这几块之间是什么关系？

规则管理定义了“查什么、怎么判”；任务调度负责“什么时候跑”；结果管理负责“跑出来以后怎么存、怎么查”；人工标注负责“对结果做反馈修正，并反哺后续优化”。它们组成了一个**完整闭环**，不是四块孤立功能。

### 12. 你觉得这套系统现在最大的工程短板是什么？

最大的短板是**业务逻辑耦合偏高，代码层次不够清晰**。它已经能支撑真实业务，但工程化程度还停留在“可用的项目型系统”，还没演进成标准化平台。

### 13. 如果要把这套系统从“项目型系统”演进成“平台型系统”，你第一步会改哪里？

我第一步会改**模块边界和配置管理**。先把接口层、任务层、外部依赖层、DAO 层拆开，再把当前 config 和本地 yaml 的耦合关系收敛掉，否则后面多人协作和多环境部署会越来越难维护。

## 二、接口设计与 FastAPI 后端开发

### 14. 你 FastAPI 的路由是怎么组织的？哪些接口是给前端/运营用的，哪些是内部控制接口？

我会按业务域来组织，例如：**规则管理、任务执行、结果查询、标注管理、导出管理**。给前端/运营用的主要是规则 CRUD、结果查询、标签修改、导出；内部控制接口主要是手动触发任务、取消任务、查看任务执行状态等。

### 15. 你如何定义一个规则创建/修改接口的请求和响应结构？

请求里我会放**规则名称、检索条件、时间范围、过滤词、method、激活状态、调度信息**等字段；响应里返回规则 ID、状态、版本或更新时间。核心原则是：外部协议稳定，内部执行细节不要直接泄漏到接口层。

### 16. 规则管理接口如何保证参数合法性？

第一层用 **Pydantic** 做字段校验，保证必填项、类型、枚举值正确；第二层做业务校验，比如规则名是否合法、是否重名、method 是否受支持、过滤配置是否可执行。这样能把输入错误尽量拦在入口。

### 17. 你有没有做接口层和业务逻辑层的分离？如果没完全分，你怎么看这件事？

当前版本是**部分分离，但不彻底**。接口层负责接收参数和返回结果，核心逻辑更多集中在业务模块里；不过整体耦合仍然偏高。这个在项目早期提高了落地速度，但后期确实会增加维护成本。

### 18. 你项目里哪些接口是同步返回，哪些适合做成异步任务？

像规则查询、结果查询、标注修改这类操作适合同步返回。像“执行某条规则的日常查询”“批量处理历史数据”“导出大批量结果”这种长任务，更适合做异步任务并返回 task_id。

### 19. 为什么“手动触发规则执行”不适合直接在接口请求里跑完整链路？

因为完整链路会涉及 ES 检索、算法调用、结果落库，时间不可控，而且可能持续几分钟。放在同步请求里会造成连接长时间占用，也不利于前端查看进度、取消任务和重试。

### 20. 如果一个任务执行要几分钟，你怎么设计 API 才不阻塞？

我会把任务提交和任务执行解耦。接口只负责**创建任务并返回 task_id**，后续由后台 worker 执行，前端通过状态查询接口拿到进度、结果和失败原因。

### 21. 任务状态查询接口需要返回哪些字段？

至少要有：**task_id、规则名、任务状态、开始时间、当前阶段、进度百分比、已处理数量、错误信息、是否可取消、完成时间**。这样业务方能明确知道任务在哪一步。

### 22. 任务取消是怎么做的？是真取消还是逻辑标记取消？

更稳妥的实现一般是**逻辑标记取消 + 执行链路定期检查取消标志**。因为很多外部调用不是瞬时可中断的，所以不是强杀线程，而是在阶段边界安全退出。

### 23. 如果两个用户同时触发同一条规则的同一天任务，你怎么避免重复执行？

我会在任务创建时做**唯一性约束**，例如按“规则 + 日期 + 任务类型”判断是否已有运行中任务。已有就直接返回现有任务或拒绝重复提交，避免重复打 ES、重复写库。

### 24. 你怎么处理接口幂等性？

查询类接口天然幂等；写操作我会靠**唯一键、任务去重、状态机约束**来保证。比如重复触发任务时，不是新建多条任务，而是复用或直接提示已有进行中任务。

### 25. 你有没有做鉴权、权限控制？如果现在没有，你会怎么补？

如果当前版本没有完整鉴权，我会如实说它更偏内网业务系统。继续演进时我会补 **用户身份、角色权限、规则级权限、操作审计**，至少区分“查看、触发、标注、导出、管理规则”几种权限。

### 26. 如果某个外部服务调用超时，接口应该返回什么，日志里记录什么？

同步接口要返回**明确可理解的错误码和错误信息**，异步任务则要把任务状态标记为失败或部分失败。日志里必须记录 request_id/task_id、外部服务名称、调用参数摘要、超时阶段、耗时和异常堆栈。

## 三、任务编排、异步执行与调度

### 27. 你的规则任务从触发到完成，完整生命周期是什么？

完整生命周期是：**提交任务 → 校验规则 → 进入队列/开始执行 → ES 检索 → 过滤与上下文拼接 → 进入对应算法分支 → MySQL 落库 → 更新索引表 → 标记完成/失败 → 可查询和导出**。

### 28. 定时任务是怎么注册的？服务重启后会不会丢任务？

当前做法是**服务启动时注册定时任务**。重启后定时任务定义会重新加载，但如果有“正在执行中的内存态任务”，纯内存实现下是可能丢失运行态的，所以后面更适合把任务状态持久化。

### 29. 任务执行过程中，进度是怎么维护的？

我会按阶段维护进度，比如“已完成检索、已完成上下文拼接、已处理多少条记录、已写入多少结果”。核心是让进度不是一个抽象百分比，而是能映射到具体业务阶段。

### 30. 任务取消的实现难点是什么？

难点在于**长链路 + 外部依赖 + 不可随意中断**。如果直接强停，容易造成中间状态不一致；所以更好的方式是在阶段节点检查取消标志，必要时先停止后续处理，再做状态收尾。

### 31. 为什么你需要异步任务队列，而不是简单开线程？

因为这不是一次性的轻量操作，而是会反复触发、执行时间长、需要状态管理和取消能力的业务任务。简单开线程虽然快，但在线上不利于统一管理任务生命周期，也不利于异常恢复。

### 32. 如果某条规则任务执行失败，你是整条失败、部分失败还是支持断点续跑？

当前版本更现实的是**整条失败或部分失败记录清楚**。如果继续演进，我会考虑按阶段或批次记录 checkpoint，支持从检索后、写库前等关键阶段继续跑。

### 33. 你如何避免定时任务重复触发？

我会做两层保护：**调度层去重 + 执行层幂等检查**。即使同一任务被意外触发两次，执行前也要再判断是否已有同 key 任务在运行。

### 34. 如果某个任务还没跑完，下一次调度时间又到了，怎么处理？

这要看业务要求。一般我会优先选择**跳过下一次触发并告警**，而不是并发跑两份，因为并发更容易打爆 ES 和下游算法服务，也可能造成结果重复。

### 35. 任务清理策略是怎么做的？为什么需要清理完成任务？

完成任务和历史失败任务如果一直不清，会让内存态管理和状态列表越来越臃肿。清理策略一般是保留最近一段时间的详细状态，老任务保留汇总信息或落持久化后再清。

### 36. 任务执行过程中，如果 ES 查到了很多数据，后续算法服务扛不住，怎么限流？

我会在任务内部做**分批处理 + 并发上限控制**。检索得到的大结果不能一下子全灌给下游，而是按批次送入算法分支，同时对外部服务设置连接数和请求并发上限。

### 37. 如果让你重构这一块，你会保留现在的方案还是换成 Celery / Kafka / 独立 worker？

如果规模继续扩大，我会考虑拆成**独立 worker + 持久化任务队列**。当前方案适合业务快速落地，但要支撑更稳定的长任务和多实例调度，Celery 或消息队列方案会更合适。

## 四、ES 检索与上下文拼接

### 38. 规则文件是怎么转换成 ES 查询的？

规则文件本质上描述了**关键词、字段、时间范围、过滤条件和执行 method**。服务会把这些配置解析成对应的 ES bool/query DSL，再发起检索请求。

### 39. 你为什么要先做规则高召回，再做后续研判，而不是一上来就让大模型判断？

因为大模型直接全量判定成本高、速度慢，而且不必要。先用规则做高召回，相当于把候选集缩小到业务关心的范围，再用 RAG 或模型做更精细的研判，成本和效果都更平衡。

### 40. ES 检索里你主要用了哪些条件？term、match、range、bool 这些你怎么选？

精确过滤一般用 **term**，文本匹配更偏 **match**，时间范围用 **range**，多条件组合用 **bool**。选择原则是：先分清字段类型，再决定用精确过滤还是分词匹配，避免一股脑都用 match。

### 41. 你如何控制召回和精度之间的平衡？

在这个系统里，前置规则层更偏**高召回**，后续模型层负责提精度。也就是说，我不会在 ES 层过早把候选筛得太死，否则后续再好的模型也救不回来。

### 42. 检索出来的数据为什么还需要过滤词过滤？

因为规则检索通常会带来很多噪声命中。过滤词是一个低成本、业务可解释的二次清洗手段，可以先去掉明显无效样本，减轻后续算法压力。

### 43. 上下文拼接的目的是什么？为什么不能只看单条文本？

很多文本单看一句话语义不完整，尤其是开放场景内容。补充前后文后，模型更容易理解语境，减少断章取义带来的误判，这也是 RAG 或意图识别效果提升的重要原因。

### 44. 上下文取多少合适？太长会有什么问题？

合适长度取决于业务和模型窗口，一般是“**能补足语义，但不把无关噪声带进来**”。太短会信息不足，太长会增加噪声、拉高 token 成本，也可能干扰检索增强效果。

### 45. 如果 ES 查询特别慢，你会从哪些方向排查？

我会先看**查询 DSL 是否合理、索引和 mapping 是否匹配、时间范围是否过大、是否命中过多字段、是否缺少合适索引**。然后再结合 ES 侧监控看是不是集群负载、热点分片或网络问题。

### 46. 如果某条规则把 ES 打得很重，你会怎么优化？

可以从三个方向做：**缩小时间窗口、优化查询条件、结果分批处理**。如果还是重，我会考虑预聚合、缓存部分查询结果，或者把大规则拆成多个可控子规则。

### 47. 你有没有考虑分页、scroll、search_after 之类的大结果集处理方式？

如果结果集很大，我会优先考虑**批量遍历而不是一次性拉全量**。scroll/search_after 的核心价值就是把大结果读取做成可控批次，避免单次查询过重和内存暴涨。

### 48. 如果 ES 返回的数据和 MySQL 最终结果不一致，你怎么排查？

先判断差异发生在哪一段：是 ES 原始命中不同，还是过滤/上下文/算法判定后被筛掉了，还是落库阶段丢了。排查时要用统一 task_id 把“检索数量、过滤数量、送模数量、落库数量”串起来。

## 五、RAG、Faiss、Memory 与 AI 组件后端化

### 49. 你项目里的 RAG 是为了解决什么问题？

RAG 主要解决的是**单条文本信息不足、模型缺少背景、纯 Prompt 判断不稳定**的问题。通过相似案例检索增强，模型能拿到更相关的背景信息，提高判定一致性。

### 50. 为什么要用 Qwen3-Embedding-0.6B 做向量化？

我的回答会是：它在效果、部署成本和本地可用性之间比较平衡。对于这个项目来说，embedding 模型不是越大越好，而是要在**召回质量、推理开销和工程可落地性**之间找到合适点。

### 51. 你的 Faiss 索引存的是什么内容？原始文本、结构化特征，还是联合编码结果？

当前更适合回答成：**存的是用于 RAG 检索增强的案例文本向量及其元信息映射**。也就是向量负责近邻搜索，真正参与拼接给模型的是对应的原始案例内容和必要 metadata。

### 52. Top-k 为什么这么选？k 变大或变小会有什么影响？

k 太小可能召回不到足够有效的相似案例，k 太大又会把噪声带进来、增加 token 开销。我的选择原则是通过离线验证，在“效果提升”和“噪声/成本上升”之间找平衡。

### 53. 向量知识库是怎么构建和更新的？

初始构建一般是先把已有高质量案例做 embedding，再写入 FAISS 和元数据映射。更新时可以做**增量写入 + 定期重建**，小规模更新直接追加，大规模变动时重建索引更稳。

### 54. 如果新增了大量人工标注数据，你如何增量更新索引？

我会先筛出**高置信、可作为案例库的数据**，做增量 embedding 后写入索引；如果更新量已经影响索引分布，我会安排离线重建，避免索引长期碎片化。

### 55. 你项目里的“Memory”如果映射到 Agent 场景，可以怎么理解？

可以把它理解成**可检索的外部记忆层**。在我的项目里，这层记忆更像规则结果、历史案例和人工标注组成的经验库；迁移到 Agent 场景，就是把这些内容组织成长期记忆和可检索上下文。

### 56. 你觉得规则结果表、人工标注结果、向量库三者之间是什么关系？

规则结果表是**原始业务产出**，人工标注结果是**高质量反馈信号**，向量库是**被挑选后用于增强检索的知识层**。三者不是重复关系，而是“数据产出 → 人工纠偏 → 知识沉淀”的闭环。

### 57. 如果让你给腾讯的读书 Agent 做 Memory 后端，你会怎么设计存储结构？

我会拆成两层：**结构化元数据层 + 向量检索层**。元数据层存用户、书籍、章节、时间、标签、来源、引用位置、会话关联；向量层存 chunk/摘要/笔记/问答等内容向量，并通过 doc_id、user_id、time 等做过滤。

### 58. 长期记忆和短期记忆在存储设计上有什么差别？

短期记忆更偏**会话态、实时更新、时效强**，通常需要快读快写；长期记忆更偏**稳定沉淀、可检索、可回溯**，要更重视索引设计、元数据过滤和版本管理。

### 59. 检索增强里，你怎么避免召回错误案例把模型带偏？

我会从三层控制：**embedding 质量、metadata 过滤、top-k 与 rerank 策略**。不是只要相似度高就直接喂给模型，还要结合时间、标签、来源质量、人工确认等信号做筛选。

### 60. 你做 RAG 的时候，有没有考虑 metadata 过滤、时间衰减、权限隔离？

如果面试官问到这点，我会说这是非常重要的演进方向。当前项目重点在业务闭环和效果提升，但如果做 Agent Memory，我一定会把 **metadata 过滤、时间权重、用户/租户隔离** 放进检索层设计里。

### 61. 如果向量库规模继续增长，Faiss 还能扛住吗？什么时候要换方案？

Faiss 在单机或中等规模下很好用，但数据量继续增长、更新频率变高、多租户需求上来之后，维护成本会变大。到那时我会考虑更适合在线检索与管理的向量数据库或分布式检索方案。

### 62. 你项目里的 RAG 更偏离线增强还是在线增强？为什么？

更偏**在线增强**。因为它是在规则检索命中后，为每条待研判记录即时补充相关案例，再交给模型判断，而不是离线预生成静态特征。

## 六、模型服务调用、LoRA 微调与推理编排

### 63. 你为什么要做 LoRA 微调，而不是只靠 Prompt 工程？

因为 Prompt 工程更适合快速验证，但面对垂直业务和稳定输出要求时，靠 Prompt 往往不够稳。LoRA 微调能把领域偏好和判定模式固化到模型里，提高一致性和可控性。

### 64. 你构造 SFT 数据的过程是什么？

我会回答成：先基于业务规则结果和人工反馈构造基础样本，再补充模型误判负例和对抗性样本。核心目标是让数据覆盖**正常样本、边界样本和高混淆样本**，避免训练出来的模型只会做简单分类。

### 65. 正样本、负样本、模型误判负例分别起什么作用？

正样本教模型“什么是目标模式”，负样本帮助模型学会排除常见噪声，模型误判负例则专门用来**纠正模型原本最容易犯的错误**。这三种数据一起用，模型边界会更清晰。

### 66. 微调后你怎么验证模型真的变好了，而不是过拟合了？

我会保留独立验证集，重点看**准确率、召回率、误报率和真实业务抽样效果**。另外还会看模型在高混淆样本上的表现，如果只是训练集指标很好、线上抽样不稳，那就说明可能过拟合了。

### 67. 推理服务为什么放远程，而 embedding 和 Faiss 放本地？

因为推理服务往往更重、资源更贵，也更适合统一管理和复用；而 embedding + Faiss 更适合作为项目内的轻量本地能力，响应快，也便于直接参与 RAG 流程。

### 68. “本地轻量模型 + 远程推理服务”的混合模式有什么好处和问题？

好处是**本地可控、响应快、成本低**，同时把重推理交给远端统一服务，减少本地资源压力。问题是链路变长，对网络和远程服务稳定性更敏感，排障也更复杂。

### 69. 你调用外部 LLM 服务时，怎么处理超时、重试和失败降级？

我会设置**合理超时、有限次数重试、明确错误分类**。如果是核心链路，会考虑降级到纯规则/纯检索结果或直接记录失败状态；绝不会无限重试，否则容易把整个系统拖垮。

### 70. 如果 LLM 服务不稳定，你的主链路还能不能继续跑？

取决于业务要求。对当前系统来说，可以保底做成**部分可运行**：即检索、过滤、落原始结果仍能完成，但依赖 LLM 的研判结果要么缺失，要么标记失败并待重跑。

### 71. 微调训练出来的新版本模型怎么接入线上？

我会做**版本化接入**。先在测试环境验证效果和兼容性，再通过配置切换或灰度流量接入新模型，保留旧版本回滚能力，而不是直接覆盖。

### 72. 你如何做模型版本管理？

至少要记录：**模型版本号、训练数据版本、训练时间、评估指标、上线时间、回滚记录**。这样出了问题能追溯，不会只知道“最近换过模型”，但不知道换了什么。

### 73. 如果线上效果下降，你怎么判断是检索问题、特征问题还是模型问题？

我会按链路拆：先看**ES 命中和上下文是否异常**，再看 RAG 召回是否偏、最后看模型输出分布和误判样本。也就是说，不会直接把锅甩给模型，而是先确认前面的输入是不是已经变坏了。

### 74. 如果腾讯追问“你有没有做过真正的训练工程”，可能会问你训练数据准备、loss 观察、checkpoint 管理、验证集设计、回滚策略这些，你分别怎么答？

我的答法是：我做过的是**偏业务落地的训练工程**，核心在数据构造、验证和接入，而不是超大规模训练平台。数据准备上重视正负样本和平衡性；训练中观察 loss 和验证集指标；checkpoint 只保留关键版本；验证集必须独立；上线时一定保留旧版可回滚。

## 七、MySQL 设计与数据建模

### 75. 你的 rules 表、result_index 表分别存什么？

**rules 表**存规则本身，包括规则名、配置、method、状态和调度信息。**result_index 表**更像汇总索引，用来记录每条规则每天的结果概览、统计信息和对应结果表。

### 76. 为什么结果不是统一放一张大表，而是按规则动态建表？

因为项目早期更关注**快速落地和按规则隔离管理的直观性**。每条规则一张结果表，查询、导出和按规则维护都更直接，业务侧也容易理解。

### 77. 动态建表这个方案的优点和缺点是什么？

优点是**规则隔离清晰、单表逻辑简单、按规则查数据方便**。缺点是随着规则增多，表数量会膨胀，迁移、统计、统一治理和权限管理都会越来越麻烦。

### 78. 随着规则越来越多，表越来越多，会带来什么问题？

首先是**库表管理复杂度上升**，其次是统一查询和统计变难，再就是后续 schema 演进成本更高。简单说，前期省事，后期会慢慢欠下工程债。

### 79. 如果让你重构数据库设计，你会不会改成统一结果表 + rule_id 分区/索引？

如果系统长期发展，我会认真考虑这个方向。统一结果表配合 **rule_id、date、status、label** 等索引，能更适合平台化治理，但前提是要评估现有查询模式和数据量，不会盲目重构。

### 80. 你规则名直接参与表名拼接时，怎么避免 SQL 注入或非法命名？

表名不能直接信任外部输入，必须做**白名单化/规范化处理**。比如只允许字母数字下划线，并把业务规则名映射成安全内部表名，而不是原样拼接 SQL。

### 81. 结果表上你建了哪些索引？为什么这么建？

我会优先给**日期、主键/业务唯一键、标签状态、查询高频字段**建索引。原则是按真实查询路径建，而不是看见字段就加索引，因为索引太多也会拖慢写入。

### 82. 你最常见的查询条件是什么？按规则查、按日期查、按标签查，还是组合查？

更常见的是**规则维度 + 日期维度 + 标签/状态维度**的组合查询。因为业务方通常不是随便扫全表，而是看某条规则在某天或某段时间的命中和标注情况。

### 83. result_index 这种汇总索引表解决了什么问题？

它解决的是**“先快速定位，再精查明细”**的问题。很多时候业务方不需要先扫所有结果表，而是先通过汇总表看到哪条规则哪天有多少数据、状态如何，再点进去查明细。

### 84. 人工标注、批量改标签、跨日期查询这类操作，SQL 是怎么写的？

这类操作本质上是**update + 条件过滤 + 分页查询**的组合。关键不在 SQL 语法本身，而在于要控制好 where 条件、事务范围和批量操作规模，避免误改和锁表。

### 85. 如果某天某条规则命中了几十万条数据，写库怎么保证效率？

我不会逐条 insert，而是做**批量写入**，必要时分批提交。这样能显著降低网络往返和事务开销，也更符合大批量结果入库场景。

### 86. 批量 insert 和逐条 insert 有什么区别？

批量 insert 的优势是**吞吐更高、网络开销更低、事务管理更集中**。逐条 insert 实现简单，但在大规模写入场景下性能差很多。

### 87. 事务边界你是怎么定的？

我会尽量把事务边界控制在**单批次、单业务原子操作**里。比如一批结果写入可以作为一个事务，但不会把“检索 + 模型调用 + 全量写库”放进一个超大事务。

### 88. 哪些操作需要事务，哪些不应该随便开大事务？

像规则创建/更新、批量写入某一批结果、批量标签修改这类需要事务保证一致性。ES 检索、外部模型调用这类耗时操作绝不能包进大事务，否则锁持有时间太长。

### 89. 如果数据库连接池打满了，你会怎么排查？

先看是不是**连接泄漏、慢 SQL、事务未提交、并发突增**。然后结合日志和监控看连接生命周期，确认是应用层没释放，还是数据库本身处理不过来。

### 90. 如果慢 SQL 很多，你怎么分析和优化？

我会先抓**最慢、最频繁、最影响主链路**的 SQL，分析执行计划，看有没有走索引、扫描行数是否异常、排序/临时表是否过重。然后再做索引优化、SQL 改写或查询方式调整。

### 91. 你有没有遇到过字段设计不合理、后期迁移很痛苦的情况？

这类问题很常见，尤其是项目早期追求快的时候。我的经验是：**核心主键、时间字段、状态字段、关联字段一定要早想清楚**，否则后面重构数据库会比重构代码更痛。

## 八、Linux、部署、Docker 与运行环境

### 92. 你平时怎么在 Linux 上部署和排查服务？

我通常会在 Linux 上做**代码拉取、依赖安装、配置切换、服务启动、日志查看、进程检查和资源排查**。出现问题时先确认进程、端口、配置、依赖连通性，再进入应用日志层排查。

### 93. 你会用哪些命令看 CPU、内存、磁盘、网络、进程？

常用的有：`top/htop` 看 CPU 和内存，`free -h` 看内存，`df -h` 看磁盘空间，`du -sh` 看目录占用，`ps -ef` 看进程，`netstat` 或 `ss` 看端口与连接，`tail -f` 看日志。

### 94. 服务突然不可用时，你的第一反应排查步骤是什么？

第一步看**进程还在不在、端口还在不在监听**；第二步看应用日志有没有报错；第三步看依赖服务如 MySQL、ES、LLM 是否可连通；最后再看机器资源是否耗尽。

### 95. 你 Dockerfile 里为什么采用 wheelhouse 离线安装？

因为这样更适合**内网、受限网络或依赖下载不稳定**的环境。先在宿主机打 wheel，再在镜像里离线安装，构建更可控，也减少线上临时拉依赖的风险。

### 96. 这种部署方式适合什么场景？

适合**内网部署、对可重复构建要求高、对外网依赖受限**的场景。尤其是业务系统要交付到固定环境时，这种方式比每次在线 pip 安装更稳定。

### 97. 你现在的 Docker 化为什么只是“后端服务镜像化”，不是“整套系统容器编排化”？

因为当前镜像里只封装了**FastAPI 后端进程**，并没有把 ES、MySQL、远程 LLM、异常检测服务一起纳入编排。也就是说，它解决的是“服务怎么打包和部署”，不是“全链路依赖如何一键拉起”。

### 98. 容器里运行的到底是什么？外部依赖怎么接入？

容器里运行的是 **uvicorn 启动的 FastAPI 应用**。外部依赖通过配置文件里写的地址访问，也就是容器启动后仍然要依赖外部网络连到 ES、MySQL 和各类算法服务。

### 99. config.yaml 现在是靠挂载或替换实现环境切换，这种方式有什么风险？

风险主要是**人为操作错误、配置漂移和环境不一致**。开发、测试、生产如果都靠手工替换 config，很容易出现“代码没变，但配置导致行为不同”的问题。

### 100. 如果要做 dev / test / prod 环境隔离，你会怎么改配置管理？

我会把配置拆成**环境变量 + 分环境配置文件 + 敏感信息独立管理**。核心目标是：代码同一份，环境靠配置区分，敏感信息不直接写死在仓库里。

### 101. 为什么你现在没有 docker-compose / k8s？如果以后要上，会先做什么改造？

当前主要是项目型交付，优先把业务链路跑通，所以没先上完整编排。以后如果要上，我会先改**配置管理、健康检查、日志输出规范和依赖初始化方式**，否则即使放进 k8s 也不好维护。

### 102. 服务启动命令为什么是 uvicorn app:app？单 worker 和多 worker 有什么差别？

因为入口就是 app.py 里的 FastAPI 实例。单 worker 简单、状态一致性好；多 worker 能提高并发，但如果内部还有内存态任务或本地状态，就要小心多进程一致性问题。

### 103. 如果服务在容器里频繁重启，你怎么判断是应用挂了、健康检查挂了还是依赖不可用？

我会先看**容器退出码和应用日志**，判断是进程异常退出还是被编排层杀掉。然后再看健康检查失败原因，以及应用在启动阶段是不是因为 MySQL/ES/模型初始化失败而退出。

### 104. 你有没有做过日志采集和日志轮转？

如果当前项目没有完整日志平台，我会如实说现阶段以**文件日志和手工查看为主**。继续演进时一定会加日志轮转和集中采集，否则线上排障成本会越来越高。

### 105. 如果镜像变得越来越大，你会怎么优化？

我会从三方面优化：**精简基础镜像、清理无用依赖、区分构建层和运行层**。如果有重模型文件，还要考虑是否应该挂载或独立管理，而不是全塞进镜像。

## 九、稳定性、监控、日志、故障排查

### 106. 你上线后最常看的监控指标是什么？

我最关注的是：**任务成功率、接口耗时、5xx/超时率、数据库连接数、外部服务调用成功率、机器 CPU/内存**。因为这个系统的故障很多不是单点崩，而是链路里某一段变慢或失败。

### 107. 你这个系统最关键的日志字段有哪些？

至少包括：**request_id、task_id、rule_name、method、阶段名称、耗时、外部依赖名称、错误信息、处理数量**。这些字段能把一条任务从入口到落库串起来。

### 108. 你会怎么设计 request_id / task_id 来串联整条链路？

同步接口以 request_id 为主，异步长任务以 task_id 为主，必要时两者关联。进入 ES、模型调用、写库阶段时都把这个 ID 带进日志，方便全链路追踪。

### 109. 如果任务执行到一半失败了，你怎么知道它失败在哪个阶段？

要靠**阶段化日志 + 进度状态记录**。不是只写“任务失败”，而是写明在检索、上下文拼接、模型调用还是写库阶段失败，以及失败前已经完成了多少处理。

### 110. 你会对 ES、MySQL、LLM、异常检测服务分别打哪些监控？

ES 关注检索 RT 和错误率；MySQL 关注连接池、慢 SQL、写入失败；LLM 和异常检测服务关注调用 RT、超时率和返回异常率。也就是说，监控要按依赖特性拆，不会只盯总接口耗时。

### 111. 如果外部 LLM 接口 RT 突然飙升，你的服务会出现什么现象？

最直接的现象是**任务整体变慢、接口超时增多、并发积压、连接占用时间变长**。如果没有限流和超时，甚至会连带把数据库连接池和任务队列也拖垮。

### 112. 你怎么做超时控制、重试和熔断？

超时要按外部服务特性单独设置；重试只针对明确的瞬时错误，而且次数有限；熔断的本质是发现下游持续异常时，**暂时停止无意义请求**，保护自己和下游。

### 113. 如果重试加多了，为什么反而可能把系统拖垮？

因为重试本质上是在**故障时放大请求量**。下游本来已经慢了，如果上游还不断重试，就会把连接、线程和队列都占住，最终放大故障。

### 114. 你有没有做告警阈值？哪些指标该告警？

应该告警的包括：**任务失败率异常、接口 P99 飙升、外部服务超时率升高、数据库连接池接近上限、磁盘/内存异常、定时任务未按时执行**。告警不是越多越好，而是要盯住关键故障信号。

### 115. 线上日志过多时，你怎么平衡“可观测性”和“性能开销”？

我会把日志分层：**关键业务日志一定打，调试型大日志只在需要时打开**。既要能定位问题，也不能让日志本身成为 IO 负担。

### 116. 如果让你讲一次线上问题排查经历，你会怎么讲？

我会按“**现象 → 初步判断 → 逐层排查 → 根因 → 修复 → 复盘**”来讲。面试时不只说最后答案，而是要体现自己是怎么从监控、日志、依赖状态一步步缩小范围的。

### 117. 你如何区分“代码 bug”“依赖故障”“数据脏问题”“配置错误”？

代码 bug 往往能稳定复现，依赖故障更多表现为外部调用异常，数据脏问题通常集中在特定样本，配置错误则经常是“同代码不同环境行为不同”。我会先看**是否环境相关、是否样本相关、是否链路外依赖相关**，再定位。

## 十、性能优化与容量问题

### 118. 你这个系统的瓶颈更可能出在 CPU、内存、数据库、网络，还是外部推理服务？

当前最可能的瓶颈通常在**外部推理服务和链路级并发控制**，其次才是数据库和 ES。因为业务链路里真正重的不是 FastAPI 接口本身，而是检索、模型调用和大批量结果处理。

### 119. 哪条链路最耗时？ES 检索、上下文拼接、向量召回、LLM 推理、写库，谁最重？

一般最重的是**LLM 推理**，其次是大结果集场景下的 ES 检索和写库。上下文拼接和向量召回相对轻，但也会在数据量上来后放大开销。

### 120. 你有没有做过批处理、并发控制、缓存、批量写入等优化？

这类系统里最常见、也最有效的优化就是这些。我的回答会是：**能批量的尽量批量，能控并发的绝不无上限放开，结果写入尽量批量化，热点环节考虑缓存或复用**。

### 121. 如果规则数量翻 10 倍，你觉得先撑不住的是哪一层？

最先吃紧的通常是**任务调度与下游依赖容量**，不是 FastAPI 路由层。因为规则多了意味着定时任务更多、ES 查询更多、模型调用更多、结果表更多。

### 122. 如果数据量翻 10 倍，ES 和 MySQL 分别会出现什么问题？

ES 可能会出现查询 RT 变高、热点分片和大结果扫描成本上升；MySQL 则会面临**结果表膨胀、索引维护开销变大、批量写入压力增加**。两者的问题性质不一样，一个偏检索，一个偏存储与查询治理。

### 123. 如果一天内任务堆积很多，你怎么削峰填谷？

我会做**任务优先级、并发上限、分时调度和批次化处理**。核心不是让所有任务一起冲，而是保证关键任务优先、整体系统不被拖垮。

### 124. 如果让你做压测，你会怎么设计场景？

我会至少设计三类场景：**接口查询压测、规则任务触发压测、长任务叠加下的依赖链路压测**。单看 HTTP QPS 没意义，因为真正重的是后面的 ES、模型和写库链路。

### 125. 你会关注哪些性能指标？QPS、P95、P99、连接数、CPU、内存、IO、错误率，你怎么解释它们？

QPS 反映吞吐，P95/P99 反映尾延迟，连接数反映资源占用，CPU/内存/IO 反映机器负载，错误率反映稳定性。对这种系统来说，我会尤其重视 **P99、超时率和依赖连接数**，因为故障往往先体现在尾部。

### 126. 如果面试官追问具体数字，但你项目没有严格打过完整压测数据，他继续追问你“那你怎么判断系统扛得住”，你该准备哪些工程性证据？

我会给出**任务执行耗时分布、上线后稳定运行情况、机器资源峰值、依赖服务可用性、批量写入和任务排队策略**。也就是说，不瞎编压测数字，但用真实上线证据说明系统是可运行、可维护的。

## 十一、代码组织、工程规范与可维护性

### 127. 你为什么没有一开始就按 controller / service / repository 分层？

因为项目初期目标是**快速打通业务闭环并上线**。当时规则管理、任务链路和算法调用变化很快，过早抽过深的层次会增加开发成本。

### 128. 现在这种代码组织方式在项目早期带来了什么好处？

最大好处是**迭代快、排查快、业务变更响应快**。核心逻辑比较集中，一个人推进效率高，适合项目早期探索和落地。

### 129. 后期为什么会逐渐暴露出耦合问题？

因为随着功能变多，规则管理、任务编排、外部调用、写库逻辑逐渐互相缠绕。项目一旦从“单人快速迭代”进入“长期维护”，这种结构的成本就会明显上升。

### 130. 如果让你现在重构，你会怎么拆目录和模块？

我会拆成：**api、service、scheduler、repository、client、model/schema、utils、config**。其中外部依赖调用单独收口，数据库访问单独下沉，避免业务层到处直接连 ES/MySQL/LLM。

### 131. 配置、常量、数据库访问、外部服务调用、任务调度、算法编排分别该放哪层？

配置和常量独立；数据库访问放 repository/DAO；外部服务调用放 client 层；任务调度放 scheduler；算法编排和规则执行逻辑放 service 层。这样职责清楚，替换实现也更容易。

### 132. 规则文件和数据库双写，为什么会带来一致性问题？

因为两份存储之间没有天然强一致保证。数据库改成功但本地 yaml 写失败，或者 yaml 已更新但数据库没更新，都会导致“界面上看到的是一套，实际执行的是另一套”。

### 133. 如果数据库更新成功、本地 yaml 写失败，怎么处理？

最基本的做法是**回滚数据库或把规则状态标记为未生效**，并记录错误日志。更好的方向是收敛成单一真源，避免长期维持双写架构。

### 134. 你有没有写单测？如果没有很多单测，原因是什么？

如果单测不多，我会实话实说：项目早期更偏业务交付，时间主要花在闭环和上线。虽然不是最佳实践，但我能清楚指出后续最该补哪些测试，而不是回避问题。

### 135. 你觉得这个项目里最应该优先补测试的是哪些模块？

优先补：**规则解析、任务状态流转、外部依赖失败处理、SQL/表名安全处理、结果导出与批量操作**。这些地方一旦出错，影响范围大，而且人工验证成本高。

### 136. 你如何看待“先把业务跑通”和“先做工程规范”之间的平衡？

我认为要看阶段。项目早期先跑通没问题，但一旦确认要长期运行，就必须**尽快补工程化**，否则早期速度会在后期变成维护负担。

### 137. 面试官如果问“你项目能跑，不代表你代码好维护，你怎么看”，你怎么答？

我会认同这个判断。我的回答是：**这套系统的价值在于它已经跑通并上线，说明我有把复杂链路落地的能力；同时我也能明确指出它在模块化、配置治理、测试覆盖上的不足，并知道下一步怎么改。**

## 十二、数据质量、人工标注与闭环迭代

### 138. 你为什么要设计人工标注闭环？

因为纯规则和纯模型都不可能一次做到完美。人工标注能把线上结果中的误报、漏报和边界样本沉淀下来，形成系统持续优化的反馈源。

### 139. 人工标注结果如何反哺规则优化、RAG 知识库和 LoRA 微调？

人工标注后的高质量样本可以回流到三个地方：**规则调优、案例库更新、训练数据扩充**。这也是为什么我觉得标注不是附属功能，而是系统长期效果提升的关键环节。

### 140. 批量修改标签时，如何保证数据一致性？

要做**明确的筛选条件、事务控制和操作审计**。不能让批量修改变成黑盒，否则一旦误操作，后果很难追。

### 141. 导出结果时，你导出的是什么粒度？原始命中、模型结果、人工标签，还是汇总结果？

这要看业务需求，但通常应该支持**明细导出和汇总导出**两种。明细包含原始命中、模型判断、标签和时间等，汇总则用于运营和统计查看。

### 142. 如果标注员改错了标签，你怎么追溯？

最好要有**操作日志**，至少记录谁在什么时间改了哪条数据，从什么标签改成什么标签。没有审计记录的话，后面很难复盘数据为什么变了。

### 143. 你有没有做过操作日志或审计日志？

如果当前版本没有很完整，我会坦诚说明。继续演进时，人工标注、批量改标签、规则修改和导出这几类操作一定要补审计日志，因为它们都是高风险操作。

### 144. 真实业务里，数据噪声和标签噪声对系统影响最大的是哪一段？

数据噪声对**前置召回和模型输入质量**影响最大，标签噪声对**微调和效果评估**伤害更大。前者让系统“看错东西”，后者让系统“学错东西”。

## 十三、结合腾讯岗位的专项追问

### 145. 你现在主要用 Python 做后端，如果团队主语言是 C++，你怎么适应？

我的优势是已经做过完整后端链路和 AI 组件接入，语言切换对我来说是实现层变化，不是思维方式重来。进入团队后我会优先补 **C++ 工程规范、内存模型、并发和服务框架**，把已有的后端设计经验迁过去。

### 146. 你觉得 Python 后端和 C++ 后端在工程上最大的差别是什么？

Python 更适合快速迭代和 AI 生态接入，C++ 更强调**性能、内存管理和工程约束**。但两者共同点是：接口设计、模块边界、异常处理、并发控制和可维护性这些后台基本功是通用的。

### 147. 如果腾讯让你写一个高性能的 Memory 检索服务，你会继续用 Python 还是会考虑 C++ / Go？为什么？

如果是原型验证和算法快速联调，我会先用 Python；如果是高性能、长期维护的核心在线服务，我会认真考虑 **C++ 或 Go**。关键不是语言偏好，而是吞吐、延迟、团队栈和后续维护成本。

### 148. 你如何理解读书 Agent 里的 Memory 构建？

我理解的 Memory 不是单纯存聊天记录，而是把**阅读内容、摘要、问答、用户偏好、引用位置、历史交互结果**组织成可检索、可更新、可控制范围的记忆层。

### 149. 读书 Agent 的长期记忆，你会存什么？原文 chunk、摘要、用户问题、回答、引用位置、标签、时间戳，这些怎么组织？

我会全部考虑，但分层存。原文 chunk 和摘要适合做检索内容层，用户问题和回答适合作为交互记忆层，引用位置、标签、时间戳、来源、用户 ID 则作为元数据层，支持过滤和追溯。

### 150. 如果 Agent 需要“根据历史阅读和对话记录做个性化推荐”，后端要提供哪些能力？

后端要提供：**记忆存储、向量检索、元数据过滤、用户画像聚合、历史会话关联、结果缓存和权限隔离**。本质上就是把“可回忆”和“可推荐”的基础设施准备好。

### 151. 你现在的 RAG 经验怎样迁移到 Agent Memory 场景？

迁移点非常直接：**案例检索 → 记忆检索，规则结果 → 用户历史，人工标注反馈 → 用户偏好和纠正信号**。虽然业务对象变了，但“存什么、怎么检、怎么过滤、怎么回流优化”的思想是一致的。

### 152. 如果让你接一个微调训练平台的后端需求，你最先关注什么？任务提交、训练状态、模型版本、日志、存储、回滚，还是权限？

我会优先关注**任务状态机、模型版本和存储/日志链路**。因为训练任务是长任务，先要保证“任务能提交、状态可追踪、产物可落地、失败可复盘”，然后再补权限和更细的平台能力。

### 153. 训练任务是长任务，你会怎么设计状态机？

至少要有：**待排队、运行中、已完成、失败、已取消**，必要时再加“资源申请中、保存 checkpoint 中、待发布”。状态机一定要清晰，不能只有一个“训练中”。

### 154. 如果一次训练耗时很长，用户页面上应该看到什么信息？

用户至少应该看到：**当前状态、开始时间、已运行时长、当前 epoch/step、最近日志、资源占用摘要、checkpoint 进度、失败原因或预计剩余阶段**。长任务最怕黑盒。

### 155. 训练失败后，后端需要保留哪些信息，才能方便复盘？

要保留：**训练配置、数据版本、模型版本、失败阶段、错误日志、资源信息、最近 checkpoint、发起人和时间**。否则训练失败就只剩一句“failed”，几乎没法排查。

### 156. 如果模型上线后效果下降，你如何支持快速回滚到旧版本？

核心是**模型版本化和配置切换**。线上服务不要直接覆盖旧模型，而是通过版本标识切换到稳定旧版，并记录这次回滚的原因和影响范围。

### 157. 如果多个用户同时提交微调任务，后端如何做资源排队和配额控制？

我会引入**队列、优先级、资源池和用户配额**。不是谁先点谁全占，而是按任务类型、租户/用户额度和资源余量调度，避免训练任务互相挤爆。

### 158. 你觉得自己最能胜任这个腾讯岗位的点是什么？是“能写后台”，还是“懂 AI 组件接入和落地”？

我会回答：**两者结合**。我不是只会调模型，也不是只会写普通 CRUD；我做过的是把 ES、MySQL、RAG、模型服务、任务调度和上线运维串起来的业务后端，这和岗位里“后台开发 + Agent 组件 + Memory/微调”是非常贴近的。

## 十四、很可能出现的“压力题”

### 159. 你这个项目能上线，但工程化一般，如果现在交给 10 个人一起维护，你觉得最危险的点是什么？

最危险的是**模块边界不够清楚，规则配置、任务执行、外部依赖和数据存储耦合较深**。一个人维护还能靠脑子记住，全员协作时就会变成理解成本和改动风险的放大器。

### 160. 动态建表这个设计，如果面试官直接说“我觉得很烂”，你怎么回应？

我不会硬辩。我会说：**从平台化角度看，它确实不是长期最优方案；但在当时的项目阶段，它帮助我快速把按规则隔离、查询和导出链路落下来。** 我知道它的边界，也知道后续应该往统一表/更标准的数据模型演进。

### 161. 如果你是现在再做一次，你最想推翻重来的一个设计是什么？

我最想重来的可能是**规则执行配置的双写和整体模块组织方式**。因为这两个点一旦定得不够好，后面会不断给配置一致性和代码维护带来问题。

### 162. 如果要求你把系统做成真正的多租户平台，你先改数据库、任务系统，还是权限系统？

我会优先改**数据模型和权限边界**。没有租户隔离的数据和权限，后面的任务系统再强也不安全；改完这两层，再去改任务调度和资源分配才有意义。

### 163. 如果某个外部算法服务一直不稳定，你会坚持编排它，还是把能力收回自己服务内？

这取决于该能力的重要性、替代成本和团队分工。如果它是核心链路且长期不稳，我会优先评估**收回本地或建立兜底方案**；如果只是可选增强能力，那就保留编排，但要做降级。

### 164. 如果让你选一个“你做得最像后台工程师而不是算法同学”的点，你会讲什么？

我会讲**把一个涉及 ES、MySQL、RAG、定时任务、人工标注、结果导出和 Docker 部署的完整系统真正做上线**。这件事体现的不是单点算法能力，而是后台工程的整体落地能力。

### 165. 如果让你选一个“你目前最欠缺、但进腾讯后最想补上的后台能力”，你会讲什么？

我会说我最想补的是**更强的系统化工程能力**，尤其是高标准的服务分层、可观测性、任务平台化和主语言 C++ 的后端实践。因为我已经做过一套真实业务后端，更清楚自己下一步不是“学概念”，而是把工程标准再往上提一层。
